## Concept 页面生成规则

本文件只定义 Concept Page 的概念提炼要求。frontmatter、页面命名、目录位置、正文来源引用、`related` 关系字段、双链格式和更新流程，以 `schema.md`、`page-types.md`、`AGENTS.md` 和 `templates/concept-page-template.md` 为准。

当整理 concept 页面时，不能直接总结原文，也不能把单篇文章观点包装成概念。必须把来源中的稳定概念、方法、模型、框架或判断工具提炼成可复用的知识单元。

### 1. 识别概念定位

先判断该内容是否真的适合进入 Concept Page。

适合进入 Concept Page 的内容通常满足以下条件：

- 它解释一个稳定概念、方法、模型、框架或判断工具；
- 它可以被多个 Reasoning Page、Topic Page 或后续资料复用；
- 它不只依赖单一事件、单一观点或一次性语境；
- 它能够回答“这是什么”“解决什么问题”“如何使用”“边界在哪里”。

不适合进入 Concept Page 的内容应转入其他页面类型：

- 重点是规定数据输入、观测口径、计算判定与 Agent 输出时，进入 Indicator Page；定义与机制可保留于 Concept，并按需互链。指标规范采用项目的专属模板与契约。

- 重点是“谁怎么看”时，保留原始资料及作者归属；满足演化或推导条件后，按 `page-types.md` 选择现有类型，不另建观点页；
- 重点是“为什么这样推导”时，进入 Reasoning Page；
- 重点是“发生了什么”时，进入 Event Page；
- 重点是“先后顺序”时，进入 Timeline Page；
- 重点是聚合一个问题域时，进入 Topic Page。

### 2. 提炼概念定义

必须用简洁、准确、可复用的语言定义概念。

定义应包含：

- 概念指向的对象或现象；
- 概念试图解决的问题；
- 概念在相关体系中的作用；
- 概念的适用范围。

推荐格式：

> 概念定义：所谓「……」，指的是在……条件下，用来判断 / 解释 / 组织……的一种概念或方法。

避免：

- 写成文章读后感；
- 写成百科式泛泛解释；
- 只复述作者原句，不做知识库语境下的工作定义；
- 把整理者推断写成来源明确提出的定义。

### 3. 压缩核心本质

必须用一句话压缩这个概念的本质。

推荐格式：

```text
概念本质 = 核心动作 + 判断对象 + 实践目标
```

示例结构：

```text
底线思维 = 先推演最坏情形 + 再判断自身承受力 + 最后决定是否进入或持有
```

这句话应能帮助后续页面快速引用本概念，而不是替代完整定义。

### 4. 拆解核心问题

必须整理这个概念在使用时需要回答的问题。

问题清单应围绕概念本身生成，而不是机械套模板。

常见问题包括：

- 要判断什么？
- 要排除什么？
- 要观察什么？
- 要比较什么？
- 要等待什么？
- 要验证什么？
- 要在什么条件下行动？
- 什么情况说明这个概念不适用？

### 5. 按问题组织核心内涵

必须拆解概念内部的关键要素，并将它们放入连贯的解释顺序，而不是平铺“要素一、要素二、要素三”。默认顺序为：

1. **为什么重要**：说明概念的用途、要解决的问题或观察价值。
2. **由什么构成或什么推动变化**：集中解释组成、条件或驱动力；若有相反方向的变化，应在同一层次比较。
3. **怎样发挥作用或产生影响**：解释作用对象、机制和后果，与上一层的原因分开。
4. **怎样理解、使用或判断变化**：说明如何综合前文、适用条件及什么证据会改变判断。

风险变量类概念可对应为“为什么关注 → 什么推动升降或变化 → 如何造成损失 → 怎样判断风险变化”。纯解释性概念、方法和工具应按自身语义改写、合并或省略不适用的问题，不强行凑齐四节，不编造来源没有支持的因果或操作规则。

每个要素需要说明：

- 这个要素是什么意思；
- 它在概念中承担什么作用；
- 它和其他要素之间是什么关系；
- 它是否来自来源明确表述，还是整理者归纳。

小节标题应直接表达读者的问题及核心回答，例如：

```markdown
### 为什么关注：它连接融资成本与资金去向

先解释作者的主要判断，再说明作用与必要条件，最后就近提供来源双链。
```

不要在同一层级混列定义、变化原因、风险后果和资料核验事项。每个小节主要回答一个问题，避免在原因与结果之间反复跳转。

不要把要素拆解写成完整因果推导。完整推导链应放入 Reasoning Page。

### 6. 转化为使用检查表

如果来源支持，应把概念转化为可执行的判断检查表。

推荐格式：

| 检查项 | 要判断的问题 | 通过标准 | 不通过时的含义 |
|---|---|---|---|
| 检查项 A |  |  |  |
| 检查项 B |  |  |  |
| 检查项 C |  |  |  |

检查表只在概念本身具有实践用途时生成。纯解释性概念不必强行生成行动检查表。

检查顺序应承接正文：先确认对象与口径，再核验解释、影响条件及反证；不重复抄录正文，也不凭空添加阈值。表中“通过”表示信息足以支持下一步判断，不代表安全、收益保证或可以买卖。

### 7. 保持精简章节结构

新建 Concept Page 只生成模板中保留的章节，不再生成以下一级章节：

- `体系位置`
- `与其他概念的关系`
- `概念边界`
- `使用场景`
- `观察信号`
- `反面误用`
- `原子化笔记`
- `相关页面`

核心关系只写入 frontmatter 的 `related` 字段。来源支持的适用条件、失效条件、观察变量或误用提醒，如确有必要，应就近写入“核心内涵”或“判断标准 / 使用检查表”，不得恢复上述独立章节。

沿用模板的六个主章节，各章分工如下；纯解释性页面可按第6节省略不适用的检查表章节：

- **一句话定义**：先说明是什么，再简述用途；必要时用一句话提示阅读主线，不堆叠审计说明。
- **概念来源**：简述来源性质、作者与整理者的贡献，不逐篇复述材料。
- **概念要解决的问题**：只列本页真正回答的问题，避免与后文重复铺陈。
- **核心内涵**：按第5节的问题顺序展开。
- **判断标准 / 使用检查表**：将理解转为核验问题，保留适用条件与反证。
- **来源**：集中详细出处、来源质量、口径歧义、历史数字和待核项；必要时使用子章节，不在正文前重复放置完整资料表。

影响正文结论成立的关键限定、作者归属与不确定性仍须就近说明，不能因集中核验细节而把正文写成无条件事实。

### 8. 标注来源依据与推断

必须区分来源明确提出的内容与整理者归纳的内容。

开头“概念来源”宜用一两段交代来源明确支持什么、整理者归纳什么以及证据性质；只有确实有内容时才分项列示，不保留空标签。详细核验信息放在文末“来源”，可按需组织为：

```markdown
## 来源

### 使用范围与来源性质

### 术语、数字与原稿歧义

### 原始材料
```

没有对应内容的子章节应省略，不另建“原文依据”主章节。正文引用已有页面时使用双链，重要观点仍就近给出来源，不只在文末罗列材料。

来源没有直接说明的概念定义、关系或使用方法，必须标注为整理者归纳或待验证。

### 9. 写作质量检查

完成 Concept Page 前，必须检查：

- 是否把概念写成了文章摘要；
- 是否把作者观点写成了稳定概念；
- 是否把完整推导链塞进了 Concept Page；
- 是否说明了概念来源和整理者归纳边界；
- 是否说明了概念解决的问题；
- 是否避免生成已从 Concept 模板移除的八个章节；
- 是否能被后续 Reasoning Page 或 Topic Page 复用；
- 是否与已有同义概念页重复。
- 核心小节是否各回答一个问题，原因、机制、后果与判断是否按顺序展开；
- 是否将相反方向的变化放在同一层次比较，避免原因与后果来回跳转；
- 是否压缩开头来源说明，将详细核验事项集中到文末，同时保留正文必要的限定与引用；
- 是否按概念类型调整问题，而不是把所有概念都套成风险变量。
