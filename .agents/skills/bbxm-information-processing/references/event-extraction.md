# 事件提取参考（Event Extraction）

## 1. 目的

定义如何从 feed 材料中提取事实性事件（Event）。

**Event** 是供下游信息处理使用的、可追溯的最小事实单元。

事件提取以当前 feed 运行中的材料为范围，不要求检索此前运行中的 Event。

本文回答：

- 什么信息可以构成 Event？
- 什么信息应保留为背景？
- 什么时候应把一个来源片段拆成多个 Event？
- 什么时候应把当前输入中的多篇报道合并为一个 Event？
- 如何表示时间、来源、歧义与信息冲突？
- 什么时候应对关键 Event 补充事件分析（Event Analysis）？

正式对象结构定义见：

`schemas/event.schema.json`

---

## 2. 核心模型

```text
原始信息
    ↓
识别事实陈述
    ↓
识别主体 / 动作 / 对象 / 时间 / 数值 / 来源
    ↓
检查该事实是否具有独立意义
    ↓
Event
    ↓
IF Event 是关键转折点
    ↓
Event Analysis（可选）
```

核心问题：

> 实际发生了什么？

---

## 3. 无状态边界

事件提取可以使用：

```text
当前 FeedContent
本次运行包含的多个来源片段
为核验当前 Event 所必需、且有来源支持的上下文
```

不要求使用：

```text
历史 Event 存储
跨轮次 Event 匹配
跨轮次生命周期状态
记忆检索
```

去重与合并在当前处理范围内完成。

---

## 4. Event 的定义

Event 描述实际发生的事情、观察、公告、测量结果或状态变化。

示例：

```text
布伦特原油从105下跌至100。
美联储将政策利率提高25bp。
微软上调计划中的AI资本开支。
美国核心CPI环比上涨0.4%。
```

事件提取应紧贴来源中的事实。

---

## 5. Event 的最低成立条件

信息满足以下条件时创建 Event：

1. 存在可识别的主体或对象；
2. 包含事实性的动作、状态、观察、公告或测量结果；
3. 有足够上下文，可以与无关信息区分。

优先提取以下事实要素：

```text
谁 / 什么
做了什么
什么时候
针对什么对象
多少
依据哪个来源
```

即使缺少某个要素，只要剩余事实仍具有独立意义，也应保留该 Event。

---

## 6. 事件与背景的区别

背景只描述上下文，不包含新的事实进展。

示例：

```text
通胀已连续数月处于高位。
```

→ 背景

示例：

```text
8月核心CPI环比上涨0.4%。
```

→ Event

本次运行提供的背景，可以作为 `context` 附在 Event 中。

---

## 7. 事件拆分

以下情况应将一个来源片段拆成多个 Event：

- 不同主体执行不同动作；
- 同一主体执行多个具有独立意义的动作；
- 事实发生时间存在实质差异；
- 同一段落包含互不相关的进展；
- 每个事实都能独立支持下游 Signal。

示例：

```text
微软上调AI资本开支指引，英伟达披露GPU订单增强。
```

通常应拆成：

```text
Event A：
微软上调AI资本开支指引。

Event B：
英伟达披露GPU订单增强。
```

---

## 8. 事件合并

在当前处理范围内，多篇报道描述同一件事实时应合并。

典型判断条件：

```text
同一主体
+ 相同核心动作
+ 同一对象
+ 大致相同的事件时间
```

合并后：

- 保留全部来源引用；
- 保留重要措辞差异；
- 保留相互冲突的数值；
- 避免重复计数同一事实。

不要为去重而查询历史 Event 存储。

---

## 9. 时间处理

每个 Event 都应按来源允许的精度保留时间。

建议精度值：

```text
exact
minute
hour
day
week
month
unknown
```

不要根据宽泛的时间表述推断精确时间戳。

---

## 10. 来源追溯

每个 Event 必须能够追溯到来源材料。

下游追溯链应支持：

```text
Theme
→ Cluster
→ Signal
→ Event
→ Source
```

本次运行中描述同一 Event 的多个来源，应保留在 `source_refs` 中。

---

## 11. 信息冲突

本次运行中的来源存在冲突时：

```text
保留双方主张
↓
标记冲突
↓
保留来源
↓
必要时调整置信度
```

证据不足时，不要悄然消解事实冲突。

---

## 12. 置信度

建议取值：

```text
high
medium
low
```

置信度反映事实的可靠性。

可以考虑：

- 一手来源还是二手来源；
- 来源独立性；
- 信息完整性；
- 内部一致性；
- 当前处理范围内可见的跨来源确认。

置信度不代表市场重要性。

---

## 13. 事件分析（Event Analysis）

事件分析是可选步骤。

仅当 Event 是有意义的转折点，且理解它需要由本次运行证据支持、有明确窗口的前后比较时使用。

典型示例：

```text
央行决策
通胀数据发布
财报发布
业绩指引变化
政策公告
重大地缘局势升级
重大供给中断
```

---

## 14. 事件分析的核心模型

```text
核心问题
    ↓
事件前预期
    ↓
关键事件
    ↓
实际结果与预期对比
    ↓
预期差
    ↓
即时反应
    ↓
再定价
    ↓
发生变化的变量
```

核心问题：

> 围绕这一事件，相对于此前已有预期，什么发生了变化？

---

## 15. 事件前预期

当前 feed 或必要的有来源核验材料提供相关信息时，记录事件发生前已知、已预期或已计入价格的内容。

可能包含的字段内容：

```text
市场预期
主流叙事
已计入价格的条件
```

示例：

```text
市场一致预期CPI环比上涨0.2%。
联邦基金期货定价反映两次降息。
所提供的报告显示，AI资本开支预期此前已经上调。
```

事件前预期必须有来源支持。

---

## 16. 实际结果与预期对比

对于关键 Event，比较：

```text
预期
vs
实际
```

示例：

```text
预期CPI：0.2%
实际CPI：0.4%
```

二者差异可能形成 `surprise`。

---

## 17. 预期差（Surprise）

预期差描述预期与实际兑现之间的差别。

建议方向值：

```text
positive
negative
mixed
none
unknown
```

建议幅度值：

```text
small
moderate
large
extreme
unknown
```

预期差方向应相对于所观察的变量或问题解释。

---

## 18. 即时反应与再定价

将最初可观察到的反应与更广泛的再定价分开。

可能观察到：

```text
价格反应
收益率反应
汇率反应
信用反应
预期变化
分析师预测修订
叙事变化
资金流变化
```

再定价回答：

> 事件发生后，哪项预期或变量被重新评估？

示例：

```text
降息预期 ↓
长期收益率 ↑
AI需求预期 ↑
通胀预期 ↑
```

---

## 19. 发生变化的变量

事件分析应识别在所观察事件窗口内，定价或预期发生变化的变量。

这些变量随后可以形成再定价信号（Repricing Signal）。

示例：

```text
rate_cut_expectation ↓
long_term_yield ↑
```

---

## 20. 事件分析的时间轴阶段

可选阶段标签：

```text
pre_event
key_event
immediate_reaction
repricing
confirmation
reversal
follow_up
```

这些标签描述本次运行证据所覆盖的有限事件窗口。

它们可以复用于同次运行中的 Cluster 时间轴。

---

## 21. 事件层的职责边界

事件提取与事件分析可以描述：

```text
事实
预期
预期差
可观察的再定价
```

不应判断：

```text
风险等级
投资吸引力
交易方向
估值结论
没有所提供证据支持的历史持续性
```

---

## 22. 质量检查

接受一个 Event 前，检查：

- 是否属于事实？
- 是否具有独立意义？
- 主体是否可识别？
- 动作或变化是否清晰？
- 时间是否如实表达？
- 来源是否可追溯？
- 是否应拆分？
- 是否与当前处理范围内的信息重复？
- 是否保留了冲突？
- 是否确实需要事件分析？
- 若使用事件分析，预期与再定价是否有证据支持？
- 处理是否避免依赖历史存储？

---

## 23. 输出原则

好的 Event 应当：

> 真实、可追溯、时间明确、粒度足够独立，并适合下游提取 Signal。

关键 Event 还可以包含：

> 基于本次运行可用证据，在明确窗口内重建事件前预期、实际兑现、预期差、反应与再定价。
