# 信息归纳 Skill

## 1. 定位与触发边界

将输入整理为可持续核验的“事件数据库 + 市场反应数据库”，回答：发生了什么、改变了什么变量、谁的行为可能改变、风险如何变化，以及后续如何确认或推翻判断。

保持显式调用边界：用户点名“信息归纳”“信息归纳技能”“信息归纳报告”、本技能标识，或要求“按冰冰小美金融信息归纳框架”处理材料时启用。旧称“信息过滤流程”“信息过滤技能”“信息过滤报告”和“按信息金融意义框架过滤”作为兼容口令，执行本归纳流程。

仅提供新闻、公告、研报、帖子并说“分析一下”“总结一下”“有没有用”“能不能交易”，不自动启用。通过其他技能分流时也须满足这一边界。用户直接要求风险识别、产业研究、估值或交易复盘，按对应任务处理。

技能显示名为“信息归纳”；目录和 `name` 保留 `bbxm-information-filter-flow`，兼容已有调用。

## 2. 每次运行先读取的依据

1. 读取项目根目录的 `AGENTS.md`、`schema.md`、`page-types.md`、`index.md`。
2. 必须重新读取 [[wiki/concepts/冰冰小美-framework-金融信息归纳框架|金融信息归纳框架]]（相对技能目录：`../../../wiki/concepts/冰冰小美-framework-金融信息归纳框架.md`），以最新正文为方法依据，不用记忆或本技能摘要代替。
3. 读取同目录 [template.md](template.md)，按其中顺序输出。
4. 只有需要细分金融/非金融信息时，按需读取 [金融信息类型字典](financial-information-types.md) 或 [非金融信息类型字典](non-financial-information-types.md)。字典仅补充分类，不替代主框架的五层归纳、建档级别和证据要求；字典内旧的评级、过滤或处理建议不作为本技能结论规则。

框架路径不存在时，先在 `wiki/concepts/` 查找同名或近义页并核验内容；无法确认则说明缺口，暂不声称已按该框架完成。框架中的作者归属、引文或来源字段尚未补全时，只称“当前 Wiki 框架的整理”，不能升级为已经核实的作者原话。报告记录框架路径、实际读取日期和证据截止时间。

## 3. 准备：整理输入与信息源

- 单条信息拆分为可核验的事件或主张；多条信息分别编号，合并同源重复转载，并保留各来源与事件的关联。
- 区分事件发生时间、首次发布时间、数据所属期、读取时间。发布日期不能自动当成现实状态切换的节点。
- 每项标注事实、发布者观点、分析推测或待验证；未经核验的传闻只能记为线索。
- 按来源分类：市场数据、机构数据、用户数据；按功能分类：风险类、交易类、分析类。允许多选或“其他/待确定”，并说明依据。
- 按主框架选择信息源建档级别：核心源（长期建档）、专题源（按研究需要建档）、观察源（试用建档）、线索源（通常不独立建档）。分别说明连续性、原始出处、相关性与可验证性；级别不是可信度分数，也不等于交易优先级。
- 对观察源记录立场、利益关系、纠错情况；未知动机写“未知”，不推定荐股、接盘等意图。线索源优先回溯原文。
- 涉及当前行情或风险方向时核验对应窗口的一手来源和数据；无法访问时记录具体失败原因与缺口，不编造数值，不把旧数据当成当前值。

## 4. 五层归纳流程

### 第一层：事件节点——发生了什么

记录事件编号、主体、发生时间、原始出处、核验状态与具体事实。节点需要写清“状态 A → 状态 B”及支持证据；只有消息发布、没有状态变化证据时，写“事件已记录，节点待验证”。保留预告、落地、执行、结果之间的区别。

### 第二层：影响——改变了什么

列出受影响的金融或产业变量，如流动性、信用、通胀、利率、融资环境、供需、价格、成本、产能。对每条路径写“事件 → 变量 → 影响对象”、方向、时滞、适用条件和证据。区分已观测变化与待验证传导假设；不能从政策目标直接推定企业兑现。

本节面向非专业读者，采用“先白话解释，再列证据表”的顺序：

1. 开头用一两句话回答“这件事会怎样改变企业的生意或普通人的处境”，明确谁可能多花钱、少赚钱、更难借钱、改变生产或消费。按材料选择相关变化，不强凑所有影响。
2. 对每条主要影响写一个白话小标题和两三句解释，逐步讲清“发生什么 → 谁受到影响 → 为什么会改变成本、收入或做法”。不要只给抽象变量、事件编号或箭头链，让读者自己补齐逻辑。
3. 必要术语首次出现就解释，例如“履约支出”是“为满足规定需要花的钱”，“技改投入”是“改设备、改生产方法要花的钱”；根据当前语境解释，不能用另一个术语替代。
4. 每条解释末尾说明“已经看到什么、还没看到什么、什么条件下才会发生、可能多久体现”。未知时间写“时间待验证”。下游影响逐环检查，不从成本增加直接跳到减产、涨价或股价上涨。
5. 当金额或公式不易理解时，可给一个简短算例：先标“假设例子，非真实企业数据”，写清单位和计算，再用一句话解释结果代表什么、没有包含什么。没有必要时不用算例；假设数字不得进入事实表或风险结论。
6. 表格用于整理与白话说明一一对应的证据，不能代替解释；表后用一句话收束“现在最需要查清什么”。读者不看表格，也应能理解主要影响及其不确定性。

写法示例（仅演示条件推演，不作为本次事件事实）：不要只写“履约成本上升 → 利润承压”，应写“如果企业需要额外购买配额，就要多花一笔钱。在售价和其他成本不变时，这笔钱会减少利润。目前还需查清它缺多少配额、需要花多少钱。”

### 第三层：市场行为——谁会如何行动

识别相关机构、散户、外资、游资、企业等参与者，说明行为变化的机制，并分别列出预期行为、实际行为和证据。缺少持仓、资金、成交或经营行动证据时写“待验证”，不能用股价涨跌替代投资者身份识别。允许信息尚未改变行为，不强行归为机会。

### 第四层：金融反应——风险方向和程度

记录价格、成交、资金、信用或波动等可观察反应，给出当前窗口、比较窗口、指标口径、来源和变化。区分风险水平（高/中/低/待验证）与风险方向（增强/持平/减弱/重新增强/证据不足）；高位不等于持续增强，单日上涨不等于风险减弱。

只有当前与比较窗口、可观察证据、传导机制齐备，并检查反证后，才判断方向。“重新增强”还需要此前减弱的时间段和证据。缺口存在时结论为“证据不足”，可以保留条件推演，但不得据此给出确定的参与或回避判断。价格同步变化只说明相关，不足以证明事件造成该反应。

### 第五层：长期跟踪——怎样确认或推翻

为有连续观察价值的事项建立风险监测对象：对象编号、跟踪范围、关联事件、风险假设、关键指标及口径、数据源、基准值及日期、最新值及日期、确认条件、反证/失效条件、检查频率或下一事件节点、当前结论和证据缺口。

用事件编号连接两张表：

- 事件时间线：发生时间、状态变化、事件影响、新证据、原判断及修订理由。
- 市场反应记录：观察时间窗、关联事件、指标变化、参与者行为、风险判断、反证与其他解释。

条件和频率属于本次跟踪设计，需说明依据；未经支持不编造通用阈值。没有历史或后续数据时先建立基线并标“首次记录”，不虚构时间线。后续更新保留旧判断，再追加新证据与修订原因，避免事后改写。

## 5. 输出与保存

最终使用 [template.md](template.md) 的完整结构，缺项保留并写“待验证”“证据不足”或“不适用”及原因。用户明确要求简版时可以压缩，但保留五层链条、来源、证据边界和下一步验证条件。多事件可在各节分行列出，通过事件编号对应，避免混合不同事件的证据。

结论以信息如何进入研究和持续观察为主：继续核验、建立基线、持续跟踪、修订判断或归档。参与/回避仅作有证据支持的方向观察，不将信息源级别、利好消息或风险减弱直接转换成买卖、仓位和估值结论。

默认在对话中交付归纳表。“长期跟踪”表示提供跟踪设计，不表示已经创建定时任务或会自动更新。用户要求保存、建档或更新已有档案时，再按项目规则执行：

- 先检索已有记录，复用同一对象及事件编号；库外原始资料先保存到当前库 `sources/`，分析不写入原始资料层。
- 具体标的的事件、行情反应、研报与监测对象进入 `workbench/`；写入前读取 `workbench/AGENTS.md`。
- 可复用知识满足准入及回流门槛后才进入正式 `wiki/`，并使用对应页面模板；不为普通个股公告建立正式事件页或问题页。
- 按落盘范围更新相应索引与项目 `log.md`，使用带显示名的 Obsidian 双链引用已有页面和库内来源。

## 6. 交付前检查

- 五层是否齐全，事实与假设是否分开？
- “影响”是否先用白话说明谁会受到什么影响、为什么、哪些条件尚未满足，再列证据表？术语是否解释，假设算例是否与实际数据分开？
- 是否把发布时间误作状态变化，把预期行为误作真实行为？
- 风险结论是否具备窗口比较、来源和反证？缺证时是否降为证据不足？
- 事件与市场反应是否通过编号关联，监测对象是否有确认及失效条件？
- 是否实际读取最新框架并说明来源缺口，是否避免无授权的保存或自动监控承诺？

## 技能变更记录

修改本技能的说明、模板、字典、配置或其他随附文件后，在同目录 [log.md](log.md) 追加日期、版本变化、修改原因、涉及文件、具体变更和验证结果；版本未调整时明确写“版本号不变”。保留已有记录，不补写未经核实的历史。业务报告不属于技能变更；项目根 `log.md` 另记维护概况。
