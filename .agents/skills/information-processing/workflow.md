# 信息处理工作流

本文件承接 [SKILL.md](SKILL.md) 的能力与输入输出约定，集中维护执行细则。

## 执行准备

### 方法与输出依据

1. 读取项目 `AGENTS.md`、`schema.md`、`page-types.md`、`index.md`，按写入范围遵守 Wiki / Workbench 规则。
2. 每次完整读取 [信息的金融处理](../../../wiki/concepts/冰冰小美-framework-信息的金融处理.md)，以其中“信息处理系统”“信息处理skill的开发”和 Output Schema 为本技能契约。页面前半部保留的五层旧框架仅作背景，不恢复旧技能的五层报告和风险方向输出。
3. 读取 [字段与证据约定](references/output-contract.md) 和 [结果结构模板](references/result-template.json)。模板忠实转录页面的 JSON 字段；[JSON Schema](references/output-schema.json) 只落实这些字段的结构校验，不另立业务输出。
4. 获取信息前读取 [来源路由](references/source-routing.md) 的适用条目。路径失效时搜索真实文件；若页面更新导致契约不同，先按当前页面调整输出并说明本地校验资源需要同步，不以旧模板覆盖页面。

页面仍有旧标题、空来源字段及待完善项，使用时称“当前项目框架”，不把其中全部设计归为已核实的作者原话。说明框架实际读取日期和本次截止时间。

### 模式与范围界定

| 模式 | 输入与处理范围 | 边界 |
|---|---|---|
| feed | 一份或多份晨报、文章、公告或用户材料；从材料提取与目标有关的 Event | 默认围绕输入处理，必要时回源核验；不自动扩成全市场扫描。无显式目标时可将“本批材料涉及的事件”作为目标并说明。 |
| monitor | 预设观察对象、来源清单、上次成功扫描截止点或用户指定窗口；获取本轮新增信息 | 本次执行一轮。没有配置时先读取用户指定配置；仍缺失则询问必要对象/来源，不把全部指标表视为默认订阅。首次运行没有历史基准时只建本轮基线，不声称已经去除历史重复。 |
| target | 具体公司、产业、宏观变量、事件或其他对象；动态路由并收集相关信息 | 先消除对象身份歧义。使用能覆盖核心问题的来源，不自动升级成研报或交易建议。 |

同一请求含多个入口时，按主动作选一个模式，其他材料作为补充输入；若观察问题和时间窗口相互独立，分别输出完整结果，不混成一个归纳簇。

确定对象、核心问题、时区、截止时间、地域/市场和具体观察项。用户给定范围优先；未给定时，feed 使用材料可确认的覆盖期，target 可暂按最近7个自然日并声明，monitor 使用已确认扫描窗口。重要歧义需要澄清；可以先处理不依赖回答的材料。历史任务排除截止时点之后才获知的信息。

## Step 1. 信息获取

1. **Targeting**：按模式确定观察目标与相关性标准，允许用于建立基准、确认状态或反驳假设的材料进入。
2. **Source Routing**：由“观察对象 → 所需证据 → 原始发布者 → 获取渠道”选择来源。按主框架区分核心源、专题源、观察源、线索源；建档级别不等于可信度评分。来源提供的事实、解释、预测分别记录。
3. **Scope**：落实时间、对象、地区和指标口径。获取当前信息须核验当期来源；逐个记录来源访问成功、失败、缺项和覆盖范围。来源不可用时可回退同一事实的原发布机构或有出处转载；不能编造内容。
4. **拆解 Event**：分离一条材料中的独立事件。Event 是特定时间内某主体发生、执行、发布或出现的一项可记录变化；保留主体、动作、对象、时间、数值和单位，以及可定位原文的 `raw_ref`。
5. **筛选与去重**：合并同一事件的转载；发布、实施、延期、撤销是不同状态变化，可分别建 Event 并沿时间组织。复用已有事件标识；重复扫描无新增事实不生成新事件。晚到信息使用真实事件时间排序，不能把获取时间冒充发生时间。

没有证实的传闻若确有观察价值，只能记录“某来源发布某说法（未核验）”这一传播事件，不能把传闻内容写成已经发生的经营或政策事实。纯预测同理。无法确定发生时间时用 `null`，另保留已知发布时间。

## Step 2. 信息结构化

1. **定时间窗口**：用“核心问题 + 关键事件 + 事前预期 + 事后重新定价”组织语境。尚无关键事件、可验证事前预期或事后反应时保留 `null`；不能从后来结果倒推当时预期。
2. **结构化 Event**：填写 domain、hierarchy、observation_objects。金融因子只记录材料直接支持的变量或有依据的描述性变化；不能凭政策标题推定利率、利润或风险方向。市场反应只录实际观察到的指标，缺失为 `[]`。
3. **建立时间轴**：`timeline.event_ids` 按 `fact.time` 排列；同一时间沿明确先后顺序或稳定输入顺序，时间不明的事件置后并说明。时间轴引用本结果事件，不复制事实、不伪造连续性。

多来源共同支持一个事件时，`raw_ref` 指向一份列明全部出处的证据记录；金融因子、市场反应与预期的依据也要能从该记录定位。未保存时可使用本轮清晰标号的材料/证据段落；不得伪造本地文件路径。

## Step 3. 信息归纳

1. **找事件密集区**：同时检查时间集中、问题相关、信息增量。多个转载不算多个事件；时间接近不代表属于同一问题。不满足聚类条件时 `clusters: []`，不为填模板强造密集区。
2. **提取共同现象**：寻找同向变化、重复状态或行为，用接近事实的一句话描述；每个现象指向支持它的事件，同时保留不一致事件。
3. **提炼共同变量**：从共同对象、共同机制向上抽象，再检查对各事件的解释力。变量是描述性观察变量，不能替换为“买入机会”“风险增强”等领域结论。依据不足时保留“候选”措辞或空数组，说明反例及解释缺口。
4. **形成归纳结构**：每簇保留核心问题、时间跨度、事件、现象、变量及归纳陈述的引用关系。归纳陈述写明已观察事实、未覆盖部分和待验证解释，不能以相关性声称因果已成立。

## 交付与验证

- 标准结果为一个严格符合页面 Output Schema 的 `InformationProcessingResult` JSON 对象；字段齐全，未知标量用 `null`，无内容列表用 `[]`，不保留模板空事件。
- 同时提供简短的范围与证据说明：模式、窗口/时区、框架版本依据、实际扫描来源、失败与未覆盖项、首次基线或新增扫描、主要事实和缺口。说明放在 JSON 外；不得擅自增加 `risk_assessment`、`recommendation`、`coverage` 等字段。用户要求纯 JSON 时仅交付 JSON；当前1.0结构无法完整承载运行诊断，缺失内容保留空值，不增设诊断字段，也不能据空结果声称完整覆盖。
- 输出为空时区分“范围内未发现新增事件”和“未能取得来源”。未覆盖或失败的来源不能被标记为已完成；monitor 不把失败来源的扫描进度推进到当前截止点。
- 用户要求风险识别时，交给 `bbxm-risk-identification`；要求已识别风险演化时交给 `bbxm-risk-evolution-monitoring`。本技能只交付结构化信息，不自动运行下游分析。
- 默认对话交付 JSON；明确要求文件或上游流程已授权保存时写入指定位置。具体标的结果进入 Workbench，先读其规则；正式 Wiki 只接收符合项目准入的可复用知识。原始资料保存与索引日志遵守项目要求。
- monitor 是单轮扫描模式。周期运行仅在用户明确要求后使用可用的调度工具配置，不把观察频率写成已启动自动任务。

保存 JSON 后运行 `python scripts/validate_result.py <结果文件>`（脚本路径相对于本技能目录），检查结构及跨对象引用。此校验不证明事实真实或机制成立；仍须逐项核对来源与归纳是否超出证据。
