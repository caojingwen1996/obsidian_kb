# T03 任务编排与可靠性架构

> V0.6 · 2026-10-24 · 面向L0的可靠执行设计；与[S01功能设计](../../03-%E7%B3%BB%E7%BB%9F%E5%8A%9F%E8%83%BD%E6%9E%B6%E6%9E%84/S01%20%E5%85%AC%E5%85%B1%E8%BF%90%E8%A1%8C%E8%83%BD%E5%8A%9B%E5%8A%9F%E8%83%BD%E8%AE%BE%E8%AE%A1.md)配合。

## 1. 两种状态的边界

PostgreSQL记录业务接收、候选状态、复核、正式提交和交付回执；Temporal推进活动、计时与重试。S01展示运行状态但不得把工作流成功自动映射为候选成功。业务结果与工作流进度不一致时，以提交回执核对并修复投影。

工作流逻辑分为资料处理、F02资料批次及候选子处理。候选可并行，数量与并发受配额限制；同一事件提交由修订校验协调。首切片采用独立工作流与数据库启动意图；父抽取工作流不负责保活候选执行，也不形成第二个业务状态源。

## 2. 可靠启动

1. 接收事务写Operation和启动意图，返回持久接收回执。
2. 中继租约领取意图，用由业务执行身份导出的确定workflow_id启动；中继崩溃可再次领取。
3. 启动响应丢失时先查确定身份及业务回执，再确认已有执行或恢复；不能用随机workflow_id重启。
4. 工作流历史过期时，先查持久处理/提交记录。已完成返回原结果；未完成经恢复策略分配新的执行代次，沿用业务身份并拒绝旧执行提交。

数据库中的启动意图不能在真正接收前删除。中继“已发送”不等于业务完成。

## 3. 重试与复核

| 情况 | 恢复点 | 保留/失效规则 |
| --- | --- | --- |
| 获取原件网络故障 | F01 Step 2 | 保留来源及命令身份 |
| 已保存但交付失败 | F01 Step 6 | 不再读取、标准化或新增版本 |
| 模型超时/限流/服务故障 | 当前AI节点，有界退避 | 输入和任务包不变，每次新attempt_id |
| 输出截断/Schema失败 | 当前任务重试或待复核 | 不接受半套候选集合，不写无事件 |
| AI-04发现身份冲突 | F02 Step 2 | Step 3～5旧上下文建议及审批失效 |
| Event修订已变化 | 最早受影响节点 | 重新读取历史、增量/评级依据，不能强行覆盖 |
| 提交成功但回应丢失 | 查询commit_key回执 | 不再模型分析或二次提交 |
| Outbox送达无回执 | 原message_id重投 | 不重跑Step 1～6 |

重试次数、退避、调用超时与总预算由固定运行政策配置，并在开始时快照；未确定数值列为部署前门槛。预算耗尽进入recoverable或review，记录reason_code与resume_step。

## 4. 取消、迟到结果与栅栏

每个可恢复处理使用execution_generation，每个候选建议使用proposal_generation。取消或重新准备上下文先在数据库改变有效代次；模型响应返回时及正式提交事务内都检查代次、输入摘要和取消状态。只有事前检查不够：提交必须对同一状态记录加锁或条件更新，保证取消与提交有唯一先后。

技术执行代次变化不自动改变proposal_generation或commit_key：输入与决定未变时保留原业务提交身份。恢复先查候选completed/dismissed及所有持久处理回执，已完成返回原结果；不能用新执行代次绕开旧回执再次写入。只有有效业务上下文/决定变化才形成新建议代次，且已正式提交结果须走授权修正。

若提交已先完成，取消仅停止未提交工作；不能声称撤销已生效事件。迟到模型结果归档为superseded，不进入正式区。复核决定绑定proposal_digest与方法/上下文版本，旧复核不能批准新建议。

## 5. 独立候选与批次结束

抽取集合一次固定后，逐候选维护状态。一个候选已提交、另一个故障时，前者不回滚，资料批次显示partial并给出未完成项；恢复只处理未完成候选。只有全部候选为completed或授权dismissed才使批次completed；计数按F02数据§3计算，技术失败/取消不计为已处置。交付状态单列；不能靠批次失败触发全量重跑。

授权重算创建新analysis_key并关联父处理；运行身份独立，但仍核对已有 Fact、Event、关联和评级的业务去重，不强制复制 Fact。[F02数据设计](../03-%E6%A8%A1%E5%9D%97%E6%8A%80%E6%9C%AF%E8%AF%A6%E7%BB%86%E8%AE%BE%E8%AE%A1/L0-%E4%BF%A1%E6%81%AF%E5%A4%84%E7%90%86%E5%B1%82/F02-%E4%BA%8B%E4%BB%B6%E7%AE%A1%E7%90%86/%E4%BA%8B%E4%BB%B6%E6%95%B0%E6%8D%AE%E4%B8%8E%E7%8A%B6%E6%80%81%E8%AE%BE%E8%AE%A1.md)定义具体状态；[故障方案](../05-%E6%9E%B6%E6%9E%84%E6%B2%BB%E7%90%86%E4%B8%8E%E9%AA%8C%E8%AF%81/%E6%9E%B6%E6%9E%84%E9%AA%8C%E8%AF%81/%E6%95%85%E9%9A%9C%E6%81%A2%E5%A4%8D%E9%AA%8C%E8%AF%81/L0%E6%95%85%E9%9A%9C%E6%B3%A8%E5%85%A5%E4%B8%8E%E6%81%A2%E5%A4%8D%E9%AA%8C%E8%AF%81%E8%AE%BE%E8%AE%A1.md)验证每个崩溃窗口。

## 6. Workflow、Activity与队列的具体划分

由资料保存、集合抽取和候选处理三种独立恢复边界定义以下工作流；均需按新契约实现。

| Workflow | workflow_id规则 | 输入 | Activity顺序 |
| --- | --- | --- | --- |
| MaterialIngestionWorkflow | l0/material/{operation_id}/{execution_generation} | operation_id、generation | checkSource → acquireRaw → normalizeText → decideVersion → saveMaterial → ensureVersionDelivery |
| EventExtractionWorkflow | l0/extract/{processing_id}/{execution_generation} | processing_id、generation | prepareExtraction → executeAI01 → validateExtraction → acceptCandidateSetAndIntents → verifyDispatchProgress |
| EventCandidateWorkflow | l0/candidate/{candidate_id}/{execution_generation} | candidate_id、generation | prepare/execute/validate AI02 → 身份复核 → AI03 → AI04 → 评价触发判断 → 必要AI05及程序计算 → 最终复核 → commitCandidate → ensureEventDelivery |

首切片只设`riskhot-l0-io`和`riskhot-l0-model`两类Activity任务队列：前者处理数据库/对象/程序计算，后者处理模型请求。Workflow注册在`riskhot-l0-workflow`队列，IO与模型Worker分别轮询上述Activity队列；业务候选不是一个长HTTP请求。Workflow历史只传ID、摘要和小状态，正文和模型响应存ArtifactStore，避免把完整资料塞入每次历史事件。

AI-01接纳候选集合的事务同时插入每个候选的execution_intent，0候选不产生候选工作流。资料抽取工作流可在成功分发后结束，批次业务完成仍以processing_runs汇总为准；后续候选不依赖父Workflow一直等待。中继从意图逐个可靠启动，不因父进程崩溃漏掉部分候选。候选Workflow在提交回执和适用交付意图确认持久后可结束；dismissed凭NOT_EVENT回执结束，不等待不存在的事件交付；接收回执由Relay/交付表独立追踪，交付失败不得触发该候选Workflow重新分析。

## 7. 单节点重试与恢复算法

每个Activity进入时先读数据库终态及有效非事件决定：dismissed直接返回NOT_EVENT回执；有待执行的disposition决定则停止普通AI/提交路径，优先执行IO Worker的处置分支。复核signal、60秒轮询和恢复对账均可发现该决定，处置失败有界恢复，不把待处置误报为完成。模型返回接纳时也重查此守卫，终结时增加执行代次以拒绝迟到结果。随后再读数据库有效代次与节点结果：已succeeded/skipped且输入摘要相同则回原结果；输入改变则拒绝复用。执行外部调用后，条件更新节点结果；旧执行只能留存attempt，不能推进candidate_step_results。

技术Activity可由Temporal进行有界重试；模型Activity设置框架自动重试为1次，业务重试由model_attempts预算控制，避免“Temporal三次×适配器三次”放大调用。HTTP适配器不再内置额外重试。调用前在 IO Worker 的短事务中锁 owner、检查剩余次数/截止时点并预留 attempt_no，事务成功后才把调用交给模型 Worker。请求工件须已保存；超时和未知状态也消耗次数。并发执行不能各自读取旧计数后突破预算。调用后保存响应和结束原因，再由 IO Worker 检查接受代次。

| 参数 | 首切片验证默认值 | 作用 |
| --- | --- | --- |
| 单次模型HTTP超时 | 120秒 | 中止等待，不认定供应方未执行 |
| 模型Activity单次执行上限 | 180秒，长活动每20秒心跳 | 给响应保存和校验留余量；具体SDK支持由PoC核验 |
| 每节点模型尝试 | 最多3次，总预算10分钟 | 仅超时、429、可恢复5xx等可重试；结构/证据错误转复核或显式修正 |
| 模型重试间隔 | 首次30秒、第二次120秒，受剩余预算截断 | 避免持续故障立即打满 |
| 数据库/对象短Activity | 最多5次，2秒起指数退避，上限30秒 | 幂等前提下处理临时故障 |
| 活动并发 | 模型2，IO 8 | 每个验证环境单个模型Worker组的初始上限；扩实例前需共享配额方案 |
| 复核唤醒对账 | 收到signal立即检查；无signal每60秒读一次决定 | signal只唤醒，不是授权；无决定不自动通过 |

这里的数值是可调整的验证参数，不能改写成生产SLO。资料超长、候选数超限或模型窗口不适配都在调用前阻断；不是增加重试次数能解决的问题。

### 7.1 F01 的复核与恢复执行

MaterialIngestionWorkflow从material_operations读取固定输入工件、state、execution_generation、decision_generation和resume_step；不从F02 processing/candidate读取恢复身份。每个Activity接纳结果及保存时重检操作代次。复核APPROVE_PLAN/RECOMPARE或授权processing恢复在同一事务保存操作变更、命令回执及新的执行启动意图，workflow_id沿用l0/material/{operation_id}/{execution_generation}。启动回应丢失按该ID和数据库回执核对，禁止随机新ID。

保存前身份冲突暂停到F01复核案件；批准后从Step 4验证固定计划，再执行Step 5，不能将批准直接当saved。依据失效时旧审批退出，程序可执行只准备新案件的Step 4，不得自动保存；新的复核决定才提供提交资格。REJECT_INTAKE持久化拒绝并推进执行栅栏，旧Activity不能写入。技术恢复只改变执行代次；输入/比较依据改变才推进决定代次。确定的恢复矩阵与原子门槛见[F01数据第7章](../03-模块技术详细设计/L0-信息处理层/F01-信息接入与标准化/关键接口与数据设计.md#7-f01-复核与恢复契约)。

saved操作的Step 6由Relay独立续接，无须重启资料工作流。授权delivery恢复保留原消息，使用material_deliveries.recovery_generation及window_start_attempts建立有审计的有界投递窗口；累计attempts保持增长，原租约失效。F01此窗口最多沿用第8章的10次验证默认值，普通自动重投无权开启新窗口。恢复预算与运行资格不足则保持待处理。F01的Relay领取/失败/确认事务按material_deliveries → platform.message_deliveries锁序同步状态，不反向取得operation锁；该顺序也适用于人工恢复。

## 8. 租约中继与交付算法

中继每秒扫描到期execution_intents/message_deliveries，每批最多20项；短事务用行锁跳过已锁记录，写lease_token及60秒lease_until并递增attempts，再提交事务。随后在事务外启动Workflow或调用接收端。长操作每20秒按当前token续租；回应只允许持有当前token的实例更新。

启动使用确定workflow_id。已启动错误进入“读取既有执行与数据库回执”路径，不另造随机ID。接收端Inbox成功而发送端超时，原message_id重投回原receipt。投递尝试采用可配置退避，首切片最多10次后recoverable，恢复命令沿用原消息；正式业务已保存，不反向退回AI分析。

接收回执先落PG，再signal唤醒Workflow。signal丢失由定时数据库读取恢复；多次signal不多消费复核决定。超时/取消不删除意图或回执。

## 9. 取消与提交竞争的确定顺序

涉及用户权限的命令先按 T06 取得权限代次锁并校验；取消命令随后锁processing再锁candidate，增加execution_generation并记录取消状态；commitCandidate采用相同锁序，在锁内核对代次和审批。取消先完成则提交失败；提交先完成则回原CommitReceipt，取消只影响剩余工作。模型Activity不能用“调用前尚未取消”替代提交时检查。

恢复仅失败执行时可增加execution_generation，但保留proposal_generation、commit_key及已成功节点；上下文/业务决定改变才增加proposal_generation并使后续结果失效。已completed或dismissed的candidate不能通过重试变成新提交资格；需要修正时走新的授权业务操作。

NEW提交因召回集合版本变化返回IDENTITY_SNAPSHOT_STALE时，按[F02数据设计第7.2节](../03-模块技术详细设计/L0-信息处理层/F02-事件管理/事件数据与状态设计.md#72-不同候选并发新建的集合版本校验)先持久失效旧建议与审批，再按resume_step=2恢复原候选。提交Activity不得仅替换epoch后自动重试；数据库锁超时才按原身份进行有界技术重试。控制记录提交后回应丢失，由数据库恢复点和代次对账，不再递增决策代次。新输入、模型调用及复核均在集合锁外；既有模型预算不因冲突清零，不能恢复时保持待处理。

## 10. 数据库与工作流之间的恢复对账

对账器每60秒分页扫描已持久受理且未终态的业务记录，并比较 execution_intents 与 Workflow 状态。每次最多100项，游标续扫；不从Temporal历史反向构造新业务对象。

| 检查结果 | 恢复动作 | 禁止动作 |
| --- | --- | --- |
| 有启动意图，工作流未受理 | 重新领取原意图，使用原 workflow_id 启动 | 随机新建运行身份 |
| 工作流终止，业务未完成 | 按运行政策记录 recoverable；授权恢复时锁业务行、增加执行代次、写新意图 | 把工作流结束直接标为业务成功 |
| 业务已完成，工作流仍等待 | 回传原提交回执并结束执行 | 重新分析和写事件 |
| 已接纳建议但响应保存后进程崩溃 | 校验输入摘要、有效代次与已保存建议后续接 | 不检查就重复调用模型 |
| 模型调用状态未知 | 保留未知尝试；按总预算决定下一次尝试 | 宣称供应商没有执行、清零调用预算 |

复核唤醒和恢复均需持久意图；signal 只作为加速通知。长期等待每1000轮对账或24小时形成一次 Continue-As-New 边界，仅传业务身份与当前代次，继续读取数据库；升级须验证历史重放与边界兼容。上述是设计上限，尚未执行长时间运行验证。
