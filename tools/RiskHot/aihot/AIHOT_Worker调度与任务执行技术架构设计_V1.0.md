## 1. 建设背景与设计目标

### 1.1 建设背景

AIHOT
包含信源采集、正文抽取、内容分析、事件归组、事件综述、热度计算、精选通知、公开数据更新和周期报告等后台处理工作。

这些工作有不同的触发方式和执行特征：

-   **周期触发**：例如每分钟检查一次到期信源。
-   **业务触发**：例如新增文章后，提交内容分析任务。
-   **流程触发**：例如内容分析完成后，继续提交事件归组任务。
-   **恢复触发**：例如定期扫描未处理资料，将遗漏或中断的工作重新入队。
-   **维护触发**：例如定期执行数据清理、运行状态检查和告警。

如果将这些工作直接放在 HTTP
请求中同步执行，容易造成请求等待时间过长、执行超时、业务处理与页面请求相互影响，也难以统一处理重试和故障恢复。

因此，AIHOT 将后台处理放到独立 Worker 进程中，通过 PostgreSQL 上的
pg-boss 队列实现持久化任务管理。

### 1.2 设计目标

  ------------------------------------------------------------------------------------------------
  目标                                具体要求
  ----------------------------------- ------------------------------------------------------------
  统一调度                            统一管理周期性任务及业务触发任务

  异步执行                            将耗时任务从 Web/API 请求链路中分离

  任务持久化                          任务入队后由数据库保存，降低进程退出造成的任务丢失风险

  并发控制                            根据任务类型设置消费者并发，控制数据库、模型和外部服务压力

  失败处理                            按任务类型配置重试次数、重试间隔和任务有效期

  故障恢复                            定期扫描业务状态，修复遗漏入队或中断的处理

  执行追踪                            区分队列任务记录、定时运行记录和业务处理结果

  生命周期管理                        Worker 关闭时停止新工作并对正在执行的任务进行优雅收尾
  ------------------------------------------------------------------------------------------------

### 2.1 架构组成

AIHOT 的 Worker 以独立 Node.js 进程运行，使用 pg-boss

  ----------------------- ----------------------------------------------------------------- ----------------------------------------

  Persistence             PostgreSQL                                                        保存业务数据、pg-boss

### 2.3 核心架构关系

Worker 任务体系需要区分三个概念：

1.  **Scheduler（调度器）**：判断何时应该触发某项工作。
2.  **Queue（任务队列）**：保存待处理任务，并将任务分发给消费者。
3.  **Consumer（任务消费者）**：获取任务并执行实际业务逻辑。

例如，信源 A 配置为每 15 分钟采集一次：

1.  `sources.schedule` 按分钟运行。
2.  调度逻辑检查哪些信源已经到达下一次采集时间。
3.  对到期信源提交相应的采集任务。
4.  pg-boss 将任务持久化到 PostgreSQL。
5.  Worker 消费对应的 `sources.fetch` 任务。
6.  执行信源抓取、材料入库等业务逻辑。
7.  根据采集结果更新信源的后续调度状态。

**`sources.schedule` 是负责检查到期信源的周期性调度任务，`sources.fetch`
是负责执行实际抓取工作的业务任务。**

例如，系统中有 100
个信源，每个信源有自己的采集周期。调度器可以统一检查这些信源的到期状态，到期后再提交对应采集工作。每个信源是否严格对应一条独立队列消息，应以完整
`sources`
任务生产代码中的入队载荷和循环逻辑为准；当前架构材料足以确认"统一周期调度、到期后触发采集任务"这一关系。\[C/I\]

### 2.4 架构职责边界

AIHOT 的 `jobs/*` 负责调度与任务生命周期，`editorial/`、`events/`
等业务模块负责具体业务判断规则。\[C\]

-   `jobs/`：定义任务类型、队列消费者、重试、调度和补偿入口。
-   `sources/`：信源计划及抓取适配器。
-   `content/`：材料统一入口、身份、修订和正文处理。
-   `editorial/`：内容预筛、评分、结构化、写作和模型分析。
-   `events/`：事实归组、事件关联、热度和事件综述。
-   `publication/`：公开数据投影和发布控制。
-   `providers/`：模型、Embedding、外部服务、回执和预算。

这种边界让 Worker
负责"什么时候执行、如何执行、失败后怎么办"，业务模块负责"具体要处理什么、按什么规则处理"。

## 3. Worker 进程与启动管理

### 3.1 进程定位

Worker 运行入口为 `apps/worker/src/main.ts`。\[C\]

Worker 与 Web、API 进程分开运行。Web 负责页面，API 负责 HTTP
接口，Worker 负责后台任务、定时调度、恢复及心跳等工作。

Worker 可访问 backend 业务模块、PostgreSQL
和外部服务。模型调用由后台任务发起，避免将耗时推理过程放入普通页面请求链路。\[C/D\]

### 3.2 启动职责

Worker 启动过程从架构职责上可划分为以下阶段；具体调用顺序应以完整
`main.ts` 为准。\[I\]

1.  读取运行环境和配置。
2.  初始化数据库连接及 pg-boss。
3.  注册任务消费者。
4.  注册周期性调度任务。
5.  启动队列消费。
6.  启动心跳、恢复和运行状态检查。
7.  进入持续运行状态。

### 3.3 生命周期

``` mermaid
stateDiagram-v2
    [*] --> Starting
    Starting --> Initializing: 初始化配置与连接
    Initializing --> Registering: 注册队列与调度
    Registering --> Running: 启动消费者
    Running --> Draining: 收到关闭信号
    Draining --> Stopped: 停止新任务并完成收尾
    Stopped --> [*]
    Initializing --> Failed: 初始化失败
    Registering --> Failed: 注册失败
    Failed --> [*]
```

### 3.4 优雅关闭

已核验的实现通过 `AbortSignal` 避免关闭阶段继续发起新的外部调用，并执行
Worker graceful drain（优雅排空）。\[C\]

优雅关闭的目标是：

-   不再接收或启动新的业务工作。
-   向正在执行的处理逻辑传递取消信号。
-   尽可能完成正在进行的数据库操作。
-   对未完成任务保留可恢复状态。
-   释放数据库连接和队列资源。

任务能否在关闭窗口内完成，取决于任务类型、外部调用是否支持取消以及关闭超时配置。对无法安全完成的任务，应依赖队列可恢复机制和业务幂等控制。

## 4. 任务类型与触发模式

### 4.1 周期性调度任务

周期任务由 Cron 表达式或固定周期触发，例如
`sources.schedule`、`content.sweep`、`hot.rank`。

周期任务通常承担以下工作：

-   检查是否存在到期业务对象。
-   扫描符合条件的记录。
-   创建后续业务任务。
-   执行周期性计算或维护。
-   检查并修复异常状态。

### 4.2 业务触发任务

业务触发任务由 API 或 backend 业务流程提交到队列，例如
`content.analyze`、`events.group`、`sources.fetch`。

这类任务通常有明确的业务对象或处理范围，例如文章、信源、事件或公开投影。

### 4.3 流程衔接任务

某项任务完成后，可以根据处理结果提交下一阶段任务。例如内容分析完成后，符合条件的文章可以进入事件归组流程。

``` mermaid
flowchart LR
    A["文章入库"] --> B["content.analyze"]
    B --> C["内容分析结果"]
    C --> D{"是否满足后续处理条件"}
    D -->|是| E["events.group"]
    D -->|否| F["结束或等待"]
    E --> G["事件归组结果"]
    G --> H["后续事件处理"]
```

> 该图用于说明任务链的逻辑模式。每一条具体任务链是否由消费者直接 enqueue
> 下一任务，仍需按对应业务代码逐条核验。

### 4.4 恢复与补偿任务

恢复任务按固定周期扫描业务状态，寻找因进程中断、入队异常或前序任务失败而未完成的工作。

例如，`content.sweep` 每 5
分钟执行一次，负责将未处理或待重试资料恢复入队。\[C\]

恢复扫描是业务状态与任务队列之间的补充保障，可以降低单次入队或执行异常造成的长期遗漏。

## 5. 任务队列设计

### 5.1 队列技术

AIHOT 使用 pg-boss 管理持久化任务队列，pg-boss 与业务数据共用 PostgreSQL
实例，并使用独立的 `pgboss` schema 保存队列相关数据。\[C\]

业务代码通过统一任务定义和入队接口提交工作。核心 `JobData`
类型约束队列名称与任务载荷，减少生产者和消费者之间的数据契约偏差。\[C\]

### 5.2 已识别的队列

  队列                             任务职责
  -------------------------------- ------------------------------
  `sources.fetch`                  常规信源抓取
  `sources.fetch-x`                X 抓取分片
  `sources.mp`                     公众号抓取或核对
  `content.analyze`                内容分析
  `content.extract-body`           正文抽取
  `events.group`                   事件归组、信息增量和身份复核
  `events.digest`                  事件综述
  `notify.selected`                精选通知
  `publication.republish-source`   信源变化后的公开投影重算
  `media.prepare`                  图片或媒体准备

以上队列名称和职责来自已核验的 `JobData` 定义及架构研究材料。\[C\]

### 5.3 任务载荷

队列任务通常需要携带消费者执行工作所需的业务标识和必要参数。当前研究确认
AIHOT 使用统一 `JobData`
类型约束任务载荷，但当前材料不足以列出每个任务的完整字段定义。

以下仅为说明任务载荷设计方式的示意，不代表 AIHOT 源码中的实际字段：

``` ts
// 示意结构：用于说明任务载荷应表达的内容
type ExampleSourceFetchJob = {
  sourceId: string;
  triggeredAt: string;
  triggerReason: "schedule" | "manual" | "recovery";
};
```

建议任务载荷保持精简，优先传递业务对象
ID、版本号或必要的执行参数。消费者根据 ID
从业务数据库读取最新且有效的业务数据，避免把大量业务对象快照直接塞入队列。\[P\]

### 5.4 入队方式与事务一致性

已核验的队列封装支持通过 `enqueue(..., tx)`
将任务入队操作与业务数据写入放在同一个数据库事务中。\[C\]

例如，业务事务需要完成：

1.  更新文章处理状态。
2.  创建或更新必要的业务记录。
3.  将后续分析任务写入 pg-boss 队列。
4.  提交事务。

这样可以降低"业务状态已更新，但任务没有成功入队"的不一致窗口。

事务内入队只解决数据库事务边界内的一致性问题。消费者调用外部模型或第三方接口时，仍需单独处理超时、重复调用和结果未知等问题。

## 6. 周期任务调度设计

### 6.1 调度注册机制

AIHOT 使用 `registerSchedules()` 注册周期任务，将定时任务建立为 `cron.*`
pg-boss singleton 队列，并将运行结果写入 `job_runs`。\[C\]

已核验的调度行为包括：

-   定时任务由统一注册入口管理。
-   使用 singleton 机制控制同一调度项的重复注册或并发触发。
-   支持 `missed: once`，用于处理错过的调度周期。
-   未指定补执行策略时采用 `skip`。
-   停用定时器时会清理对应队列，历史运行记录仍保留。

### 6.2 已识别的周期任务

以下周期以架构研究快照中的 Asia/Shanghai 配置为准。\[C\]

  --------------------------------------------------------------------------------------
  调度任务                 执行周期                 主要职责
  ------------------------ ------------------------ ------------------------------------
  `sources.schedule`       每分钟，采集功能开启后   检查到期信源并触发采集

  `content.sweep`          每 5 分钟                未处理及待重试资料恢复入队

  `content.translate`      每 5 分钟                检查符合条件的全文翻译任务

  `hot.rank`               每 5 分钟                重新计算热度排名

  `hot.snapshot`           每小时第 2 分钟          生成热度快照

  `stories.links`          每小时第 12 分钟         刷新事件关联

  `reports.compose`        每小时的 00、30 分       检查日报、周报、月报到期情况并补刊

  `ops.recover`            每 10 分钟               停顿任务和未知回执恢复

  `ops.alerts`             每 10 分钟               运行告警检查

  `sources.mp-reconcile`   每 15 分钟，按配置       微信公众号信源核对

  `ops.retention`          每天 03:30               数据清理与隐私保留策略
  --------------------------------------------------------------------------------------

### 6.3 `sources.schedule` 与单个信源的关系

需要区分"调度器的运行频率"和"信源的采集频率"。

例如：

  信源     配置采集频率   调度器行为
  -------- -------------- ------------------------
  信源 A   每 15 分钟     到期时触发一次采集工作
  信源 B   每小时         到期时触发一次采集工作
  信源 C   每天           到期时触发一次采集工作

`sources.schedule`
每分钟运行一次，负责集中检查信源是否到期。每个信源的采集周期由信源配置和调度状态决定。

因此，不能把 `sources.schedule` 理解成"每个信源各自运行一个每分钟
Cron"。它是统一的周期检查入口。到期后具体如何生成 `sources.fetch`
任务、任务载荷如何携带信源 ID，需要结合完整 `jobs/sources.ts` 和
`sources/` 相关代码确认。\[C/I\]

### 6.4 `job_runs` 与 `pgboss.job` 的职责边界

这是理解 AIHOT 任务持久化最重要的地方。

  -------------------------------------------------------------------------------------------------
  记录位置                主要用途                     记录范围
  ----------------------- ---------------------------- --------------------------------------------
  `pgboss.job`            pg-boss 管理的持久化队列任务 进入 pg-boss
                                                       的任务，包括待执行和执行过程中的队列任务

  `job_runs`              定时任务运行记录             已注册调度任务的运行情况

  业务数据表              保存业务处理结果及业务状态   文章、分析、事实、事件、公开投影等领域数据
  -------------------------------------------------------------------------------------------------

**`job_runs` 不应被理解为所有后台任务统一使用的任务流水表。**

例如：

-   `sources.schedule` 这类 Cron 调度运行结果记录在 `job_runs`。
-   `sources.fetch`、`content.analyze` 等业务任务由 pg-boss
    队列持久化管理。
-   内容分析的业务结果仍保存在相应业务数据中。

架构研究材料确认了 `pgboss.job` 和 `job_runs`
的存在及用途，但未提供完整数据库迁移文件。因此，本文不推断 `job_runs`
的全部字段、索引和外键，也不将其描述成所有任务的统一执行明细表。\[C\]

### 7.1 消费者注册

Worker

业务处理逻辑位于 backend
领域模块，任务消费者负责组织执行过程和调用业务能力。\[C\]

## 8. 并发控制与资源管理

### 8.1 队列级并发

不同任务的执行成本、资源占用和业务冲突程度不同，因此应按队列设置并发策略。

  `sources.mp`                     3 次重试配置，延迟 60 秒                             待核验

  `notify.selected`                无自动重试，任务有效期 300 秒                        待核验

  `publication.republish-source`   2 次重试配置，任务有效期 3600                             1

> 参数的精确含义、任务过期语义以及不同版本的配置映射，仍应以
> `jobs/queue.ts` 和锁定的 pg-boss
> 版本为准。表中"待核验"表示当前材料未确认具体并发值。

### 8.2 为什么不同队列需要不同并发

-   **模型分析任务**：单次处理可能涉及多个模型调用，适合设置有限并发，避免模型预算和外部速率限制被瞬间耗尽。
-   **事件归组任务**：同一事件可能涉及多条事实和报道，较高并发容易增加写入冲突，因此已识别到
    `events.group` 使用并发 1。
-   **正文抽取任务**：主要受网页访问、网络等待和解析资源影响，需要结合抓取服务承载能力控制并发。
-   **公开投影重算任务**：对同一业务对象的公开状态更新需要控制写入顺序，已识别到相关队列并发
    1。

### 8.3 并发控制的边界

队列并发值只约束对应消费者的任务执行数量，不能直接代表整个系统对外部 API
的总并发上限。

实际外部调用并发还受到 Worker
进程数量、同一队列消费者并发、不同队列是否调用相同外部服务、单个任务内部是否并行发起多个请求，以及模型供应商和信源服务速率限制的共同影响。

因此，模型服务和外部信源还需要独立的速率限制、预算和超时控制。

## 9. 失败处理与重试机制

### 9.1 失败类型

  -------------------------------------------------------------------------------------
  失败类型                典型情况                         处理方向
  ----------------------- -------------------------------- ----------------------------
  临时网络错误            连接超时、短暂不可用             可按策略延迟重试

  外部服务限流            模型或信源接口返回限流           等待限流窗口后重试

  业务状态冲突            数据版本已变化、记录已被处理     重新读取状态并判断是否继续

  模型输出异常            输出无法通过结构化校验           按输出错误策略限制重试

  预算或回执冲突          预算不足、付费回执仍在处理中     等待、恢复或转人工处理

  不可恢复错误            参数错误、权限错误、资源不存在   记录失败原因并停止自动重试
  -------------------------------------------------------------------------------------

### 9.2 AIHOT 已识别的异常处理

当前研究材料确认内容分析对多类错误分别处理：\[C\]

-   `ReceiptBusyError`、`BudgetExceededError`：进入等待与重试路径。
-   `ReceiptUnknownError`：中止当前分析，等待恢复机制释放或确认回执状态。
-   `ModelOutputError`：连续输出失败有独立上限。
-   Worker 关闭：通过 `AbortSignal` 避免继续发起新的外部调用，并执行
    graceful drain。

### 9.3 重试策略

重试配置应至少考虑最大重试次数、首次重试延迟、后续重试间隔或退避规则、任务有效期、错误类型是否允许重试，以及重试耗尽后的处理方式。

重试策略需要与业务幂等结合。对已经成功写入业务结果的任务，如果因确认环节异常再次执行，消费者必须能够识别已有结果，避免重复创建事实、重复发布或重复扣费。

## 10. 幂等与数据一致性

### 10.1 任务重复执行的原因

在分布式任务处理中，同一业务任务可能由于网络超时、进程退出、消费者重启、确认状态不明确或恢复扫描而再次进入执行流程。

因此，任务系统需要允许任务被重新投递，同时保证业务结果不会因为重复执行而产生错误。

### 10.2 入队一致性

AIHOT 已支持通过 `enqueue(..., tx)`
将任务入队与业务写入放在同一个数据库事务中。\[C\]

例如，业务事务需要完成：

1.  更新文章处理状态。
2.  创建或更新必要的业务记录。
3.  将后续分析任务写入 pg-boss 队列。
4.  提交事务。

这样可以降低"业务状态已更新，但任务没有成功入队"的不一致窗口。

事务内入队只解决数据库事务边界内的一致性问题。消费者调用外部模型或第三方接口时，仍需单独处理超时、重复调用和结果未知等问题。

### 10.3 业务幂等

对于需要避免重复处理的任务，建议使用业务对象标识、版本号和任务类型构建幂等判断条件。\[P\]

  任务类型       可考虑的幂等维度
  -------------- ---------------------------------------
  内容分析       `articleId + revision + analysisType`
  正文抽取       `articleId + sourceRevision`
  事件归组       `factId + groupingVersion`
  事件综述       `storyId + inputHash`
  公开投影重算   `sourceId + publicationVersion`

以上是设计示例，不能视为 AIHOT 已经采用的完整幂等键定义。

### 10.4 版本校验与并发写入保护

AIHOT
的业务处理还使用材料修订号、行锁、乐观校验等机制，避免过期任务覆盖较新的业务结果。\[C\]

-   内容分析会保留过期修订结果供追踪，并通过文章修订检查避免旧结果覆盖当前状态。
-   事件综述会根据输入报道集合和正文哈希判断是否需要重算，并在结果写入前重新核验输入版本。
-   事件归组使用串行消费者降低冲突，同时仍通过行锁和修订检查保护写入。

**队列并发控制解决"同时有多少任务在执行"，业务锁和版本校验解决"多个任务能否安全修改同一业务对象"。两者需要配合使用。**

## 11. 故障恢复机制

### 11.1 恢复目标

故障恢复需要解决两类问题：

1.  队列层面的任务执行中断，例如 Worker 退出或任务执行超时。
2.  业务层面的处理遗漏，例如业务记录处于待处理状态，但没有对应的有效队列任务。

pg-boss
负责持久化队列及任务执行管理；业务恢复扫描负责从业务数据状态中识别需要重新提交的工作。

### 11.2 已识别的恢复机制

  机制                 主要作用                                 证据
  -------------------- ---------------------------------------- -------
  `content.sweep`      扫描未处理及待重试资料并恢复入队         \[C\]
  `ops.recover`        定期处理停顿状态及未知回执恢复           \[C\]
  pg-boss 持久化队列   保存队列任务，支持进程恢复后的继续处理   \[C\]
  管理后台重跑         对部分失败任务进行人工重新执行           \[C\]
  定时任务补执行策略   支持错过调度周期后的补执行控制           \[C\]

### 11.3 恢复流程

``` mermaid
flowchart TD
    A["定时恢复任务触发"] --> B["扫描业务状态"]
    B --> C{"是否发现待恢复对象"}
    C -->|否| D["本轮结束"]
    C -->|是| E["校验对象版本和当前状态"]
    E --> F{"是否仍满足执行条件"}
    F -->|否| G["跳过或更新状态"]
    F -->|是| H["检查是否已有有效任务"]
    H --> I{"是否需要重新入队"}
    I -->|否| D
    I -->|是| J["重新提交任务"]
    J --> K["Worker 后续消费"]
```

### 11.4 恢复过程的保护条件

恢复任务在重新入队前应检查：

-   业务对象是否仍然存在。
-   当前业务状态是否仍需要处理。
-   对象版本是否发生变化。
-   是否已经存在有效的执行任务。
-   上一次执行是否已经成功但状态尚未同步。
-   是否超过自动重试或人工处理边界。

这些检查可以减少重复任务和无效任务。具体检查项应以对应恢复处理器实现为准；本文将其作为恢复设计审查要点。\[P\]

## 12. 运行监控与执行追踪

### 12.1 监控对象

任务监控应同时覆盖队列层、Worker 进程层和业务处理层。

  监控层        建议关注内容
  ------------- ----------------------------------------------
  Worker 进程   进程存活、启动失败、关闭过程、心跳
  队列          待处理数量、执行中数量、失败数量、积压时间
  消费者        当前并发、任务耗时、异常类型、重试次数
  调度器        调度是否按时触发、漏执行、补执行情况
  业务处理      待处理对象数量、处理成功率、业务状态停留时间
  外部依赖      模型接口错误率、限流、超时、预算和回执状态

### 12.2 任务追踪关系

建议通过统一的任务标识和业务对象标识建立关联：

``` text
调度运行记录
    └── 触发的业务队列任务
            └── Worker 消费执行
                    └── 业务对象
                            └── 业务处理结果
```

该关系用于说明可观测性设计。当前研究已确认 `job_runs`、`pgboss.job`
和多类业务表存在，但尚未核验它们之间是否存在完整的数据库外键或统一 trace
ID。

### 12.3 关键指标

建议至少采集：

-   队列任务提交数量。
-   队列任务成功率和失败率。
-   各队列平均等待时间。
-   各队列平均执行时长及 P95/P99。
-   重试次数和重试耗尽数量。
-   超过预期时间仍未完成的业务对象数量。
-   Worker 重启次数和异常退出次数。
-   恢复扫描重新入队数量。
-   外部模型调用错误率和预算消耗。

## 13. 配置与运行安全

### 13.1 配置管理

调度周期、并发、重试次数、任务有效期和外部服务超时应集中管理，并区分开发、测试和生产环境。

修改调度配置时，应考虑已有 Cron 队列和历史运行记录的处理方式。AIHOT
的调度注册实现会清理已停用计时器对应队列，同时保留历史运行记录。\[C\]

### 13.2 运行安全

建议重点检查：

-   数据库连接串、模型密钥和信源凭据不得写入任务载荷或普通日志。
-   任务载荷只包含完成工作所需的最小数据。
-   管理后台手动重跑应有权限控制和操作审计。
-   对外部请求设置超时、重试上限和速率限制。
-   对可能产生费用的模型调用，执行预算与回执校验。
-   对长期失败的任务设置告警和人工处理入口。

### 16.2 一致性与幂等测试

-   在业务事务提交前模拟失败，确认业务写入和入队操作一起回滚。
-   对同一业务对象重复提交任务，确认不会产生重复业务结果。
-   在任务执行中途终止
    Worker，重启后确认任务可以继续处理或进入恢复流程。
-   模拟外部服务已完成处理、客户端未收到响应的场景，确认不会产生重复扣费或重复发布。
-   模拟旧版本任务晚于新版本任务完成，确认旧结果不会覆盖新结果。

### 16.3 性能与容量测试

-   分别测量不同队列的等待时间和执行时长。
-   在多个队列同时积压时观察资源占用。
-   验证单队列并发限制是否生效。
-   验证模型接口和信源接口的速率限制。
-   测试大量任务入队时 PostgreSQL 连接池和队列查询负载。
-   测试 Worker 重启后积压任务的恢复速度。

### 16.4 验收标准

1.  周期任务能够按配置注册和触发。
2.  业务任务能够可靠入队并被对应消费者执行。
3.  任务状态、定时运行记录和业务结果能够分别查询。
4.  失败任务按配置重试，重试耗尽后有明确处理结果。
5.  Worker 异常退出或重启后，未完成工作能够恢复。
6.  重复执行不会造成业务数据重复或旧版本覆盖新版本。
7.  不同队列的并发限制符合配置。
8.  Worker 关闭过程不会无控制地启动新任务。
9.  关键任务积压、失败和长时间未完成情况能够被监控发现。

### 17.1 RiskHot 的任务分类建议

RiskHot 可以先按以下类别整理后台任务：

1.  **采集类任务**：信源拉取、网页抓取、文件解析。
2.  **信息处理类任务**：正文清洗、信息标准化、事件候选抽取。
3.  **风险识别类任务**：变量抽取、风险识别、风险评分。
4.  **事件管理类任务**：事件归并、状态更新、影响分析。
5.  **知识处理类任务**：知识抽取、实体关联、向量生成。
6.  **系统维护类任务**：失败恢复、数据清理、索引更新、运行检查。

每类任务需要定义任务名称、触发方式、输入对象、输出结果、超时、重试、并发、幂等和恢复规则，再决定是否共用队列或独立队列。

## 18. 术语说明

  术语             含义
  ---------------- ----------------------------------------------------
  Worker           后台工作进程，负责消费任务并执行处理逻辑
  Scheduler        调度器，负责按时间或规则触发任务
  Cron             按时间表达式周期触发任务的机制
  Queue            任务队列，保存待执行工作并提供分发能力
  Job              一次具体的后台任务实例
  Producer         任务生产者，负责创建并提交任务
  Consumer         任务消费者，负责从队列获取并执行任务
  JobData          任务载荷的数据类型定义
  Concurrency      并发数，表示同一消费者可同时处理的任务数量
  Retry            失败后重新执行任务
  Backoff          退避策略，控制重试之间的等待时间
  Singleton        单例调度或任务控制机制，用于避免重复注册或重复触发
  Idempotency      幂等性，同一业务操作重复执行仍能保持预期结果
  Graceful Drain   优雅排空，关闭时停止新工作并处理正在执行的工作
  Recovery Scan    恢复扫描，定期检查业务状态并修复遗漏或中断的任务
