## 2. 架构结论摘要

AIHOT 的提示词能力由以下组件协同完成：

- **提示词资产**：`industry/prompts/` 下的 Markdown 文件。
- **提示词装配**：`packages/backend/src/editorial/prompts.ts`，负责变量替换、递归包含和提示词版本哈希。
- **模型选择**：`modelFor()`，根据配置优先级确定调用模型。
- **统一模型调用**：`chatJson()`，通过 OpenAI 兼容的 `/chat/completions`
  接口请求模型。
- **结构化输出校验**：解析 JSON，并使用 Zod Schema 验证结果。
- **执行追踪**：请求身份包含模型、提示词版本、输入哈希、采样参数等信息，并通过回执机制记录执行结果。

**核心原则：业务代码决定何时调用哪项能力；提示词定义该能力的判断方式与输出要求；程序负责结构校验、业务约束和正式状态变更。**

模型不会自行扫描
`industry/prompts/`。后端代码先读取并组装提示词，再将组装后的内容与任务输入发送给模型。

## 4. 提示词资产目录

### 4.1 现有目录与文件映射

现有业务架构资料将提示词资产映射到
`industry/prompts/`。按资料中出现的文件名，目录可概括为：

``` text
industry/
└── prompts/
    ├── prefilter.md
    ├── selection-score.md
    ├── structure.md
    ├── content-understanding.md
    ├── summarize-*.md
    ├── mend-wording.md
    ├── group-*.md
    ├── story-digest.md
    ├── report-period.md
    └── report-period-sections.md
```

这是依据现有架构资料整理的资产映射，不应将通配符 `*`
理解为固定文件名。措辞修正与翻译相关资产、部分归组复核配置仍有待完整源码进一步核验。

### 4.2 目录组织原则

1.  **按业务能力组织**：文件名体现预筛、评分、结构化、归组、综述或报告等任务职责。
2.  **共享内容通过包含机制复用**：公共规则可以被多个提示词引用，减少复制后产生的版本漂移。
3.  **任务与提示词保持多对多关系**：一个任务可以多次调用同一提示词；一次模型调用也可能返回多个逻辑判断。
4.  **能力编号与文件名分离**：AI-01～AI-13 是业务分析编号，不代表存在 13
    个独立提示词文件、13 种 Capability 或 13 次模型请求。

## 5. 提示词装配机制

### 5.1 支持的模板语法

现有技术架构资料确认 `prompts.ts` 支持两种语法：

| 语法                | 用途                     | 示例                   |
|---------------------|--------------------------|------------------------|
| `{{变量名}}`        | 在模板中注入运行时变量   | `{{industry_context}}` |
| `{{> prompt-name}}` | 递归包含另一个提示词片段 | `{{> shared-rules}}`   |

示例用于说明语法，不代表 AIHOT 当前文件中一定存在这些变量名或片段名。

### 5.2 装配器行为

已记录的实现机制包括：

- 替换模板中的变量。
- 递归展开包含的提示词片段。
- 缺少必需变量时抛出错误。
- 引用的提示词文件缺失时抛出错误。
- 检测并拒绝循环包含。
- 将依赖文件内容纳入 SHA-256 提示词版本哈希。

共享片段发生变化时，依赖它的最终提示词也可以通过版本哈希识别变化。

### 5.3 运行时读取规则

执行 AI
任务时，由后端代码调用装配器读取对应提示词，并完成变量替换和依赖展开。模型收到的是**最终组装后的请求内容**，不会在推理过程中自行访问项目文件系统。

提示词文件修改后何时生效，取决于实际读取方式、进程运行状态、缓存策略和部署方式。现有资料能确认哈希追踪机制，但不足以保证所有环境都支持即时热加载。上线前应验证实际读取与刷新行为。

## 6. 模型路由与统一调用

### 6.1 模型选择优先级

现有架构资料记录 `modelFor()` 的模型配置优先级如下：

1.  后台 `settings.models.*` 配置。
2.  环境变量。
3.  `site/models.ts` 默认配置。
4.  内建默认值。

后台覆盖值的缓存时间为 60
秒；新调用读取新的模型选择后，旧结果不会自动回溯重算。

**模型配置缓存与提示词文件加载属于不同机制。** 不能仅凭模型配置的 60
秒缓存推断提示词文件也按相同周期刷新。

### 6.2 Capability 与业务任务

AIHOT 使用 Capability 作为模型能力配置键，现有资料列出的 11 类键为：

`prefilter`、`score`、`understand`、`summarize`、`wording`、`structure`、`group`、`groupReview`、`digest`、`report`、`translate`。

Capability
负责配置能力调用所需的模型等参数；业务任务编号负责描述业务处理步骤。二者属于不同维度。

### 6.3 `chatJson()` 的职责

现有架构资料确认，`chatJson()` 统一执行以下工作：

1.  检查模型是否已注册、当前能力是否允许调用，以及调用凭据是否可用。
2.  请求 OpenAI 兼容的 `/chat/completions` 接口。
3.  解析模型返回的 JSON。
4.  使用 Zod Schema 校验结构。
5.  对不可用输出记录失败回执，并保留错误恢复路径。

模型生成合法 JSON
只代表结构层面可解析；它仍需通过业务规则检查，才能进入后续业务流程。

## 8. 推荐的提示词编写规范

本节是面向新建或重构提示词的**工程化建议 \[P\]**，不代表现有 AIHOT
的每一份提示词都已经采用统一章节结构。

建议采用四层结构：

### 第一层：核心认知原则

说明模型执行任务时必须遵守的基础原则，例如证据优先、区分事实与推断、允许返回不确定状态，以及禁止编造实体
ID、时间、数值或来源。

### 第二层：领域判断规则

写清任务所依赖的业务定义、分类标准、边界条件和排除条件。需要频繁变更的业务阈值，优先考虑由代码配置或规则模块管理，避免散落在多个提示词中。

### 第三层：执行步骤

将任务拆成可执行步骤，明确输入阅读顺序、判断顺序、证据比对方式、冲突处理方式和不确定情况的处理规则。

### 第四层：输出契约

明确输出
Schema、字段类型、枚举范围、必填字段、空值规则、证据引用要求和禁止输出的额外内容。提示词中的文字要求不能替代程序校验。

建议每份提示词都能回答四个问题：模型应遵守什么原则、依据哪些业务规则、按什么步骤完成任务、最终必须输出什么结构。

## 9. 版本追踪与执行回执

### 9.1 请求身份

现有架构资料记录，请求逻辑身份包括模型标识、Prompt
版本、系统输入与用户输入哈希、采样参数及额外模型参数。提示词版本哈希会考虑依赖文件内容。

该设计有助于区分“相同输入、不同提示词版本”产生的执行结果，并支持响应复用与成本追踪。

### 9.2 建议保留的执行元数据 \[P\]

| 元数据                       | 目的                       |
|------------------------------|----------------------------|
| 业务任务编号 / Capability    | 识别执行的是哪类任务       |
| Prompt 标识与 SHA-256        | 确定实际使用的提示词版本   |
| 模型标识及参数               | 追踪模型选择与生成配置     |
| 输入快照或输入哈希           | 确定模型当时收到的任务数据 |
| 输出原文与解析结果           | 支持问题排查和评测         |
| Schema 校验结果              | 区分结构失败与业务判断失败 |
| 执行状态、错误类别、重试记录 | 支持恢复与运行监控         |
| 运行时间、Token 用量和成本   | 评估运行效率及成本         |

## 10. 测试与评测

建议将测试分成四个层次，避免仅凭少量人工试跑判断提示词质量。

### 10.1 装配器单元测试

- 普通变量正确替换。
- 多层 `{{> ...}}` 包含正确展开。
- 缺失变量与缺失文件能够明确报错。
- 循环包含被拒绝。
- 修改任一依赖片段后，最终提示词哈希发生变化。
- 同一组文件与变量在相同版本下产生稳定的装配结果。

### 10.2 输出契约测试

- 模型返回有效 JSON 时，解析和 Schema 校验通过。
- 缺字段、错误类型、非法枚举及额外格式文本能够按既定规则处理。
- Schema 变更时同步更新测试样例和对应提示词。
- 结构失败不会直接进入正式业务写入。

### 10.3 任务评测集

每个任务至少准备正常样例、边界样例、冲突样例和信息不足样例。可按任务选择指标，例如：

| 任务类型     | 建议关注的指标                             |
|--------------|--------------------------------------------|
| 相关性预筛   | Precision、Recall、UNKNOWN 比例            |
| 双评分       | 分数稳定性、与人工基准的偏差               |
| 事实结构化   | 字段准确率、证据可定位率、时间识别准确率   |
| 事件关系判断 | 关系分类准确率、错误合并率、漏合并率       |
| 综述与报告   | 事实支持率、关键事实覆盖率、无依据内容比例 |

评测集应固定版本，提示词修改前后在同一批样例上进行对比；关键任务应设定发布门槛。

### 10.4 线上观测

持续监控模型调用失败率、JSON / Schema
失败率、业务校验拒绝率、重试率、人工复核率、延迟和成本。异常指标应能追溯到任务、Prompt
哈希、模型版本及输入快照。

## 11. 安全与业务边界

1.  **外部资料视为不可信数据**：新闻正文、网页内容和引用文本中的指令不得覆盖系统任务规则。
2.  **提示词不保存密钥**：API
    Key、访问令牌及其他敏感配置由安全配置机制管理。
3.  **模型输出不直接获得写权限**：正式写入应由业务服务和领域规则控制。
4.  **限制输入与输出规模**：对长正文、递归包含深度和输出大小设置合理边界。
5.  **保留证据来源**：对影响业务结论的事实，尽量保留原文定位或可追溯引用。
6.  **不确定结果走明确分支**：信息不足或判断冲突时，应返回约定状态、进入复核或安全降级，避免强行生成确定结论。

## 12. 后续工程化建议

以下内容属于建议新增项，不代表现有 AIHOT 仓库已经具备。

### 12.1 保留现有提示词路径

优先沿用
`industry/prompts/`，避免在没有迁移收益的情况下重构全部文件路径。可增补说明文档和评测资产：

``` text
industry/
├── prompts/
│   ├── prefilter.md
│   ├── selection-score.md
│   ├── structure.md
│   ├── content-understanding.md

└── prompt-evals/
```

新增文件应根据真实任务和测试需要逐步建立，不要求一次性补齐所有目录。

### 12.2 建议的提示词变更流程

``` mermaid
flowchart LR
    A["提出变更"] --> B["明确任务与输出契约"]
    B --> C["修改 Prompt / 共享片段"]
    C --> D["装配器单元测试"]
    D --> E["任务评测集回归"]
    E --> F{"达到发布门槛？"}
    F -->|否| C
    F -->|是| G["代码审查与版本发布"]
    G --> H["观察线上指标"]
    H --> I["保留回滚版本"]
```

每次变更应说明修改原因、影响的任务、预期收益、评测结果和回滚方法。共享片段变更时，需要同时评估所有引用该片段的提示词。

## 13. 对 RiskHot 的迁移注意事项

AIHOT
可以作为提示词加载、版本哈希、模型路由、结构化输出校验和任务评测的工程参考。RiskHot
应维护自己的业务任务编号、领域规则、Schema 与提示词资产，避免直接照搬
