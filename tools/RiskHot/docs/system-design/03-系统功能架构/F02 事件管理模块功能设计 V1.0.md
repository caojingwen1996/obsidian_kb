# F02 事件管理模块功能设计

本文件定义 F02 的业务功能、处理流程、业务规则、页面操作及验收要求，包含三组二级功能、14 项末级功能和七步处理流程。

业务对象与关系见[[tools/RiskHot/docs/system-design/02-业务架构与领域设计/RiskHot_L0_信息处理层_业务架构与领域设计V1.0|L0 领域设计]]；存储实现见[[tools/RiskHot/docs/system-design/04-系统架构设计/01-数据模型与存储设计/F02事件管理模块数据模型与存储设计|F02 数据模型与存储设计]]。

## 1. 模块定位与职责边界

F02 将 F01 已保存的 Information 提取为候选 Fact，匹配已有唯一 Event，确认新增、进展、补充、纠正、来源增加或重复，形成当前有效事件、直接主体/变量关系与金融意义评价。

- F01 负责原件获取、解析、标准化、资料身份与资料版本。
- F02 负责候选、事件身份、Fact 归属、当前事实、证据引用、评价及业务交付。
- M2 维护正式变量等定义；定义缺口可保留，不自动发布。
- M3 管理方法、提示词和模型版本；S01 管理调度、尝试、预算与运行恢复。
- Fact 不是正式 Event；模型成功输出不代表业务核定成功。
- 不把 M 当作风险等级，不替代 F03/F05 的风险识别与演化判断。

## 2. 功能架构与详细清单

### 2.1 二级功能结构

事件处理：抽取 Fact、匹配 Event、确认归属及隔离歧义。
更新管理：对比 Fact 与当前事件，维护当前事实和证据关系。
事件分析：关联观测主体/变量、评价金融意义、查询与交付。

### 2.3 编号与功能范围

SF02 中“更新”表示依据候选事实维护当前事件内容及其关联。自动合并/拆分属于 P1；任何改变正式事件身份或候选归属的维护操作，均须说明影响范围并取得相应授权。

## 3. 业务对象与信息组织

### 3.1 核心关系与所有权

一份 Information 可支持多个 Fact，一个 Fact 也可由多份 Information 支持。一个 Event 可汇集多个 Fact；尚未归组的 Fact 保留为候选，确认归属后最多属于一个 Event。事件的每项事实均应能追溯到支持或质疑它的资料。

### 3.2 Event：稳定事件身份

系统根据行为主体、具体行动、发生时间及适用范围核对事件身份，确认后创建或复用唯一事件，并关联候选事实及来源证据。事件展示当前有效的标题、事实描述和业务阶段。发生时间未知时不推测补齐。

### 3.3 Target：事件的观测主体

主体按类型、辖区、范围匹配，可跨事件复用。事件的行为主体不等于观测主体 Target；正式定义与使用关系分开。

### 3.4 候选事实的来源与原文证据

同一 Fact 可由多份 Information 支持，同一 Information 可支撑多个 Fact。证据固定 F01 版本及原文位置；矛盾资料也须保留并明确证据作用。用户可从事件详情经候选事实追溯到对应原件。

### 3.5 事件、观测主体与直接变量

必须先确认事件与观测主体的关系，再引用有效的正式变量定义，并由本事件的候选事实支持。保存直接关联类型、方向、阶段、说明与定义依据；不把推测传导当作直接事实。

### 3.6 Fact：候选事件

Fact 承载从资料提取的完整候选陈述。Step 1 校验后即可保存，之后再确认 Event 归属。相同实际陈述可经核对复用 Fact；不同阶段、数字、范围或冲突分别保存有依据的 Fact。处理状态与候选所述事件阶段分开。

### 3.7 EventRating：金融意义评价

按固定范围、研究期限和方法分析，保存维度、用途、解释、限制与采用的 Fact。量化规则未批准时 M 为空，评价为草案。每项评价应明确对应事件与事实依据；不同范围和期限可保留独立评价。

### 3.8 候选归属与事实作用

候选归属明确 Fact 对应的唯一 Event，并说明它在事件中的作用：初始事实、进展、补充、纠正或佐证。正式 Event 至少有一个 Fact；主体、变量及评价均须有可核对的事实依据。

### 3.9 上游只读引用契约

F01 已保存的 Information、确定资料版本、必要原件/附件和段落定位必须可读。标题、URL 或发布时间可以依来源情况缺失，不编造补齐。定义版本和运行方法版本继续保留。

### 3.10 证据与处理记录

候选事实与证据、处理过程与操作记录应清楚区分。用户可追溯处理步骤、建议、复核决定、保存结果及交付结果；重复执行同一步骤不应产生新的候选事实。

### 3.11 结果一致性与追溯

保存完成意味着当前事实、适用关系、评价及其依据均完整且相互一致，不能将部分完成展示为全部成功。重复处理复用已完成结果。用户查阅历史时，应能看到当时的候选事实、来源原文及处理决定，并区分它们与当前事件结论。

## 4. 功能详细设计

### 4.1 总体流程

| 步骤 | 输入 | 程序职责 | AI 职责 | 输出 |
| --- | --- | --- | --- | --- |
| 1 提取候选 | Information、确定资料版本及原文定位 | 读取固定资料、校验并保存 Fact 与来源证据 | AI-01 提取独立候选 | Fact；或无事件原因 |
| 2 匹配归组 | Fact、召回的 Event 及其关联 Fact、原文证据 | 召回真实 Event、校验建议并组织复核 | AI-02 比较身份 | 事件匹配与归组建议（NEW / REUSE / UNRESOLVED）、比较依据及歧义 |
| 3 关联主体与变量 | Fact、事件匹配与归组结果、Event（已有时）、Target、Variable 及有效定义、原文证据 | 准备有效定义、检查直接依据 | AI-03 提出关系或定义候选 | EventTarget、EventTargetVariable；定义候选及缺口 |
| 4 比较当前事实 | Fact、Event（已有时）及其关联 Fact、主体与变量关系建议、原文证据 | 读取 Event 及已关联 Fact，核定重复与变化 | AI-04 比较新增、补充、纠正等 | Event；增量分类、Fact 复用或归属调整建议及比较依据 |
| 5 评价金融意义 | Event 当前事实建议、采用的 Fact、Target 与 Variable 定义及直接关系、固定评价范围与研究期限、方法规则、原文证据、可比 EventRating（已有时） | 判断是否评价，固定范围与方法并校验 | AI-05 分析维度、用途与限制 | EventRating；或合法沿用原因 |
| 6 确认并保存 | Fact、步骤 2～5 的有效建议、原文证据、资料与定义版本、当前 Event 上下文、权限及复核决定 | 复查身份、证据、权限及处理期间的事实变化 | 不调用 AI | Event、Fact、EventTarget、EventTargetVariable、EventRating；候选归属及保存结果 |
| 7 交付 | 当次已确认的 Event、Fact、EventTarget、EventTargetVariable、EventRating、来源证据及变化原因 | 读取已确认保存的当次交付内容，投递并核对回执 | 不调用 AI | 接收回执、应用结果或待恢复状态 |

输出列直接使用领域对象名称；步骤 2～5 的对象内容及关系仍为待确认建议，统一在步骤 6 校验保存，步骤 1 的 Fact 则已独立保存。关系与评价按适用条件输出，允许缺口、跳过或沿用；不因表格列出对象就要求强制生成。

### 4.2 Step 1：提取候选事件

读取完整确定版本；同一资料允许 0～N 个候选，无需拆分原始资料。候选含主体、行动、阶段、发生时间、描述、缺口及原文证据。程序保存候选及其来源证据；AI 不决定正式事件身份。

模型超时、截断或证据无效是失败，不能当作0候选。完整零候选保留正常结果。重复同一已接纳输出复用原 Fact；跨资料同义候选由明确比较结果核定复用，不能仅凭标题自动合并。

### 4.3 Step 2：匹配事件与归组

#### 4.3.1 匹配与归组

比较行为主体、具体行动、发生时间、范围、政策/行动标识和已关联 Fact。相似主题或相同事件阶段不足以证明同一事件。不同日期独立操作分别建档；同一行动生命周期中的进展复用身份。

#### 4.3.2 稳定身份与资料关系

NEW 仅在完整检索及有效确认后创建；REUSE 只能引用真实召回的 Event。匹配决定先作为建议保存，候选的正式归属在 Step 6 确认保存。一个 Fact 不允许同时关联两个 Event。

#### 4.3.3 归组歧义隔离及复核

UNRESOLVED 保存差异和证据，清晰 Fact 可以独立推进。检索失败或覆盖不足不能视作无匹配。复核改归属后，依赖旧身份的关系、增量及评价建议失效。

### 4.4 Step 3：关联观测主体及直接变量

#### 4.4.1 Target 身份与关系

按正式定义的类型、辖区和范围匹配；无法确认时保留缺口，不造正式 ID。行为主体与观测主体分别核对。

#### 4.4.2 直接变量三元关系

只保存有直接证据的三元关系及说明，采用的定义版本和 Fact 必须明确。无定义可形成治理候选；授权继续处理缺口不等于批准发布定义或正式保存。

### 4.5 Step 4：判定增量与更新

#### 4.5.1 增量判定

按以下七类结果决定如何处理候选及当前事件；每项判定均须说明证据和比较依据。

| 分类 | 判定 | 保存动作 |
| --- | --- | --- |
| NEW_EVENT | 独立新事件 | 新 Event 与已保存 Fact 建立归属 |
| EVENT_PROGRESS | 同一行动阶段推进 | 关联进展 Fact，明确更新当前阶段及事实 |
| MATERIAL_ADDITION | 新增关键数字、范围、条件 | 关联补充 Fact，更新适用的当前事实 |
| CORRECTION | 有依据地纠正此前事实 | 关联纠正 Fact，明确纠正原因及纠正后的事实，保留原 Fact 与审计 |
| SOURCE_ADDITION | 新增资料佐证，实质事实未变 | 复用 Fact 并补资料/证据，或关联经确认的佐证 Fact；不建新 Event |
| DUPLICATE | 内容、来源及所需关系均已存在 | 复用结果，无重复业务写入或通知 |
| UNRESOLVED | 身份或差异仍不明确 | 保留 Fact 与待复核结果，不提交当前事件变化 |

#### 4.5.2 进展、实质补充及纠正

逐项说明原事实、本次陈述、变化内容与双方依据。需更新时明确标题、描述、行为主体、具体行动、业务阶段和发生时间中哪些内容改变。程序不得只留一条“纠正”说明而继续展示错误的当前数字。

原来源修订、不同来源冲突、解析错误修复分别说明；新资料版本不自动证明事件被纠正。纠正应能追溯原候选、原文及处理决定，并说明为何采用新的事实结论。

#### 4.5.3 来源增加与纯重复处理

一份资料可支持多个候选，多份独立资料可支持同一候选。Fact 复用需核对实际陈述、数字、条件和阶段；Event 复用需核对行动身份。候选陈述一致与事件身份相同须分别判定，不能仅凭文本相似认定。

#### 4.5.4 生命周期与时间

事件阶段包括预计发生、已宣布、实施中、已生效、已完成、已取消和未知，应按证据判定，不要求依次经过所有阶段。发生时间只表示行动实际发生的时间；预计安排在描述和证据中表达，不能代填发生时间。迟到 Fact 可以增加事实依据，但不得仅因较晚接收而覆盖较新的有效状态。系统记录时间保留在审计及保存记录中。

### 4.6 Step 5：评价金融意义 M

#### 4.6.1 执行顺序与分工

程序判断初评/复评，固定范围、期限、方法、当前 Event 与采用的 Fact；AI-05 提供维度、用途、解释和限制；程序校验并在批准量化规则时独立计算。评级须明确所评价的事件及采用的事实依据。

#### 4.6.2 沿用、空分与异常处理

仅来源增加、纯重复或依据未变通常不复评。方法未批准允许文字草案、空 M；模型失败不是合法空分。不同范围/期限独立保存，不互相覆盖；M 不推断风险等级或市场涨跌。

### 4.7 Step 6：校验并保存事件结果

复查有效建议、授权、资料/定义版本、Fact 归属、证据和事件当前上下文；新 Event 至少关联一个合格 Fact。没有自动通过政策时，身份和正式提交分别需要有效复核。

确认保存时，事件当前事实、候选归属、适用的主体/变量关系、评价及其依据应完整一致，并可追溯批准决定和保存结果。重复提交返回已完成结果；处理期间事实或依据发生变化时，原批准不得直接用于变更后的内容，须重新核对受影响步骤。

### 4.8 Step 7：交付事件变化

分别交付新事件、事件事实变化、评价变化和来源增加。下游应能读取当次已确认的事件内容、候选事实、相关关系、评价及来源证据，并识别变化原因。

保存成功后交付失败，只重新交付当次已确认的内容，不重新创建事件、候选或评价。下游已接收与已采用分别展示；重复交付不重复生效，较早结果晚到不得覆盖较新的有效结果。

### 4.9 处理状态与恢复

| 情况 | 处理 |
| --- | --- |
| 资料版本不可读、附件缺失 | 交 F01 恢复，不编造原文 |
| 模型失败或输出校验不通过 | 恢复当前节点，不默认无事件、NEW 或 DUPLICATE |
| 归属不清或定义缺口 | 保存复核或治理候选；合法部分独立推进 |
| 部分 Fact 已完成 | 重复投递仅恢复未完成分支 |
| 提交响应丢失 | 先核实原保存结果，已完成的结果直接复用 |
| 权限或批准上下文失效 | 拒绝写入，重新准备相关步骤 |
| 已提交后交付失败 | 仅恢复原结果的交付及接收确认 |
| 非事件候选 | 经明确处置保留 Fact/原文及审计，不创建 Event |

### 4.10 事件查询与受控维护

#### 4.10.1 事件检索详情与证据追溯

按标题、行为主体、具体行动、发生时间、阶段、观测主体及评价检索。详情显示当前 Event、关联 Fact、原文、主体/变量关系、评价和处理状态。操作审计单独呈现；历史候选与证据应标明当时的陈述及后续纠正情况，避免误认为当前结论。

#### 4.10.2 合并/拆分及关联调整核对

错归组需明确哪些候选改变归属、哪些当前事实及下游引用受影响，授权后按完整维护方案处理。自动合并/拆分须先明确审批规则；调整后应保留原资料和决定依据，任何正式事件仍须有有效事实支持。

## 5. 页面设计与交互

### 5.1 页面定位与导航

事件管理用于阅读正式事件、理解金融意义、追溯关联候选及原始资料，并查看结果交付状态。页面沿用工作台的深绿导航、浅色阅读区、统一按钮与焦点样式，优先呈现业务内容。

当前已实现的页面如下；本章描述现行页面，后续新增能力须单独验收。

| 页面 | 入口 | 主要内容与操作 |
| --- | --- | --- |
| 正式事件列表 | 从侧栏“内容 → 全部”进入，默认打开；详情中可点击“返回事件列表” | 浏览已保存事件，按页读取，点击事件打开详情 |

### 5.2 正式事件列表

列表标题为“正式事件”，辅助说明为“按展示时间 · 最新在前”。每条白色卡片展示真实信源、标题、完整 description 与阶段；只有标题链接进入详情，来源与时间说明独立展开。日期与星期为分组标题，标记“本页N条”，可收起；时间列、节点及细线形成阅读顺序。窄屏将时间移至卡片顶部，长标题、正文与来源自然换行。

展示时间与业务发生时间 `event_time` 分离：设原文发布时间为 P、该版本首次成功收录为 C。0≤C−P≤72小时（含边界）时采用 C，超过72小时时采用 P；不使用当前时间、Event 建档或更新时间。采用最早成功收录且具有本事件实际证据的版本，C/P 始终同版本配对；修订、重复抓取与普通转载不得重新置顶。同刻按事件ID稳定排序，按上海时间归日，全局排序后再偏移分页。

仅有日/月/年的发布时间保留精度，按可能范围判断；成功收录可将该低精度范围上界收紧到 C。整个可行范围均在72小时内才采用收录时间，全部超过阈值才采用原文时间；跨阈值、非法日历、缺失/无法解析或完整未来时刻采用 C 并说明待核实。完整时刻无明确时区不猜测。无 C 时可采用可解析 P；两项皆无归入“展示时间未明确”。完整日期组在前，月/年各自进入该年月值的“展示日期不完整”组并排在其后，不补造午夜；组内排序用范围起点，页面仍显示原精度。

多来源按信源ID去重，同名不同ID保留；时间依据的信源在前，其余按最早来源关联时间与ID稳定排序。一个 Event 只出现一次。只要事件关联来源中存在无权读取者，整事件及来源数量均不返回，与详情权限保持一致。

| 交互或状态 | 页面表现 |
| --- | --- |
| 默认进入 | 读取正式事件时间线，不进入候选处理队列 |
| 浏览记录 | 每页最多20条；全局倒序后分页；有前后页时显示“上一页”“下一页”；切页定位列表顶部 |
| 打开事件 | 标题链接进入当前正式事件详情，携带经过校验的分页与事件锚点；支持原生新标签页操作 |
| 返回列表 | 显式返回与浏览器后退恢复原页、可见阅读锚点、焦点及展开状态；单独打开详情返回首页 |
| 阅读依据 | 可展开其他信源及时间说明，显示原始发布时间、首次收录与选择原因；原文沿用详情证据入口 |
| 刷新 | 无内容变化不重建；有变化保留可见事件锚点、键盘焦点、日期和来源展开状态 |
| 刷新失败 | 已读取列表保留，说明失败并指向“刷新状态”重试；首次失败与无权读取分别说明 |
| 没有正式事件 | 显示“还没有正式事件。已抽取的候选可从信息接入任务查看。”，不将候选充作正式事件 |

当前列表仅提供浏览、分页和打开详情。第4.10节的多维检索、合并／拆分及关联调整属于完整功能要求，尚未作为本列表的已实现控件交付。偏移分页在静态数据下稳定；并发新增或时间纠正可能改变跨页位置，不提供快照分页保证。本次运行结果见[[tools/RiskHot/docs/verification/event-timeline|事件时间线验证]]。

### 5.3 正式事件详情布局

阅读顺序为返回入口、标题摘要、主体与金融意义、关联候选、结果交付与下载。前两个内容版块承担主要阅读任务，追溯和操作信息置于后方。

| 区域 | 展示内容 | 交互与缺失处理 |
| --- | --- | --- |
| 标题与摘要 | 事件标题、当前事实摘要；发生时间和阶段作为辅助信息 | 默认直接显示；原文未明确发生时间时如实提示，不补造时间 |
| 主体 Subject | 实施行动的主体 | 与Target分开展示；缺失时显示主体待确认 |
| 观测对象 Target | 已保存的正式观测对象名称及关联说明 | 没有有效关联时显示“尚未确认观测对象”，不能用Subject代替Target |
| 直接变量 | 已保存的变量名称及说明 | 有变量时提供“直接变量（数量）”展开项，不强行补充缺失关系 |
| 金融意义 | 已保存的评价摘要、分析维度说明、研究用途、评价范围和研究期限 | 显示草案、已确认或待重新评价；没有评价时明确提示尚无已保存评价 |
| 评价依据与限制 | 评价中已保存的限制和缺口 | 默认收起，显示数量，点击后展开；不将尚未验证的解释当作事实 |

Subject与Target在桌面并列，金融意义位于其下；窄屏改为顺序阅读。金融意义只呈现已有评价；M为空时显示“文字评价，未量化”，保留草案或待重新评价状态。多个评价可分别展示，不将不同范围或期限的评价混为单一结论。

### 5.4 关联候选与原文追溯

正式事件在主要阅读版块下直接展示“关联候选事件（数量）”，不要求进入独立候选处理页。

| 内容或动作 | 展示与规则 |
| --- | --- |
| 候选概要 | 直接显示每项候选的标题、摘要及其对当前事件的关联作用和说明 |
| 关联作用 | 按已有归属显示初始事实、进展、补充、纠正或佐证；不自行改变已确认关系 |
| 查看候选详情与原文 | 在本页展开该候选的主体、行动、发生时间、阶段及逐条引文 |
| 查看对应版本原文 | 从引文旁打开所引用版本的原始资料，保留当前事件阅读位置 |
| 候选范围 | 仅显示已经确认归入本事件的候选；未归组候选及其他事件的候选不能混入 |

### 5.5 资料候选列表与只读详情

“资料的候选事实”页以一份已保存资料为范围，列出其全部候选事实的标题和当前归属。点击“查看正式事件”进入已确认的所属事件；点击“查看未归组候选”进入只读候选事实详情。页面提供“返回信息接入任务”。

候选事实详情展示标题、摘要、主体、行动、发生时间、阶段、事件归属及来源证据。已有正式事件归属时提供“查看所属正式事件”；尚未归组时显示“尚未确认归属，保留为候选事实”。引文旁提供对应版本原文入口，页头可返回正式事件列表。

候选列表没有结果时显示“尚无候选事实，请查看接入任务的抽取状态”。这些页面承担阅读与追溯，不提供人工批准、事件新建或归属修改表单；待复核状态须按既有受控流程处理，不能通过查看页面自动推进。

### 5.6 结果交付、下载与恢复

“结果交付与下载”作为详情末尾的折叠区，默认收起。展开后提供当前结果下载，并逐项展示已有交付及文件状态。

| 状态或动作 | 页面表现与限制 |
| --- | --- |
| 下载当前结果 | 下载当前已保存的正式事件结果 |
| 已接收并采用 | 接收端已持久接收且已采用该结果 |
| 已接收，等待前序交付 | 结果已经收到，但采用顺序尚不满足；不得显示为已经采用 |
| 等待交付或文件待恢复 | 如实显示当前状态，不能因文件未生成而显示成功 |
| 下载当次交付结果 | 当对应交付文件可读取时显示，供核对该次实际交付内容 |
| 下载接收回执 | 对已接收的交付提供对应消费者回执 |

## 6. 跨模块协作与业务契约

F01 提供已保存且版本明确的 Information 与原件定位，F02 据此抽取候选并保留资料归属。F03/F05 接收正式 Event、本次采用的 Fact、直接关系与评价依据，用于各自的风险分析；接收成功不代表其业务分析完成。

定义缺口提交 M2，方法问题提交 M3，执行失败交 S01。每项业务结论应能追溯采用的资料版本、定义版本、方法及复核决定。

## 7. 核心业务规则

- 一份 Information 对应多个 Fact 合法；一个 Fact 由多份 Information 支持也合法。
- 正式 Event 唯一且至少有一个 Fact；Fact 未归组时不创建空 Event。
- 同一行动经完整检索和证据比较后复用已有事件；创建前再次核实是否已有其他处理确认了同一事件。
- 候选归属、主体/变量关系和评价依据须明确，原文、定义和处理决定均可追溯。
- 当前事实的纠正必须反映在事件展示及交付内容中，原 Fact 与审计仍可追溯。
- 没有变化不生成重复业务结果或通知；证据冲突不伪装成已确认事实。
- 可量化方法和自动审批政策仍需正式发布，未获批准前不得生效。

## 8. 功能验收要求

以下场景用于核对业务结果与异常处理是否符合要求，验收执行情况另行记录。

| 编号 | 输入情境 | 验收预期 |
| --- | --- | --- |
| AC-F02-01 | 一篇宏观评论只有观点，没有具体变化 | 记录无事件结果，Information 保留，0 Fact、0 Event；模型失败不得冒充无事件 |
| AC-F02-02 | 一份报告同时包含两项独立政策决定 | 一条 Information 关联两个 Fact，分别匹配独立 Event，处理互不阻断 |
| AC-F02-03 | 相同政策被两家官方机构报道 | 相同事实可复用 Fact 并关联两条 Information；确认同一 Event 后建立唯一归属 |
| AC-F02-04 | 同一机构在两日独立宣布不同措施，标题相似 | 不按标题合并，分别创建事件身份 |
| AC-F02-05 | 新资料只增加独立佐证，无核心事实变化 | 复用已有 Fact 或确认佐证 Fact，保留资料关系；不制造新的 Event 或无依据复评 |
| AC-F02-06 | 同一来源重复交付相同资料版本三次 | 复用已有结果，不新增业务进展、不重复通知 |
| AC-F02-07 | 某政策先公布，下周正式实施 | 公布与实施事实分别可追溯，同一行动归入原 Event，按证据更新当前阶段 |
| AC-F02-08 | 原官方资料修订了已记入事件的关键数字 | 新旧资料版本及 Fact 均保留；明确纠正理由，原 Event 当前数字、标题和描述同步更新 |
| AC-F02-09 | 可确认 Target，无法确认某个全局变量 | 事件与观测主体的关系有效，三元关系可空，提交 M2 候选 |
| AC-F02-10 | AI 引用了不存在的正式事件或变量 | 校验失败，禁止写入虚构正式关系，保留异常依据 |
| AC-F02-11 | 本次事件作用于两个 Target，只有其中一个变量有直接依据 | 分别说明事件与各观测主体的关系；仅有依据的关系建立三元引用 |
| AC-F02-12 | 新证据与多个历史 Event 均相似，无法排除冲突 | 转 `UNRESOLVED`，保存候选对比与证据，不强行合并 |
| AC-F02-13 | 某 Information 的两个事件中一个歧义、一个明确 | 明确事件完成处理，歧义事件待归组 |
| AC-F02-14 | 事件 M 的正式权重/分值阈值尚未确认 | 维度、用途、理由和草案可保存；总分为空且不宣称正式评级 |
| AC-F02-15 | 实质进展未改变金融意义依据 | 关联有效进展 Fact、更新适用当前事实，记录未复评原因并沿用评价 |
| AC-F02-16 | Event 已提交，F03 消费通知失败 | 只重试原提交的交付文件，不重复 Fact、Event、关系或 Rating |
| AC-F02-17 | 用户查阅几个月前的事件状态 | 可查看当时 Fact、资料版本和授权操作记录，并与当前事件结论清楚区分 |
| AC-F02-18 | 人工处理错归组，拟合并两个 Event | 提示身份/历史/下游引用影响；自动正式重定向在审批前禁用 |
| AC-F02-19 | 已保存的文件资料无标题、URL 或发布时间，但来源凭据及内容完整 | 正常受理，缺失项明示；不补造标题、URL 或发布时间 |
| AC-F02-20 | 资料仍暂存、部分保存或必需内容不可读 | 不开始正式事件分析，反馈具体输入问题，由 F01 恢复 |
| AC-F02-21 | 同一原件重新解析形成新资料版本，事件事实未变 | 保留 F01 解析版本与证据，核对一致后复用候选/事件，不自动生成来源纠正或复评 |
| AC-F02-22 | 原来源只更正排版或与当前事件无关的内容 | 保留版本对照，当前事件无实质增量，不按版本变化自动纠正 |
| AC-F02-23 | 已接收的资料含多个候选，只有部分处理完成，此时收到同版补发 | 复用接收与已完成结果，继续未完成部分，不整份跳过或重复建事件 |
| AC-F02-24 | F02 已可靠接收，F01 未记录回执而再次投递；分析尚未完成 | 恢复接收回执，处理状态仍如实显示进行中/待处理，不宣称分析完成 |
| AC-F02-25 | 重解析揭示既有事件结论源于错误读取，原来源未修订 | 进入受控复核，保留旧结论与两版解析证据，不标成来源主动纠正；授权后才能修正 |
| AC-F02-26 | 较旧资料或迟到公告在较新事件状态之后送达 | 按事实和业务时间补充历史，不因到达顺序回退当前状态 |
| AC-F02-27 | 正式提交成功但确认丢失，随后恢复或并发重试 | 核实原保存结果，复用已保存 Fact、Event、关系及评价，不产生重复结果 |
| AC-F02-28 | 同一资料多个版本、每版多个位置支撑同一事件 | 可逐项查看支持该事实的资料及其准确版本、原文位置和证据作用，不能跳到其他版本 |
| AC-F02-29 | 关系引用了另一事件的证据，或三元关系没有有效的事件与观测主体关系 | 关系证据所用 Fact 必须归属本 Event，三元关系必须有有效的事件与观测主体关系，否则拒绝 |
| AC-F02-30 | 同一事件同一方法，分别评价两个范围或研究期限 | 各组评价独立保存；同操作重试不重复，不覆盖其他范围/期限 |
| AC-F02-31 | 两家独立来源描述同一个已确认实质进展 | 经实质核对复用同一 Fact，并保留两个资料关系与证据，不重复建 Event |
| AC-F02-32 | 一份资料包含同一事件的两项独立实质补充 | 保留两项独立 Fact，均关联原 Information，确认同一事件后关联同一 Event |
| AC-F02-33 | 主体范围、直接变量方向或关联被调整 | 受控变更当前关系并记录操作及采用的定义版本；原批准不适用于已改变的事实依据 |
| AC-F02-34 | 候选抽取尚未完成即中断，随后恢复并再次投递 | 候选数量未知不当成0；恢复后明确完整候选清单，已完成候选不重复保存 |
| AC-F02-35 | 来源纠正后再次查看纠正前状态 | 旧 Fact、旧资料版本及审计仍可读；显示纠正理由，并区分纠正前陈述与当前有效事实 |
| AC-F02-36 | 新事件进入 Step 5，量化规则已批准且证据充分 | 程序固定范围/期限/方法并准备输入；AI-05 给出维度与用途依据；程序校验和独立计算，整理评级记录后交 Step 6；AI 总分或状态不能直接成为正式评级。 |
| AC-F02-37 | 评级依据未改变，或仅增加来源/重复资料 | 程序记录沿用或不适用；不调用 AI-05，不创建重复评级；适用来源变化仍按 Step 6～7 保存交付。 |
| AC-F02-38 | AI-02 返回虚构 ID，或 AI-05 改变范围/返回越界分值，或调用超时 | 在当前步拦截，不传入后续分析/正式保存；记录待恢复或复核，执行失败不能伪装成无事件或合法空分。 |
| AC-F02-39 | 人工改变候选归属，已有后续分析但尚未提交 | 程序确认新身份，重新处理依赖旧身份的关系、增量和评级；不直接复用旧结果进入 Step 6；已提交结果走受控修正。 |
| AC-F02-40 | 两份资料共同支持一个 Fact | 同一个 Fact 可查看两份来源及各自证据，不重复建立候选 |
| AC-F02-41 | 同一 Fact 拟归属两个 Event | 拒绝同时归属两个事件，保留已确认的有效归属；需改归属时进入受控复核 |
| AC-F02-42 | 只知道发生日期，或只有预计日期 | 只存确定发生日期或空，不伪造精确时刻 |
| AC-F02-43 | 用户查看当前事件 | 当前事实、阶段和发生时间明确，关联 Fact、资料与处理决定可逐项追溯 |
| AC-F02-44 | 交付消息乱序到达 | 如实展示已接收但尚未采用的结果，较早结果晚到不覆盖较新的有效结果 |
| AC-F02-45 | 打开事件管理或旧候选处理入口 | 默认展示正式事件；旧入口按实际归属转到正式事件或只读候选资料，不展示独立处理页面，不触发复核或保存 |
| AC-F02-46 | 正式事件关联多项候选 | 直接显示各候选标题、摘要和关联说明，可展开各自原文；未归组及其他事件的候选不得混入，刷新保留展开状态 |

## 9. 待明确的业务规则与范围

- 自动合并/拆分：明确可操作角色、审批条件和下游引用调整责任后，方可开放自动维护。
- M 量化与自动审批：正式方法、权重、阈值及自动通过政策由对应治理方批准；未批准时保留草案、空分或人工复核。
- 跨模块职责：F02 的交付验收以接收和采用状态为依据；M2/M3 的定义与方法治理、F03/F05 的风险分析由各模块分别验收。
