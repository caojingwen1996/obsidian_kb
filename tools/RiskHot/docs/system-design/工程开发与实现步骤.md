# 工程开发与实现步骤 V1.0

## 1. 文档概述

### 1.1 目的

建立从系统技术架构设计到可测试软件版本的统一工程实施流程，明确各步骤的输入、关键活动、交付物、完成标准及质量控制要求，使架构设计能够转化为可运行、可验证、可维护的工程制品。

### 1.2 适用范围

适用于企业应用、平台系统、微服务系统、数据处理系统及 AI/Agent 系统等软件工程项目。团队可按系统规模裁剪步骤的工作量和文档数量，但应保留必要的质量门禁与可追溯性。

### 1.3 阶段边界

- **上游输入**：需求与业务设计、系统总体技术架构、相关技术专题、模块技术详细设计、公共技术契约、架构决策记录（ADR）。
- **本阶段目标**：形成经开发验证、可以部署到测试环境、可移交进一步系统测试的软件版本。
- **后续阶段**：完整系统测试、用户验收、生产发布及运维。开发阶段的单元、组件、契约和集成验证应持续进行。
- **实施原则**：可以按模块分批完成设计与开发；进入某个开发任务前，其必需的契约、边界及验收要求应明确。

### 1.4 核心工程原则

1. **架构驱动**：实现遵循已确认的架构边界；偏离设计时记录变更与依据。
2. **契约优先**：共享 Schema、API、事件契约明确责任人和版本。
3. **垂直切片**：尽早构建最小端到端业务闭环，验证真实集成关系。
4. **持续质量控制**：编码、测试、审查和自动化检查同步推进。
5. **环境可复现**：开发环境、依赖、数据库迁移及构建过程可重复执行。
6. **结果可追溯**：需求、设计、任务、代码变更、测试结果与发布制品可关联。
7. **小步迭代**：优先实现当前业务闭环所必需的公共能力，避免过早抽象。

## 3. 开发启动条件（Entry Criteria）

在启动某一迭代或模块的实现前，确认：

- [ ] 本迭代业务目标、范围、验收条件明确。
- [ ] 相关系统架构与模块边界已评审，关键约束可追踪。
- [ ] 本迭代涉及的公共数据模型、API 和事件契约已有明确版本或决策计划。
- [ ] 高风险技术选型已有验证结论，或安排了明确的 PoC 任务。
- [ ] 主要开发依赖、人员职责、外部系统及环境条件已识别。
- [ ] 遗留问题区分为“阻断开发”和“允许带风险推进”，指定责任人和处理期限。

不要求全系统所有设计同时完成；每个开发任务应满足自身的进入条件（Definition of Ready，DoR）。

## 4. 详细执行步骤

### 4.1 步骤 01：开发任务规划与拆解

**输入**：已确认的功能范围、模块设计、公共技术契约、质量要求与技术约束。

**执行内容**：

1. 确定迭代目标、开发范围与关键业务闭环。
2. 将工作分解为功能任务、技术任务、数据契约任务、测试任务和环境任务。
3. 识别任务依赖、外部阻塞、风险及优先级；落实责任人。
4. 对每个任务定义输入、预期行为、异常路径、验收标准和验证方式。
5. 确立迭代基线，约定变更和缺陷跟踪方式。

**交付物**：迭代计划、任务清单、依赖关系、风险与阻塞清单。

**完成标准**：首轮任务具备清晰的 DoR，可以进入工程实施；关键依赖有处理方案。

### 4.2 步骤 02：代码仓库与工程结构初始化

**输入**：总体技术架构、模块与组件边界、技术栈选型。

**执行内容**：

1. 按部署单元、服务和模块边界选择代码仓库组织方式。
2. 建立源代码、测试、配置、脚本、数据库迁移和部署描述目录。
3. 固定核心依赖和构建版本，建立项目启动入口与基础健康检查。
4. 编写最小 README，说明本地启动、配置示例、运行命令和测试命令。
5. 验证新开发环境可从干净状态完成依赖安装、构建和启动。

**交付物**：代码仓库、工程骨架、依赖锁定文件、初始化说明。

**完成标准**：开发者可按文档拉取代码、安装依赖、启动最小服务并运行基础检查。

### 4.3 步骤 03：开发规范与质量门禁建立

**输入**：组织工程规范、代码仓库结构、质量属性目标。

**执行内容**：

1. 约定分支策略、提交规范、代码审查与合并流程。
2. 配置格式化、Lint、类型检查、基础安全与依赖检查（按技术栈适配）。
3. 建立 Pull Request 模板、任务与需求关联约定。
4. 配置自动化构建与测试的最低合并门禁。
5. 明确严重缺陷、安全问题、失败测试和架构偏离的处理规则。

**交付物**：开发规范、PR 模板、CI 工作流、质量门禁配置。

**完成标准**：一次示例变更能完成自动检查、审查和可追踪的合并流程。

### 4.4 步骤 04：开发环境与基础设施准备

**输入**：系统部署架构、依赖清单、环境隔离及安全要求。

**执行内容**：

1. 明确本地、开发、集成测试等环境的用途与差异。
2. 准备数据库、缓存、消息服务和外部依赖的真实服务或可控替身。
3. 使用环境变量、密钥管理机制和配置模板管理环境参数，避免真实密钥入库。
4. 编写环境初始化、数据准备、清理和故障排查脚本。
5. 检查环境启动、服务连通性、基本权限和可观测性。

**交付物**：环境配置模板、启动脚本、依赖说明、验证记录。

**完成标准**：环境可重复创建，工程可启动，关键依赖连通且敏感配置受到保护。

### 4.5 步骤 05：数据模型与接口契约实现

**输入**：公共技术契约、模块设计、数据架构和接口集成设计。

**执行内容**：

1. 将共享对象转化为受版本管理的 Schema、API 定义及事件契约。
2. 明确对象标识、字段语义、必填约束、状态枚举、错误码和兼容规则。
3. 设计并实现数据库建表、索引、迁移与必要的回滚或修复方案。
4. 生成或建立契约校验工具，准备请求响应样例与测试数据。
5. 确认数据写入主责、消费方、版本升级以及跨模块兼容性。

**交付物**：Schema、接口定义、事件定义、迁移脚本、契约测试。

**完成标准**：核心契约能够自动验证；消费者和生产者对字段、状态与版本的解释一致。

### 4.6 步骤 06：公共技术组件与基础能力开发

**输入**：总体架构、横切技术要求、相关技术专题和首轮开发需求。

**执行内容**：

1. 实现当前闭环必需的配置、日志、追踪、错误处理和持久化适配能力。
2. 按实际需求实现认证授权、任务执行、消息发送、缓存等公共能力。
3. 为公共组件提供明确接口、默认行为、失败语义和使用示例。
4. 增加基础组件测试，并明确组件维护和版本兼容规则。
5. 避免在缺少业务需求和调用方时过度建设公共框架。

**交付物**：公共组件代码、接口说明、使用示例和测试结果。

**完成标准**：首个业务闭环所需公共能力已具备，组件接口稳定且可测试。

### 4.7 步骤 07：最小端到端业务闭环实现

**输入**：已具备的工程骨架、核心契约、必要公共组件与最小业务场景。

**执行内容**：

1. 选择一条覆盖真实输入、关键处理、结果输出的代表性业务链路。
2. 打通模块间调用、数据持久化和业务状态传递。
3. 建立贯穿链路的关联标识、日志与基本监控。
4. 验证一个正常流程和至少一个关键失败/恢复场景。
5. 记录架构与契约在真实执行中暴露的问题，并及时回写设计文档。

**交付物**：最小可运行闭环、端到端测试、缺陷和架构反馈记录。

**完成标准**：业务链路可重复运行；结果可查询、状态可追踪，核心失败行为可验证。

### 4.8 步骤 08：功能模块迭代开发

**输入**：当前模块的功能设计、技术详细设计、公共契约、迭代任务清单。

**执行内容**：

1. 按功能单元进一步拆解任务，明确接口、状态、数据访问和异常路径。
2. 实现业务逻辑、接口适配、数据操作及必要算法。
3. 对并发、幂等、超时、权限、错误码和状态转换实施约束。
4. 编写自动化测试，将任务、代码、测试和需求关联。
5. 在代码审查和集成验证通过后合并变更。

**交付物**：模块代码、变更记录、自动化测试和更新后的技术说明。

**完成标准**：任务满足本文件第 5 节的 DoD，且不违反已确认的公共契约。

### 4.9 步骤 09：单元测试、组件测试与代码审查

**输入**：功能实现、技术约束、任务验收标准和测试策略。

**执行内容**：

1. 覆盖核心业务规则、边界输入、异常和状态转换。
2. 对关键组件验证失败语义、幂等性、超时和资源释放。
3. 运行格式、类型、静态分析、依赖和安全基础检查。
4. 审查代码可维护性、架构遵循、日志质量与接口兼容。
5. 对发现的问题修复并补充防回归测试。

**交付物**：测试结果、代码审查记录、缺陷修复记录。

**完成标准**：约定的质量门禁通过；已识别阻断问题均关闭或经正式批准处理。

### 4.10 步骤 10：模块集成与自动化回归验证

**输入**：已合并的模块版本、共享契约、业务场景和集成环境。

**执行内容**：

1. 验证模块间 API、消息、事件与数据库交互。
2. 覆盖跨模块端到端业务流程和关键异常场景。
3. 检查请求重复、乱序、重试、并发、超时及恢复后的业务结果。
4. 进行契约兼容性检查及必要的性能基线验证。
5. 将发现的问题纳入回归测试集并持续执行。

**交付物**：集成测试结果、自动化回归集、缺陷清单与修复记录。

**完成标准**：当前迭代关键链路通过；阻断级集成缺陷已解决。

### 4.11 步骤 11：构建打包与测试环境部署

**输入**：通过质量门禁的代码、部署架构、配置和数据库迁移方案。

**执行内容**：

1. 自动化构建可标识版本的制品，记录源码提交和依赖版本。
2. 验证环境配置、密钥引用、存储和消息服务连接。
3. 执行数据库迁移与服务部署，保留部署与变更记录。
4. 检查健康状态、基础业务功能和关键监控指标。
5. 演练适用的回滚或恢复操作，明确不可逆迁移的处理方案。

**交付物**：可追溯构建制品、测试环境版本、部署与回滚记录。

**完成标准**：制品可重复构建、可部署，基本健康检查和冒烟测试通过。

### 4.12 步骤 12：开发验收与测试移交

**输入**：已部署版本、开发计划、测试结果、已知问题与设计变更记录。

**执行内容**：

1. 按迭代范围逐项核验功能、接口、约束和开发完成条件。
2. 汇总测试覆盖、缺陷状态、架构偏差、变更与风险。
3. 整理部署说明、配置清单、测试数据、接口文档和运维初始信息。
4. 与系统测试方确认测试入口、环境、账号权限和数据准备。
5. 建立正式的版本交付记录和遗留问题跟踪机制。

**交付物**：开发验收清单、版本说明、测试移交材料、遗留问题清单。

**完成标准**：测试方可以独立部署或访问版本、执行约定测试并追溯问题。

## 5. 模块开发标准工作流

### 5.1 单个开发任务的执行循环

```text
确认任务范围与验收条件
        ↓
核对功能/技术设计及接口契约
        ↓
实现功能与必要自动化测试
        ↓
本地验证、静态检查与代码审查
        ↓
跨模块联调与回归验证
        ↓
合并代码、更新文档与任务状态
```

如出现架构边界、公共接口或共享 Schema 的变更，先履行设计变更评审，再更新权威契约与依赖实现。

### 5.2 开发任务输入模板

| 字段 | 说明 |
|---|---|
| 任务编号与名称 | 唯一标识和简要目标 |
| 关联需求 | 功能编号、业务规则、验收场景 |
| 设计依据 | 模块设计、相关专题、ADR |
| 依赖契约 | API、事件、Schema 版本 |
| 影响范围 | 模块、数据、接口、测试、部署 |
| 实现要求 | 正常流程、异常流程、状态约束 |
| 验证要求 | 单元、契约、集成及必要非功能测试 |
| 完成条件 | 可检查、可验证的验收标准 |

### 5.3 开发完成标准（Definition of Done，DoD）

- [ ] 实现与已批准的功能设计、模块设计和公共契约一致。
- [ ] 正常路径及关键异常、边界路径均已处理。
- [ ] 适用的单元、组件、契约和集成测试通过。
- [ ] 日志、错误处理、权限与必要监控已落实。
- [ ] 代码审查、自动化构建和质量门禁通过。
- [ ] 数据库迁移、配置及兼容影响已处理。
- [ ] 任务、代码、测试及相关文档可相互追踪。
- [ ] 重大遗留问题已解决或经过明确风险接受流程。

## 6. 工程质量与变更管理

### 6.1 持续质量验证

- **提交前**：格式检查、单元测试、必要的本地契约检查。
- **代码合并前**：CI 构建、自动测试、静态检查、代码审查。
- **迭代集成时**：跨模块接口、端到端流程、关键异常与回归测试。
- **版本交付前**：部署验证、冒烟测试、关键质量指标和遗留问题审查。

覆盖率、性能、恢复时间和质量阈值应由项目质量目标明确给出，避免无依据套用统一数字。

### 6.2 设计变更规则

1. 发现现有设计无法支撑开发时，先记录问题、影响范围和候选方案。
2. **局部实现调整**：由模块责任人和代码审查流程处理。
3. **公共 Schema、接口或事件变更**：更新公共技术契约并进行消费者影响评估。
4. **跨模块技术机制变更**：更新专题设计并进行相关方评审。
5. **总体架构原则或组件边界变更**：更新总体架构与必要的 ADR。
6. 变更完成后同步更新测试、文档及迁移安排。

### 6.3 关键工程风险

| 风险 | 控制措施 |
|---|---|
| 架构与实现脱节 | 设计引用、架构符合性审查、ADR |
| Schema 多处重复维护 | 统一契约所有者与版本基线 |
| 公共框架过度建设 | 最小闭环驱动、按需扩展 |
| 集成风险集中暴露 | 提前打通端到端链路、持续集成 |
| 开发环境不可复现 | 依赖锁定、初始化脚本、配置模板 |
| 失败重试造成重复结果 | 幂等键、状态约束与恢复测试 |
| 只验证正常流程 | 异常、边界、恢复及回归测试 |

## 7. 工程里程碑与阶段验收

| 里程碑 | 目标 | 最低验收条件 |
|---|---|---|
| **M1 工程就绪** | 建立可运行、可协作的开发基础 | 工程启动成功；环境可复现；CI 与基础测试可执行 |
| **M2 核心闭环可运行** | 验证架构与关键业务链路 | 输入、处理、输出、状态及持久化贯通；关键异常可验证 |
| **M3 开发版本可交付** | 形成可交接的工程版本 | 当前范围完成；自动化与集成检查通过；测试环境部署成功；移交材料齐备 |

每个里程碑应记录版本号、评审结论、问题及后续行动。达到 M3 后继续实施独立的系统级质量验证和正式验收。

## 9. 项目应用示例：RiskHot 首轮开发闭环

> 本节仅为应用示例；各模块职责、数据对象、技术选型及实现方式应以项目已确认的业务设计和技术设计为准，不预先认定某个业务层级对应独立部署服务。

### 9.1 建议首轮目标

围绕信息接入与处理能力，验证从任务发起/接收至信息处理、事件候选结果保存及执行状态监测的最小链路。

### 9.2 建议实施顺序

| 顺序 | 开发内容 | 验证目标 |
|---|---|---|
| 1 | 工程骨架、依赖环境与任务执行基础设施 | 服务可启动、可调试、可追踪 |
| 2 | 信源与抓取任务有关的配置、调用和状态能力 | 任务可发起或接收，状态可记录 |
| 3 | 内容获取、解析及标准化处理 | 产出符合约定 Schema 的标准化信息 |
| 4 | F02 AI-01 事件候选抽取 | 模型输出经过 Schema 与业务规则校验 |
| 5 | 结果持久化与状态追踪 | 处理结果可查询，执行链路可定位 |
| 6 | 超时、失败、重试及恢复验证 | 失败可识别、可恢复，正式结果满足去重/幂等约束 |
| 7 | 端到端自动化验证 | 关键链路可持续重复运行 |

### 9.3 需要优先确认的技术决策

- 任务标识与信息标识的生成、关联及唯一性规则。
- F01/F02 的真实功能边界、任务主责及状态持久化归属。
- 原始信息、标准化信息与事件候选的 Schema 和生命周期。
- AI 抽取成功、失败、重试、人工处理等状态与结果判定。
- 幂等及重复数据处理规则、追踪标识和监控指标。

未经确认的数据库、消息队列、Agent 框架及编程语言应记录为候选方案或待决策项。
