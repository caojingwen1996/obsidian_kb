# EventTarget 关系简化评测集

版本：0.2.0；日期：2026-10-29；状态：评测设计草案，标注待人工复核，尚未执行模型或数据库评测。

## 用途与来源

本集承接用户对删除 event_target、只保留 event_target_variable 的讨论，用于比较两个方案的行为和信息损失。V0.1仅收录仓库内设计文档、代码依据与16个合成场景。V0.2增加运行目录中已经采集的160份真实来源Information。本次未重新联网抓取或核验原网页。16个既有场景仍全部为合成用例，不能作为模型真实准确率的依据。

资料属于 RiskHot 软件项目，保存在项目场景验证目录，不进入正式 Wiki。评测集创建不等于批准删表或修改核心驱动变量的业务定义。

[[tools/RiskHot/docs/system-design/05-场景验证/EventTarget关系简化评测集/依据说明|依据说明与原始路径]]记录来源位置、现有冲突与用户提案；[[tools/RiskHot/docs/system-design/05-场景验证/EventTarget关系简化评测集/依据快照.json|依据快照]]保存6份仓库材料的关键原文摘录、整文件SHA-256及用户原话。摘录可离线核对，指纹用于发现来源后续变动。

## 评测假设

- 现有设计：允许独立主体关系；三元关系依赖主体关系。
- 待评估提案：Event及事实正常保存；只有主体、变量和直接依据齐备时才新增三元关系；没有合格关系时零新增记录，不写NULL变量占位。
- “核心驱动变量”暂未正式定义。本集以现有“直接涉及的变量”作为可判定用例的临时口径，不将该假设写回正式设计。ETV-015专门保留两种语义分支。
- “留空”指本轮没有新关系，不默认清空事件的历史关系。ETV-014检验这一边界。
- E1/T1/V1/F1等为样例别名，执行数据库测试时须映射为有效UUID及夹具，不可直接作为生产ID。
- 样例中的定义有效、Fact归属等为受控前置条件；不涉及生产数据读取或写入。

## 逐例输入与预期

### ETV-001 明确主体与直接变量

输入（合成）：

```json
{
  "event": "E1：A经济体政策利率已下调。",
  "definitions": {
    "targets": [
      "T1：A经济体，v1，有效"
    ],
    "variables": [
      "V1：政策利率，v1，有效"
    ]
  },
  "facts": [
    "F1属于E1，直接支持下调"
  ]
}
```

现有设计：建立E1/T1及E1/T1/V1。

提案预期：建立E1/T1/V1，方向decrease、阶段effective，记录F1和定义依据。

判定断言：

- 恰有一组三元关系。
- 不需要独立event_target记录。
- 正式定义与本事件事实均可追溯。

依据：S02, S03, S06, U01。

### ETV-002 已确认主体但没有直接变量

输入（合成）：

```json
{
  "event": "E1：A经济体召开政策讨论会，未宣布具体措施。",
  "targets": [
    "T1已匹配"
  ],
  "variable_evidence": []
}
```

现有设计：可保存E1/T1，变量关系为空。

提案预期：保存Event与事实；新增三元关系为零；不独立保存主体关联。

判定断言：

- 不得编造变量或删除Event。
- 记录已完成分析且无合格变量。
- 按三元关系派生的Target事件查询不包含E1。

依据：S01, S05, U01。

### ETV-003 变量概念明确但字典缺定义

输入（合成）：

```json
{
  "event": "E1：A经济体宣布新增专项支持额度。",
  "targets": [
    "T1有效"
  ],
  "variables": [],
  "fact": "F1支持额度调整，但正式变量库无对应项"
}
```

现有设计：可保留主体关系并提交变量定义缺口。

提案预期：三元关系为零，保留Event及变量定义缺口。

判定断言：

- 不得生成伪variable_id。
- 缺口不能标为没有相关变量。
- 定义获批后允许重新分析。

依据：S02, S05, U01。

### ETV-004 主体定义无法匹配

输入（合成）：

```json
{
  "event": "E1涉及某新设区域的正式利率调整。",
  "targets": [],
  "variables": [
    "V1有效"
  ],
  "fact": "F1直接支持，但区域范围未核定"
}
```

现有设计：暂不建立正式主体或变量关系。

提案预期：三元关系为零，记录主体范围及定义缺口。

判定断言：

- 不得以名称近似的T1替代。
- 保留Event与Fact。
- 缺口原因可区分。

依据：S02, S05, U01。

### ETV-005 关系分析失败

输入（合成）：

```json
{
  "event": "E1已存在",
  "analysis": "AI-03超时",
  "existing_relations": []
}
```

现有设计：保留失败状态，不当合法空结果。

提案预期：保留失败/待恢复状态；不新增三元关系。

判定断言：

- 不得将超时记录为分析完成且无变量。
- 不破坏已有Event。
- 支持后续重试。

依据：S05。

### ETV-006 同主体涉及两个变量

输入（合成）：

```json
{
  "event": "E1同时下调政策利率并提高信贷额度。",
  "targets": [
    "T1有效v1"
  ],
  "variables": [
    "V1政策利率有效v1",
    "V2信贷额度有效v1"
  ],
  "facts": [
    "F1属于E1，支持两项调整"
  ]
}
```

现有设计：一条主体关系、两条变量关系。

提案预期：两条三元关系：E1/T1/V1和E1/T1/V2。

判定断言：

- 两条关系均有直接依据。
- 按Target查询事件去重后仅E1一条。
- 主体定义范围保持一致。

依据：S02, S03, U01。

### ETV-007 两个主体涉及同一变量

输入（合成）：

```json
{
  "event": "E1分别调整A、B经济体的政策利率。",
  "targets": [
    "T1=A",
    "T2=B"
  ],
  "variables": [
    "V1政策利率"
  ],
  "facts": [
    "F1属于E1，分别列明两地变化"
  ],
  "definitions": "三项均有效"
}
```

现有设计：两条主体关系、两条变量关系。

提案预期：E1/T1/V1和E1/T2/V1均保留。

判定断言：

- 不能只按event_id和variable_id去重。
- 各主体的方向及证据分别准确。

依据：S02, S03, U01。

### ETV-008 行为发起者不是观测主体

输入（合成）：

```json
{
  "event": "E1：监管机构宣布下调A经济体政策利率。",
  "actor": "监管机构",
  "targets": [
    "T1=A经济体",
    "T2=监管机构"
  ],
  "variables": [
    "V1=政策利率"
  ],
  "fact": "F1仅支持A经济体利率变化"
}
```

现有设计：关联T1，不因发起者身份自动关联T2。

提案预期：仅建立E1/T1/V1。

判定断言：

- 不得自动创建E1/T2/V1。
- 行为主体信息保留在Event语义中。

依据：S05, S06。

### ETV-009 后续传导推测

输入（合成）：

```json
{
  "event": "E1：A经济体政策利率下调。",
  "targets": [
    "T1有效"
  ],
  "variables": [
    "V1政策利率有效",
    "V2企业利润有效"
  ],
  "fact": "F1仅支持利率下调",
  "model_suggestion": "因此企业利润可能提高"
}
```

现有设计：可关联V1，不能以推测建立V2直接关系。

提案预期：同样只接受V1；若核心驱动另有含义须先修订契约。

判定断言：

- 不得把后续传导推测当事实依据。
- V2不能仅凭模型推测正式入库。

依据：S05, S06, U01。

### ETV-010 禁止空变量占位

输入（合成）：

```json
{
  "proposed_row": {
    "event_id": "E1",
    "target_id": "T1",
    "variable_id": null
  }
}
```

现有设计：联合主键不允许空变量。

提案预期：拒绝该记录；没有合格变量时用零条新增关系表达。

判定断言：

- 不得保存NULL或空串变量ID。
- 不得用unknown之类虚构ID占位。

依据：S03, U01。

### ETV-011 禁止跨事件借用事实

输入（合成）：

```json
{
  "triple": [
    "E1",
    "T1",
    "V1"
  ],
  "fact": "F2只属于E2",
  "definitions": "T1/V1有效"
}
```

现有设计：复合外键阻止跨事件事实关系。

提案预期：保留同事件Fact约束，拒绝F2作为E1关系依据。

判定断言：

- 不得因删表而移除同事件证据约束。
- 关系和证据应原子提交或失败。

依据：S02, S03。

### ETV-012 主体定义快照冲突

输入（合成）：

```json
{
  "triples": [
    "E1/T1/V1引用T1 v1",
    "E1/T1/V2引用T1 v2"
  ],
  "definition_change": "v2改变了主体覆盖范围"
}
```

现有设计：主体关系只有一条当前主体定义快照。

提案预期：检测冲突并进入复核；是否允许逐关系不同版本尚待明确。

判定断言：

- 必须指出范围冲突。
- 未确定版本政策前不得宣称两条均一致有效。

依据：S02, S04, U01。

### ETV-013 重复提交保持幂等

输入（合成）：

```json
{
  "existing": [
    "E1/T1/V1，依据F1"
  ],
  "incoming": [
    "同一E1/T1/V1与相同F1再次提交"
  ]
}
```

现有设计：联合主键和受控写入复用原关系。

提案预期：仍只有一条三元关系及一条对应事实关联。

判定断言：

- 不得重复增加关系。
- 重复请求不能导致重复事实关联。

依据：S03, S04。

### ETV-014 本轮空结果不代表撤销旧关系

输入（合成）：

```json
{
  "existing": [
    "E1/T1/V1"
  ],
  "new_fact": "F2补充会议地点，未涉及变量",
  "explicit_retraction": false
}
```

现有设计：保留旧关系；未提及不等于删除。

提案预期：新增三元关系为零，已有E1/T1/V1保留。

判定断言：

- 区分新增关系为零和事件全部关系清空。
- 只有明确撤销决定才能处理旧关系。

依据：S02, S04, U01。

### ETV-015 结果变量是否算核心驱动

输入（合成）：

```json
{
  "event": "E1：A经济体失业率已上升。",
  "fact": "F1仅为统计结果，无原因陈述",
  "definitions": [
    "T1=A经济体有效",
    "V1=失业率有效"
  ]
}
```

现有设计：有直接依据时可建立observed_change关系。

提案预期：若准入包含直接观测变量则建立；若仅收因果驱动则不建立，需先确定核心驱动定义。

判定断言：

- 不得暗中选定核心驱动含义。
- 两种条件分支均写明。
- 未定规则不计入确定性准确率分母。

依据：S02, S03, U01。

### ETV-016 历史孤立主体关系的迁移

输入（合成）：

```json
{
  "existing_target": "E1/T1",
  "existing_variables": [],
  "target_definition": "v1",
  "facts": [
    "F1支持主体关联"
  ],
  "query": "按T1查找涉及事件"
}
```

现有设计：查询可返回E1。

提案预期：仅从三元关系派生时无法返回E1；必须先决定归档与产品查询口径。

判定断言：

- 记录这项可预期的信息损失。
- 不得编造变量迁移。
- 未完成归档及依赖核对前不能直接删旧表。

依据：S01, S02, S03, U01。

## 执行与评分

1. 先确定评估的是“现有实现符合性”还是“提案可实现性”，不得用提案答案给尚未迁移的现有实现判失败。确认核心驱动定义及主体快照政策后，升级评测集版本并复核标注。
2. 对语义评估，将input和已确认的准入规则提供给模型，不提供预期答案；保留完整输入、模型标识、参数、提示词/Schema版本、原始响应和多次运行结果。未知状态、超时、遗漏单独记录。
3. 对存储及迁移评估，使用隔离测试数据库建立夹具、执行指定操作，保存前后查询结果及异常。当前只有场景和断言，没有编写或运行数据库执行器。
4. 每例每条断言记录pass、fail或blocked及证据；所有断言通过才算该例通过，任一失败算失败，因规则未决无法判断则blocked。ETV-012、ETV-015当前列为规则未决，不能算通过。
5. 建议报告：可判定用例通过数/已执行可判定用例数；已执行可判定用例数/14；未执行数；规则阻塞数；硬失败数。所有失败与漏处理保留，不只挑成功响应。
6. 目前不设未经批准的模型准确率阈值。程序受控测试与真实模型语义质量分别报告；16个公开合成开发用例不能证明真实业务泛化效果；160份真实输入尚无人工金标，不能计算真实准确率。
