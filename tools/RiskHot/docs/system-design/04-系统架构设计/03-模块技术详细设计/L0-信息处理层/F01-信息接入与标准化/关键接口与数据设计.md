# F01 关键接口与数据设计

> V0.6 · 2026-10-24 · 数据契约与物理设计。第6章及T01明确字段类型、索引、事务和存储协议；本稿不创建DDL或执行迁移。

## 1. 最小逻辑记录

| 记录 | 标识及内容 | 约束 |
| --- | --- | --- |
| Information | information_id、source_id、source_identity、identity_rule_version、current_version_ref | 来源身份稳定；current只用于导航，业务引用必须固定版本 |
| InformationVersion | version_ref、information_id、revision_kind、parent_version_ref、source_config_ref、原件/正文/映射引用与摘要、completeness、保存时间 | 已提交内容不可覆盖；同身份版本并发唯一 |
| AcquisitionAttempt | acquisition_id、operation_ref、来源、获取时间、来源声明时间、响应元数据、原件摘要、结果 | 多次获取可指向同版本，不能用获取次数生成版本 |
| VersionDecision | 规则版本、比较版本、身份判据、有效内容摘要、标准化产物摘要、决定、理由、review_ref | 保留为什么复用或新增；冲突不自动合并 |
| Segment / MappingManifest | segment_id、文本/顺序、原件位置、标准化版本、映射质量及摘要 | 对应固定版本，遵循T05码点与定位规则 |
| InformationDelivery | version_ref、consumer_id、message_id、delivery_status、processing_ref、receipt_ref | 保存状态与交付状态独立 |

版本主键由程序分配；并发判据同时包含资料身份、相关版本比较条件及有效产物，不能仅以raw_hash唯一。若源文回滚导致内容相同但业务上是新修订，仍保留不同版本及发生顺序证据。

版本决定与保存通过information身份记录的当前修订号协调：事务内核对expected_current_version与决定的比较依据，若已变化则退出并重新比较，不直接插入预先判断的新版本。同一有效决定持有固定version_commit_key，保存重试查询此键回原版本；来源提供修订号时同时保存其命名空间与原始值。来源未提供版本序号时不能仅靠内容哈希确定先后；无法区分晚到与真实回滚则待复核。

身份规范化规则升级不改变information_id；新旧标识经明确别名映射到同一稳定身份，规则版本仅用于解释判据。

## 2. 标准化资料交付契约

AcceptInformationVersion提供information_id、information_version_ref、source_id/source_config_ref、原件清单、标准化正文与字段、segment_manifest_ref、mapping_manifest_ref、completeness、保存回执及授权上下文。原文发布时间可空；资料类型与内容必须一致，正文和必要附件不能仅剩外部URL。

F02在受理前核对资料已保存、对象可读、版本与摘要匹配、支持的格式和授权。传输摘要只能验证内容一致性，不能代替信源准入。接收成功回执含processing_ref、接收时间和当前处理状态；拒收给出具体理由，F01保留交付待处理状态。

## 3. 版本决定矩阵

| 身份与内容比较 | 决定 | 可交付行为 |
| --- | --- | --- |
| 同来源、同强身份、同有效正文及标准化产物，且确认属于已有来源修订 | REUSE指定版本，追加获取记录；不更新当前指针 | 恢复该版本原交付；F02复用INITIAL处理；与历史版本同文时仍须排除真实来源回滚 |
| 同身份，仅广告或获取时间变化 | 在规则确认无有效变化后复用 | 不触发隐式重算 |
| 同身份且确认来源新修订，正文数字/条件/范围/有效附件改变 | 新来源修订 | 新版本交付，F02比较事件历史 |
| 基于当前版本原件，标准化规则修复改变有效产物 | 新处理修订 | 标明处理修复；不能伪装来源纠正 |
| 原件和产物相同，仅normalizer_version变更 | 记录新运行，不新增版本 | 无新业务处理 |
| 同文但来源不同 | 不同Information | F02判断来源增加/重复或新变化 |
| 标题相同但稳定来源标识不同 | 不因标题合并 | 分开保存 |
| 稳定ID/URL冲突、摘要规则不可比 | 待复核 | 不以不确定身份交付 |
| 已有相同记录但保存未完成 | 恢复原保存 | 完成后才可交付 |
| 已匹配已保存历史版本，且有依据确认晚到 | REUSE，reason=HISTORICAL_LATE；关联历史target_version_id | 当前指针和row_version不变，返回历史版本保存回执；仅恢复该版本原交付 |
| 已证实来源新发布一次回滚，内容与旧版本相同 | SOURCE_REVISION；保留新来源修订及其顺序证据 | 分配新版本并推进当前指针，不能直接把指针指回旧版本 |
| 同文但无法判断历史晚到还是新回滚，或晚到内容未匹配已保存版本 | 待复核；不自动选择REUSE或新当前修订 | 不更新当前指针；历史补录未定义时保持待处理，不伪装成当前修订 |

## 4. 状态与读取语义

资料处理状态建议为accepted、processing、review、recoverable、saved、rejected；delivery_status独立为pending、received、recoverable。saved只能由保存事务产生，received只能来自接收回执。rejected表示本次接入命令被拒，不删除以前已保存资料。

ReadInformationVersion返回固定清单；ResolveSourceLocation按证据定位获取原文段落/页区，不解析模型自由路径。若读取权限变化返回受控拒绝，若对象缺失返回证据不可用，两者不得混成空正文成功。

### 6.2 首切片标准化规则 normalizer-text-v1

仅接收UTF-8文本；保留输入原始字节为raw对象。解码失败直接拒绝，不替换乱码后继续。文本标准化仅移除起始UTF-8 BOM、将CRLF/CR统一为LF；不删除数字、标点、空格、脚注，不做Unicode兼容折叠、不摘要。首切片不识别HTML广告或复杂附件噪声，避免把有效正文误删；这些格式留给后续适配规则。

按换行分段并保留空行顺序，给每段分配segment_id和ordinal。mapping记录原件字节范围、原始行号、规范化段内码点与原始字符位置的对应；CRLF合并的两字节映射明确，不能把段内码点直接当文件字节。normalized_text与mapping一起冻结。

raw_digest是原始字节摘要；effective_digest对完整标准化正文及有效标题等字段求摘要；normalized_digest 另覆盖受控结构化字段、段文本/顺序及映射规则的语义版本；不包含随机 segment_id、artifact_id、对象路径、获取时间或模型运行编号。获取时间、运行ID等不进入有效内容比较。哈希相同还核对必要的长度与规范化判据，不以哈希相同自动合并不同资料身份。

### 6.3 Step 4/5的可执行事务协议

1. 事务外完成原件、标准化文本、映射和版本清单对象，记录artifact_objects=ready并取得摘要；查询storage.stat核对可读性和大小。
2. 对来源标识计算identity_digest，解析既有materials/aliases；唯一键冲突者读取既有行并逐字比较identity_value。没有可靠强身份且规则无法确认时转review。
3. 按权限代次 → material_operations → materials锁序，先查material_save_receipts中的version_commit_key；已提交则回原版本（即使当前指针已向后推进）。未提交才核对操作状态、执行/决定代次、有效复核及VersionDecision.expected_current_version_id；拒绝/review状态不得保存。已有复核绑定的版本冲突按第7章失效处理；无人工复核依赖则按原规则重新比较，不因普通并发强制人工批准。
4. 按第6.3.1节分支执行：REUSE验证target_version_id属于同一资料且为已保存可读版本，只关联获取记录；新增分支在materials锁内分配该资料max(version_no)+1，首次为1，写新版本、segments及parent关系。不能用target_version_id的版本号加1分配新修订。
5. NEW、经确认的新SOURCE_REVISION及基于当前版本的PROCESSING_REVISION才更新materials.current_version_id并使row_version加1；所有REUSE（包括HISTORICAL_LATE）均不更新这两个字段。各成功分支同事务写material_save_receipts，version_id指向本次新增或复用的结果版本，绑定操作saved_receipt_key并置saved；不是统一把结果版本设为当前版本。仅按第6.3.1节写入或复用交付记录后提交。跨系统对象不可读时事务前阻断；提交后损坏走证据修复，不覆盖原版本。
6. 中继按回执中的固定结果版本交付F02并持久接收回执；REUSE且已received直接回原接收结果，未received只恢复原消息，不因重新获取生成新message_id。

同一原件处理规则升级但有效产物不变时只记录新的获取/处理尝试，不产生资料版本。早到/晚到不能仅靠version_no推断业务时间：version_no表示本系统记录次序，来源修订时间单独保留。

### 6.3.1 保存分支与当前版本指针

本表是第3章业务判据在保存事务内的执行规则。expected_current_version_id是比较依据，target_version_id是REUSE结果，两者可以不同；例如expected=v3、target=v1表示在当前v3基础上确认复用历史v1。不能把“保存成功返回的版本”当成“当前版本”。

| 分支 | 新版本与父版本 | 当前指针及row_version | 回执与交付 |
| --- | --- | --- | --- |
| NEW首次保存 | 分配v1，parent为空；并发首次由资料身份唯一约束协调 | current=v1，row_version加1 | 回执指向v1，按固定版本建立交付意图 |
| SOURCE_REVISION新来源修订 | 锁内分配max+1，parent为经校验的当前版本 | 指向新版本，row_version加1 | 回执指向新修订，建立其交付意图 |
| PROCESSING_REVISION当前资料处理修复 | 必须基于当前资料版本的原件；产物有效变化才分配max+1，parent为当前版本 | 指向新版本，row_version加1 | 新修订标明处理修复，不伪装来源变化；历史版本原文不覆盖 |
| REUSE当前版本 | 不新增版本或segments，只增加获取关联 | current及row_version均不变 | 回执指向target=current，复用该版本交付记录 |
| REUSE历史版本，HISTORICAL_LATE | 不新增版本、parent或segments，关联已确认的历史target | current及row_version均不变，例如仍为v3 | 回执指向v1，已received回原结果；未完成则恢复v1原消息 |
| 已确认来源回滚到旧内容 | 仍走SOURCE_REVISION；例如分配v4，parent=v3，依据记录内容与v1相同 | current=v4；不将指针退回v1 | v4独立保存与交付，保留来源新修订发生顺序证据 |
| 无法确定顺序、历史版本处理修复或历史补录未定 | 不自动进入新增当前修订分支，转复核/待处理 | 不变 | 没有成功保存回执或新交付；历史修复须另行明确版本承载规则 |

REUSE须验证target与原比较依据匹配且复用版本及交付记录可追溯；不因哈希碰巧相同跨资料复用。若既有保存版本缺少应有交付行，按一致性异常恢复原交付依据，不临时造新消息掩盖缺失。SOURCE_REVISION与HISTORICAL_LATE的来源顺序证据及reason_code纳入basis_digest；仅发布时间或正文哈希不足时进入复核。

上述指针、版本、获取关联、保存回执及适用交付意图处于同一事务。中断时全部回滚；保存成功后回应丢失，仍先按原version_commit_key返回原回执，不因当前指针后来推进而改写回执或重新执行指针更新。

### 6.5 重复、历史晚到与来源回滚推演

| 输入/并发情况 | 比较和锁内处理 | 应保存的效果 |
| --- | --- | --- |
| 同来源强身份，相同正文，两次独立请求 | 两个 operation 可不同；取得同一 materials 行锁后核对有效摘要 | 一个资料版本，两条获取记录，同一个 INITIAL processing |
| 两请求同时提交同身份的新正文 | 第一个保存 v2；第二个发现 expected=v1 失效，重新比较 v2 | 第二个转 REUSE，不再生成 v3 |
| 保存 v2 成功后丢回应，此时别人已保存 v3 | 首先按旧 version_commit_key 查回执 | 返回 v2 的原保存结果，不误报冲突或重建版本 |
| 正文有效数字从10改为12 | 有效内容摘要变化；固定父版本和新证据映射 | 新资料版本，旧版本及旧事件引用可继续解析 |
| current=v3，已保存v1晚到且来源版本证据一致 | expected=v3、target=v1、REUSE/HISTORICAL_LATE | current及row_version不变；无v4，回执返回v1，复用v1交付 |
| current=v3，来源新修订确实恢复v1内容 | 固定来源新修订顺序，SOURCE_REVISION | 新增v4且parent=v3；current=v4，不退回v1 |
| 同文v1，但无法判断晚到还是新回滚 | 无可靠顺序依据，不以哈希裁决 | 保持review、current=v3；不新增版本或交付 |
| 晚到判断后别人已保存v4 | expected=v3失效；原决定重新比较，审批按第7章失效 | 重新确认复用v1时仍保持current=v4，不覆盖并发新修订 |

同一个模型请求或处理尝试不参与资料版本身份。资料比较规则、保存回执与幂等判据都由程序保存，AI 不参与 F01 的资料版本决策。

## 7. F01 复核与恢复契约

本章以接入operation_id为根身份。复核案件可早于information_id和version_decision_id存在；任何F01命令均不要求F02 processing_id/candidate_id，不写platform.review_decisions或F02提交回执。T02维护公开路由，本章维护字段含义、状态及事务规则。

### 7.1 操作、依据与复核对象

受理前保存完整不可变输入命令工件（含正文、来源声明及元数据）并核验可读；受理事务同时写command_receipts、material_operations及execution_intent，再返回202。command_artifact_id/input_digest提供崩溃恢复输入，摘要本身不能重建正文。工件保存成功但事务失败时按T05暂存规则回收，不产生已受理操作。

checkpoints按步骤记录input_digest、规则版本、输出工件及摘要、成功接纳代次；Step 2/3只有输入一致且工件重新验证可读才可复用。保存结果由专用回执判定，交付结果由material_deliveries判定，不能依靠checkpoint声称saved/received。

Step 4发生身份冲突或版本不可比时，程序固定复核依据工件：原操作及来源配置、原件/标准化产物摘要、身份规则、拟关联资料与比较版本、各资料expected_current_version_id/row_version、冲突原因、证据位置及可确认的resolution_plan。计划包含目标资料/版本、规范化身份、NEW/REUSE/SOURCE_REVISION/PROCESSING_REVISION动作、reason_code及来源顺序判据；expected_current_version_id与REUSE的target_version_id分开绑定；计划ID仅在该依据工件内有效。basis_digest覆盖完整依据与计划，案件绑定decision_generation；不是只有标题或一段人工理由。

复核动作：APPROVE_PLAN仅确认工件内指定resolution_ref；RECOMPARE要求以当前事实重新执行Step 4；REJECT_INTAKE拒绝本次接入且保留原件与历史。审批不能绕过来源资格、强身份唯一约束、缺失正文/映射或跨来源边界；没有可靠可执行计划时只能重新比较或拒绝。修改原始内容、source_id或固定规则不属于恢复，应建立有parent_operation_id的新受理操作；不在复核请求中任意改写历史资料。

### 7.1.1 完整接入请求的持久化定义

**保存位置。**完整已校验业务请求保存为ArtifactStore不可变工件，kind=intake-command，object_key为`l0/intake-command/{artifact_id}`。单机验证环境的设计落点是`/var/lib/riskhot/artifacts/l0/intake-command/{artifact_id}`，正文按UTF-8 JSON存储，媒体类型application/json；本轮不创建目录或文件。业务读取通过artifact_id授权解析，不能直接依赖进程内存、HTTP连接或临时上传目录。不可变发布及清理由T05维护。

**工件契约。**设计Schema标识为`f01-intake-command.v1-draft`，尚未发布。内容如下；字段由服务端严格校验或生成，客户端不能自报授权上下文。

| 字段 | 内容与来源 | 约束 |
| --- | --- | --- |
| schema_version / canonicalization_version / command_type | 上述工件Schema、canonical-json-v1、SubmitInformation | 固定解析版本；未知版本阻断恢复，不按latest猜测 |
| operation_id | 服务端预分配的原接入操作UUID | 必须与material_operations及接收回执身份一致；并发请求失败方的预分配ID不成为业务操作 |
| payload | source_id、source_identity{namespace,value}、content{text,media_type}、title、published_at、parent_operation_id | 覆盖T02该接口全部业务字段；可选缺省值规范为null，未知字段拒绝；完整正文不得截断或仅保存外部URL |
| context | 认证得到的actor_id、authorization_scope_ref、permission_epoch、source_config_ref及受理政策版本 | 仅为当时依据快照；执行时仍检查当前权限/资格，不能当成长期授权凭证 |
| payload_digest | 对canonical-json-v1(payload)的UTF-8字节计算SHA-256 | 同步写command_receipts.payload_digest和material_operations.input_digest；不含服务端时间、operation_id等运行字段 |
| text_sha256 | 对UTF-8(payload.content.text)字节计算SHA-256 | Step 2原件字节校验值；正文中的空格、换行、BOM及有效Unicode字符原样保留 |

artifact_objects.sha256是**整个工件文件字节**的摘要，byte_size是实际文件大小，与payload_digest、text_sha256各自独立。JSON键顺序或转义写法的不同不改变按T02规则计算的语义请求摘要；正文字符本身不做换行归一化、Unicode折叠或清洗，非法UTF-8/未配对代理字符在受理前拒绝。资料原件定义为content.text编码后的UTF-8字节；HTTP报文头、JSON缩进或转义形式不是资料正文。令牌、Cookie、Authorization头及连接凭据不得进入工件，日志仅记录身份与摘要。

**受理顺序。**

1. 认证、来源范围与严格Schema/大小检查后计算payload_digest；在当前权限下查询幂等键。同键同摘要已有回执则返回原operation；同键异摘要409，不替换旧工件。
2. 新命令预分配operation_id与artifact_id；完整工件按T05先登记staged、写入并持久发布，再校验大小/摘要与可读性，登记ready。工件写入或校验失败不受理、不返回202。
3. 单连接短事务内校验权限，锁定对应artifact_objects行并确认仍为ready，原子插入command_receipts、material_operations（绑定command_artifact_id、input_digest、source_config_ref）和初始execution_intent。校验工件内operation_id、来源与摘要一致；actor来自会话。三类业务记录任一失败则全部回滚，工件不因此冒充已受理操作。
4. 同一幂等键的并发请求以唯一约束决定胜者；失败方读取已提交回执，相同摘要回原operation，不把自己的工件挂到胜者操作，异摘要409。失败方未绑定工件按T05清理规则处理。
5. 只有数据库提交确认后才能返回202。提交成功但回应丢失时客户端用原键重试，返回原operation；数据库提交结果暂时未知时先按幂等键查询，不宣称受理成功、不另换业务身份。

**工作流恢复读取。**MaterialIngestionWorkflow只传operation_id/执行代次。IO Worker通过material_operations查command_artifact_id，再读取artifact_objects并授权获取字节；核对ready、文件大小、整工件sha256、Schema、工件内operation_id、payload_digest与操作/接收回执一致，重算text_sha256。检查通过后Step 2把content.text编码成原件raw工件，按同一text_sha256校验；Step 3才允许执行既定标准化规则。进程重启不得改变这份输入。

缺失、损坏、摘要不符或未知Schema返回INPUT_ARTIFACT_UNAVAILABLE或INPUT_ARTIFACT_INVALID，原操作保持recoverable且resume_step=2；不得把输入错误转为空正文成功。修复须恢复同一内容及摘要，不能让模型、客户端新请求或最新来源页面覆盖已受理输入；确需替换时走新操作及父关联。已保存资料的后续恢复优先读取原保存回执，不为重放已完成结果重新生成请求工件。

### 7.2 复核受理、失效与保存门槛

1. API验证当前information_review权限及来源范围，取得权限代次共享锁，再锁material_operations及复核案件；涉及现有资料按UUID排序锁materials。核对操作处于review、case属于该操作、expected_execution_generation/decision_generation/basis_digest均匹配，并重新核对比较版本、规则和可读工件。外部读取与工件准备在事务外，锁内只校验已冻结引用及当前资格。
2. 在同一事务写F01复核决定、审计与命令回执，案件置resolved。APPROVE_PLAN使execution_generation加1，保留decision_generation并生成Step 4启动意图；RECOMPARE使两类代次加1，失效旧决定/案件并生成Step 4启动意图；两者操作置processing、resume_step=4。REJECT_INTAKE则操作置rejected、执行代次加1、resume_step=NULL，不创建启动或交付意图。事务成功才返回受理或拒绝结果。
3. IO Worker在Step 4核对有效决定，将批准计划转换为固定VersionDecision，并在Step 5按第6.3节保存；批准不等于已经保存。保存时再次检查当前权限、来源资格、操作代次、basis_digest及expected_current_version_id。新资料身份在保存事务内通过唯一约束分配，不能因为复核时尚不存在就绕过并发冲突。
4. 复核前或批准后发现比较版本/有效依据改变，返回REVIEW_BASIS_STALE；保留旧案件和审批作为历史，decision_generation与execution_generation各推进一次，清除当前有效决定，操作回review、resume_step=4，同事务写新执行代次的Step 4启动意图，仅用于准备案件。review_required保持true，程序重新比较并形成新依据案件后再申请复核，不能将旧审批换绑到新版本。缺少新依据时GET显示待准备，不允许批准；技术读取故障保持可恢复原因。原失效代次与原因写审计，旧命令重放不再次推进代次。
5. 审批、拒绝、恢复和保存共用operation锁。保存先完成，则新的拒绝或改判命令返回OPERATION_ALREADY_SAVED；拒绝或代次变更先完成，则旧保存Activity不得提交。撤权后未保存的批准不能继续消费。saved/rejected不由processing恢复接口重新打开；已保存版本的修正使用新操作和新版本。

同一案件只能有一个最终复核决定；相同Idempotency-Key同体回原命令回执，异体409；不同键对已resolved案件返回REVIEW_ALREADY_DECIDED并提供有权读取的原决定引用。通过新案件/代次重新决定，不覆盖旧理由。所有命令先鉴权再返回幂等结果。

### 7.3 原操作恢复与续接位置

恢复命令携带expected_execution_generation、reason和scope=processing；服务器从检查点选择续接位置，客户端不能指定任意步骤或直接改状态。在权限与operation锁内先查保存回执：已saved返回原保存结果；rejected拒绝恢复；processing返回OPERATION_RUNNING；review且无有效批准返回REVIEW_REQUIRED。只有recoverable或有效批准但执行中断的操作可续接；同事务增加execution_generation、保存恢复原因/前后代次及命令回执、写确定workflow_id启动意图。decision_generation及version_commit_key在事实与规则未变的技术恢复中保持不变。

| 失败位置 | 服务端确定的续接 | 前提及禁止行为 |
| --- | --- | --- |
| 原件未完整获取 | Step 2 | 从command_artifact读取原输入；输入工件缺失则阻断并修复，不能要求后台猜正文 |
| 原件已保存，正文/映射未完成 | Step 3 | 复用校验通过的原件和原标准化规则；不能静默升级规则 |
| 身份/版本待定 | Step 4 | 必须先有本案件有效复核，或由RECOMPARE生成新依据；普通retry不能自动批准 |
| 保存失败或结果未知 | 先查保存回执，未提交才Step 5 | 原决定、审批与预期版本有效则沿用version_commit_key；依据变化回Step 4，禁止随机换键新增版本 |
| 已保存，仅交付失败 | 独立scope=delivery，续接Step 6 | 固定version_id/consumer_id/message_id；不重新获取、标准化或生成版本 |

Activity接纳结果和保存均核对当前执行代次；旧执行仅留尝试记录，不能覆盖检查点。技术恢复不隐式改变业务事实、批准内容或F02首次处理身份；F02分析失败也不触发F01恢复。

### 7.4 交付恢复、查询与重试预算

scope=delivery携带version_id、consumer_id、expected_delivery_generation及reason。服务器核对该版本确属该操作保存回执；按权限 → operation → material_deliveries → platform.message_deliveries锁序操作。已received返回原接收回执；仍在有效租约投递中返回DELIVERY_RUNNING；pending到期由Relay自行领取，人工恢复只针对recoverable。成功受理使recovery_generation加1、记录审计/命令回执，保留原message_id，撤销旧lease_token并将原投递行重新置pending及next_attempt_at。

F01消息的Relay租约领取、失败及接收回执确认也先锁material_deliveries，再锁platform.message_deliveries，同事务同步两表状态；不得持平台投递锁反向取F01交付锁。它们不修改已saved操作，也不反向申请operation锁。窗口检查与attempts预留在该锁内完成。

授权交付恢复开启一个新的有界投递窗口：window_start_attempts记录当时累计attempts，窗口上限沿用固定T03投递政策（首切片10次）；累计attempts不清零，Relay按attempts-window_start_attempts限制本窗口。预算、操作者及恢复原因必须可追溯，不能靠普通技术重投自动开启新窗口。旧租约迟到确认不得覆盖新窗口，接收端Inbox仍按原消息去重。

GET F01操作返回state、execution_generation、decision_generation、resume_step、失败原因、有效检查点、active_review_case及basis_digest、固定版本/保存回执、逐consumer交付状态和recovery_generation。尚未建立的information_id/version_decision_id/F02 processing_id返回null，不制造占位UUID。案件查询提供授权范围内的比较依据、可选计划、决定及历史失效原因；资料正文仍按原件权限读取。复核、恢复及交付重试的command_receipts.result_ref均关联原接入operation_id和实际结果，不能把控制命令的新回执ID当成新的资料接入。
