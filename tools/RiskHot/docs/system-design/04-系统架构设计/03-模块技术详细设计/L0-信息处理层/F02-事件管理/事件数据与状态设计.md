# F02 事件数据与状态设计

> V1.1 · 2026-10-31 · 同步 fact_material 与 Fact 直接事件归属的目标设计，相关读写、事务及迁移尚待实施。此前 V1.0 的 Fact/Event 核心实现及 schema4 验证见[[tools/RiskHot/docs/verification/fact-model|实施验收]]，不覆盖本次结构调整。

## 1. 文档分工

本文件只定义执行状态、事务、并发、查询和恢复。具体表结构移至[[tools/RiskHot/docs/system-design/04-系统架构设计/01-数据模型与存储设计/F02事件管理模块数据模型与存储设计|F02 数据模型与存储设计]]，不再在此维护第二套字段表。业务规则见[[tools/RiskHot/docs/system-design/03-系统功能架构/F02 事件管理模块功能设计 V1.0|F02 功能设计]]。

取消 EventUpdate 作为更新历史实体，采用 Fact 候选。取消 EventRevision 及事件修订引用；F01 资料版本、定义版本、模型方法版本和审计保留。

## 2. 受理、候选与运行关联

按 F01 确定资料版本及分析操作固定输入。普通重投复用原处理，授权重算创建新的运行记录但仍进行业务去重。

AI-01 校验成功后，原子保存或明确复用 Fact、fact_material、fact_evidence，并将当前运行输出项与 Fact 连接。多个处理可引用同一 Fact；Fact 不嵌入 processing_id 或单一 material_id，当前 Event 归属由可空 event_id 及归属说明字段承载。新 Fact 归属字段全空，复用 Fact 不清除已有归属。模型返回临时序号只在该次输出中有效，不能当作全局 Fact 身份。

运行记录保存执行代次、建议、预算、恢复点、复核决定和回执。原 candidate 运行身份可作为迁移连接的兼容身份，但不能再拥有独立于 Fact 的第二份业务事实真值。

## 3. 状态与合法空结果

| 对象 | 状态或含义 | 边界 |
| --- | --- | --- |
| 资料处理 | pending / processing / partial / review / recoverable / completed | 抽取未完成时数量未知；正常零候选才能记0 |
| Fact 处理分支 | pending / processing / review / recoverable / completed / dismissed | 放在运行记录，通过关系关联 Fact；不混入 event_status |
| 当前步骤 | pending / succeeded / skipped / review / recoverable / superseded | 跳过须有业务原因 |
| Event | expected / announced / in_progress / effective / completed / cancelled / unknown | 业务阶段，独立于模型与任务运行 |
| 交付 | pending / received / recoverable，另记应用状态 | 接收成功不代表已应用或下游分析完成 |

### 3.1 授权确认非事件与正常结束

对非事件候选保存明确处置理由、依据摘要、授权主体和审计，将相应处理分支置 dismissed；Fact 与原文证据仍保留；未归组 Fact 保持 event_id 为空，不产生 Event。已有正式归属不得由该处理分支直接清空，须另走受控维护。模型失败不能走本分支。

### 3.2 关系变化与恢复

同一 Fact 的当前事件归属由 fact.event_id 单值表达，普通提交必须锁定并检查旧归属，防止并发覆盖；依赖关系以 (event_id, fact_id) 复合引用 fact(event_id,id)。修改归属必须失效依赖旧归属的关系、增量、评级建议及批准。已有正式归属的调整属于受控维护，不能由普通重试静默改挂。

## 4. 建议和复核依据

建议固定本次 Fact、资料证据、目标 Event 当前内容、已关联 Fact、主体/变量关系、方法版本、检索范围及摘要。身份与正式提交批准分别绑定当前建议；定义缺口的批准只允许按明确限制继续，不能代替最终保存。

批准时上下文与提交时不一致，回到受影响步骤重新比较。旧 event_id + expected_revision 改为事件身份 + 批准时内容摘要；摘要属于运行上下文，不是 Event 新增业务字段。

## 5. 七类判定与实际效果

Fact 在抽取接纳时已保存，不因 Step 4 判定 NEW_EVENT、PROGRESS 或 CORRECTION 再复制一份。七类结果控制 Event 当前事实及关系的变更，不恢复 event_updates。

- 新事件：创建 Event 并关联 Fact。
- 进展、补充、纠正：建立或核对 Fact 归属，应用经过复核的具体字段变化。
- 来源增加：复用 Fact 并补资料/证据，或关联经确认的佐证 Fact。
- 纯重复：返回已有结果；无重复写入或通知。
- 待定：保留候选和复核状态，不正式保存 Event 变化。

当前字段更新须覆盖标题和描述等实际被纠正的内容，不能只更新阶段与时间。部分日期、未来计划和未知时间按数据模型统一解释。

## 6. 数据访问与所有权

表结构唯一来源为[[tools/RiskHot/docs/system-design/04-系统架构设计/01-数据模型与存储设计/F02事件管理模块数据模型与存储设计|F02 数据模型与存储设计]]。API 提交复核和查询；业务 Worker 执行受控正式保存；模型只产生建议；交付进程只读已提交内容并维护回执。

Fact 证据固定 F01 原文版本；涉及多份资料时逐份验证读取资格。Event 的读取和修改范围由 fact.event_id → fact_material → material 推导，不能只检查触发当前操作的一份资料。关系证据必须来自本 Event 已归属 Fact。

## 7. 正式提交事务

目标固定锁序：权限协调 → 运行记录 → 共享事件集合协调 → 受影响 Event（按稳定身份排序）→ Fact（按稳定身份排序）。锁定后重查 Fact 旧归属；若涉及未锁定的其他 Event，回滚后按完整集合重新获取锁，不在已有 Fact 锁后追加 Event 锁。新建 Event 在同一事务内创建并关联 Fact。模型、原件抓取和人工等待在事务外。

1. 检查同一操作是否已有回执；已有则返回原结果。
2. 校验执行代次、完整步骤、当前权限和有效复核。
3. NEW 检查召回完整性及集合上下文；REUSE 锁定 Event，重算当前内容与关系摘要。
4. 核对 Fact 与资料证据、定义版本、fact.event_id 旧归属、评价和字段变更；普通重试不改挂，受控调整须同时处理依赖及最后一条 Fact 约束。
5. 原子写入 Event 当前事实、Fact 当前归属四字段、其他关联、适用评价、审计、提交回执、处理完成与交付意图；提交时检查归属完整性及事件内事实依据。
6. 有业务变化时更新共享协调状态；无变化不刷新 Event 或生成重复通知。
7. 事务成功后才发布交付工件。失败按原操作恢复，不换身份掩盖冲突。

### 7.1 两候选更新同一事件

两项建议均基于内容摘要 A。第一项提交后，第二项在锁内发现内容或关系摘要变化，必须重新比较、核定并复核；不能直接替换为新摘要。内容摘要必须包括关系与事实依据，不仅包括 title。

### 7.2 不同候选并发新建的集合校验

共享协调记录保存事件集合变化标记；召回在短读事务固定标记及完整清单。正式创建在集合锁内再次检查，变化则回到身份核对。它是运行并发控制，不是按 Event 保存版本历史。

该机制防止沿用过期 NEW 批准，不保证语义检索永不漏判。检索截断、错误或覆盖不足不得返回可自动建档的“空集合”。

## 8. 交付、查询与恢复

新交付以提交身份和 message_id 固定已提交内容，包含当前 Event、采用的 Fact、资料证据、关系与评价。数据库保存交付意图和内容摘要，文件异步落盘；发布失败可按原固定内容恢复，不再次读取最新 Event 生成旧消息。

无 revision_no 时仍需顺序控制：共享交付记录通过前序消息依赖关系表达同事件先后顺序，消费者先接收、再按依赖应用；缺前序则待应用并恢复前序。同消息重投复用回执，收到旧消息不覆盖新结果。本机采用 v2 固定消息和前序依赖协议；旧修订消息已冻结归档，不交给新接收端解释。

事件查询读取当前 Event 与关系；Fact 查询读取候选、原文证据与运行状态；审计查询显示授权变更。删除事件历史版本入口，不提供隐式的 EventRevision 兼容视图冒充新模型。

### 8.1 正式事件时间线查询契约

> 本节保留历史已验证的查询契约与实现说明；其中 EventFact/FactInformation 和资料版本表链路不代表当前目标结构。V1.10 改造须沿 fact.event_id → fact_material → material 读取来源，并对齐 F01 当前资料版本字段；展示时间与权限规则需重新验证，不能沿用历史测试宣称新查询已完成。

`GET /api/v1/l0/events?cursor=0&limit=20` 保持 `items / next_cursor` 外层及已有 Event 字段；cursor 为非负安全整数偏移，limit 为1～100，默认20。`event_time` 保持业务发生时间，列表展示时间为派生字段，不写回 Event，无数据库迁移。

| 派生字段 | 内容与约束 |
| --- | --- |
| display_time / display_time_precision | ISO瞬间，或保留日/月/年的原精度值，或null；precision为instant/day/month/year/unknown |
| display_time_basis / display_time_reason | first_collected / published / unknown及中文依据；异常降级不宣称满足72小时 |
| first_collected_at | 依据版本的首次成功收录ISO瞬间，缺证据则null |
| published_at / published_at_text / published_at_precision | 可解析的原文时间、原始文本与精度；无法解析保留原文文本 |
| time_material_id / time_version_id / time_source_id | 同一依据原文及其证据版本、信源身份，无依据则null |
| sources | 仅返回id、catalog_key、name；按ID去重，时间依据信源优先 |

一次批量查询联结 EventFact → FactInformation → FactEvidence → MaterialVersions，并校验 MaterialVersionOrigins 与 Acquisition 的原文工件、首次时间及采集操作身份一致。只有具有本事件实际证据的版本可参与；同篇更早但无该事件证据的版本不贡献 C，禁止从旧版本借 C 与新版本 P 配对。重复证据及多Fact不增加事件条数。选最早成功收录的依据版本，同刻依次按资料ID、版本ID；均缺C时优先选可解析P的原文，再按资料/版本身份稳定选择。来源按最早建立关联的时间及ID排序。

发布时间解析只接受合法的 `YYYY`、`YYYY-MM`、`YYYY-MM-DD` 或带明确Z/数值时区的ISO完整时刻；无时区完整文本不假定本机时区。部分日历值按上海日历范围计算，上界可依据成功收录约束收紧至C，仅内部范围起点参与排序，不对外假造完整时刻。0～72小时采用C，超过72小时采用P；跨阈值、缺失、无效和负延迟用C并给原因；无C可用P，两项皆无稳定置后。完整日期组在前；月/年在其后按范围起点倒序、原值及ID稳定排序，各原值独立分组；未知时间最后。日精度显示“时刻未明确”。

权限在批量读取时执行与详情相同的整事件规则：任何关联来源无权即排除事件，不泄露隐藏来源名称或数量。所有可见事件先计算展示时间并全局排序，再分页；同展示时间以Event ID稳定排序。没有逐事件详情查询、原文工件读取或N+1。

应用层时间成本为 O(E + Σ(Ve×logVe) + N×logN + Σ页内(Ee×logEe + Se×logSe))：N为可见事件数，E为批量证据行总数，Ve为每事件去重后版本数，Ee为该事件证据行数，Se为去重信源数。包括全量证据整理、每事件依据版本排序、全局事件排序以及当前页证据/来源排序；空间为O(E+N)。数据库联结与jsonb去重聚合的执行计划和成本需另行评估。单进程需承载全部可见时间依据；只验证了本机当前单事件与25条受控多日事件，不宣称适用于大规模生产数据。扩大规模前应实测执行计划与内存，按需要设计规范化日期/读模型及回填；本期不引入该迁移。偏移分页不保证并发新增/纠正下的快照一致性。实际验证见[[tools/RiskHot/docs/verification/event-timeline|时间线验证记录]]。

## 9. 迁移与验证边界

迁移步骤及验收场景统一见数据模型第9章。需要特别验证：一资料多 Fact、一 Fact 多资料、唯一 Event 归属、纠正当前数字、多来源权限、批准过期、重复提交、原文版本完整、乱序与丢失回执。

现行 src 及运行库已经采用 Fact/Event 模型，但本次来源表改名、Fact 归属字段和锁序调整尚未实施；不删除现行表、旧交付文件或既有验收证据。代码和数据库切换须配套，旧名称不能先于读写适配退出。
