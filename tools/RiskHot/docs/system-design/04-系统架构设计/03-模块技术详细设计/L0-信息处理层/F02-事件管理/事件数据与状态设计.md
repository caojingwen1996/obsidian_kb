## 1. 处理与候选

| 记录 | 核心字段/约束 | 作用 |
| --- | --- | --- |
| f02_processing_result | processing_id；唯一information_id + version_ref + analysis_key；parent_processing_id、method_manifest_ref、extraction_status、candidate_count、result_status | 同版普通提交固定INITIAL；数量在完整抽取前为空 |
| event_candidate | candidate_id；唯一processing_id + candidate_key；payload、evidence、matching_candidates、EventContextRef、increment_type、status、resume_step、review_ref、saved_result_refs | 独立恢复与提交；正式event_id新建前为空 |
| TaskProposal | proposal_ref、candidate/processing_ref、task_id、input_digest、manifest_ref、generation、output_ref、validation_ref | 保存有效建议和被替代建议，禁止旧结果覆盖 |
| ReviewDecision | decision_id、actor、policy_version、proposal_digest、context_refs、decision、reason、time | 必须能证明批准的是哪一组内容 |
| CommitReceipt | commit_key、candidate_id、generation、effect_refs、revision_ref、result_kind | 回应丢失后可证明已提交；纯重复也有无变化回执 |

candidate_key在完整抽取结果被接纳时由程序分配，集合与键原子固定。失败尝试的序号、文本哈希不跨尝试直接当身份。固定后技术恢复只用现有候选；要改变集合必须授权重算，不能一边固定旧集合一边追加迟到模型输出。

## 2. 正式聚合与约束

| 记录 | 关键约束 |
| --- | --- |
| Event | event_id程序生成；不以标题或Subject+Action+Time强制唯一；新建至少一项来源及证据 |
| EventInformation | 唯一event_id + information_id；多个资料版本证据分别保留，不把关系重复计数 |
| EventEvidence | 固定information_version_ref、原文定位、证据角色、artifact digest；必须属于关联事件/资料 |
| EventTarget | 唯一event_id + target_id；引用固定正式Target版本及证据 |
| EventTargetVariable | 唯一event_id + target_id + variable_id；对应同事件EventTarget，引用正式Variable版本和事件资料 |
| EventUpdate | 唯一event_id + business_change_key；时间、状态、证据、supersedes引用可追溯；来源增加/重复不造更新 |
| EventRating | 唯一event_id + assessment_key；scope、horizon、method、basis_revision_no、证据、draft/confirmed/rerate、M可空 |
| EventRevision | 唯一event_id + revision_no及event_id + commit_key；冻结事件与关系版本、更新/评级/证据引用 |

引用应同时保证同事件归属和真实存在，不能只检查一个UUID形状。operation_ref可关联多个事件修订，不能设为唯一。Target/Variable定义候选另存，不填写伪造正式ID。

business_change_key在身份归组、历史比较后核定：同一实际变化的多来源复用，一份资料中的两项独立变化使用不同键；不能简单用资料ID+分类。assessment_key固定一次评价操作及范围/期限/方法/依据；技术重试复用，授权复评另建。M未知用空值，不以0冒充未知；不同范围或期限不覆盖旧评级。

## 3. 状态转移

| 对象 | 转移 | 触发条件 |
| --- | --- | --- |
| 抽取 | pending → completed | 完整结果通过结构/覆盖检查并固定集合，count为0或正整数 |
| 抽取 | pending → recoverable → pending | 模型/解析/覆盖失败；count仍为空；按原处理身份恢复 |
| 候选 | pending → processing | 领取有效代次并准备当前步骤 |
| 候选 | processing → review / recoverable | 业务不确定 / 技术失败，写reason与resume_step |
| 候选 | review / recoverable → processing | 授权决定或恢复命令；必要时使下游建议失效 |
| 候选 | processing → completed | 正式提交成功或确认无变化，必须有CommitReceipt |
| 候选 | review → dismissed | 授权确认非事件且处置事务完成，有result_kind=NOT_EVENT的CommitReceipt；不是删除候选 |
| 交付 | pending → received 或 recoverable | 接收回执 / 重试预算耗尽；不反向改变已完成业务 |

资料汇总优先顺序：抽取未完成时按其pending/processing/recoverable表达；抽取完成且count=0为completed；固定集合内全部候选为completed或dismissed时批次为completed；部分候选已进入这两类终态且仍有未处置项时为partial；没有终态项时按review优先于recoverable，再按processing/pending表达。completed_count只计completed，dismissed_count只计dismissed，resolved_count为两者之和，pending_count=candidate_count-resolved_count。抽取未完成时上述候选计数均为空，不以0表示成功。汇总与候选终态变化同事务更新，查询必须对完整固定集合统计，不能只统计当前分页。

取消是运行控制及提交栅栏，不能自动变completed或dismissed。确认非事件按第3.1节处置；候选集合人工增删仍未定版，不以删除候选改变candidate_count。已经completed或dismissed的候选不由普通重试重新打开；误判须授权新处理并关联父处理，保留原决定与回执。

### 3.1 授权确认非事件与正常结束

**适用条件。**候选已由Step 1固定，但授权复核者根据候选内容和固定资料证据，明确确认其不构成具体事件。理由必须非空、可审计；不能把模型故障、证据不可读、身份待定、处理超时、取消或“暂不关注”当作非事件。与已有事件重复应走REUSE/NO_CHANGE，不能用本处置跳过归组。首切片只允许人工授权确认，模型无权生成有效否决决定。

**复核入口。**GET Candidate返回程序计算的disposition_basis_digest，覆盖candidate_id、proposal_generation、固定候选内容摘要、资料版本及证据引用摘要。复核者通过T02的reviews接口提交scope=disposition、decision=CONFIRM_NOT_EVENT、proposal_generation、proposal_digest=该依据摘要及reason。API按权限 → processing → candidate锁序检查candidate_disposition权限、来源范围、未取消、代次及摘要；仅未终态候选可以受理。持久写scope=disposition的ReviewDecision、审计记录和复核唤醒意图，并将候选置review。此时只是待执行的业务决定，202不表示已经dismissed。

有效的非事件决定一旦受理，普通模型结果接纳、原身份/最终审批及commitCandidate均不得再推进该候选；程序必须在同一候选锁内检查当前代次是否存在该决定，返回DISPOSITION_PENDING。原任务结果保留供审计，不能用稍后到达的普通审批覆盖非事件决定。未终结前如该决定失效或需改判，须按既有授权重新准备流程增加proposal_generation，使原决定及下游审批失效，不能删除决定或直接重用旧批准。

**处置事务。**由IO Worker执行独立的候选处置分支，复核唤醒和数据库对账都能触发；不要求AI-02～05成功，也不进入正常Step 6的事件保存门槛。候选Workflow已终止时，按T03授权恢复规则建立原候选的新执行代次及启动意图，保留proposal_generation和有效非事件决定；新执行先处理该决定，不重跑模型。取消未解除或权限失效时不得借恢复绕过检查。

| 顺序 | 程序与数据库动作 | 拒绝或恢复语义 |
| --- | --- | --- |
| 1 | 取得T06权限代次共享锁，再锁processing和candidate；读取终态及回执 | dismissed直接回原NOT_EVENT回执；completed返回CANDIDATE_ALREADY_COMMITTED，不能撤销正式事件 |
| 2 | 重新检查复核者当前candidate_disposition权限、资料范围、取消/执行代次、当前proposal_generation、依据摘要及有效ReviewDecision | 撤权、取消、过期或证据不可核验均保持未处置，不自动补默认理由或终态 |
| 3 | 固定当前候选/决策代次的commit_key；写CommitReceipt(result_kind=NOT_EVENT, effects=[], review_decision_id)及审计记录 | 复用已固定的同代次提交身份；同候选终态受行锁保护，不能产生两种完成结果 |
| 4 | 候选置dismissed、resume_step=NULL，execution_generation加1阻断迟到执行；Step 2～5结果标为superseded；同事务更新批次汇总 | 保留候选、原文、建议与复核历史；事务失败全部回滚，使用原决定与提交身份恢复 |

处置不创建或修改Event、来源/证据关系、EventUpdate、EventRating、EventRevision，不消费NEW身份决定，不推进catalog_epoch，也不创建事件变化Outbox或交付行。审计记录和处理回执不是事件变化通知。NOT_EVENT回执中的event/revision引用为空，通过review_decision_id、候选、固定资料版本及证据追溯理由。

**并发与恢复。**非事件复核与正式提交使用同一candidate锁：正式提交先完成，则拒绝非事件处置；非事件决定先受理，则阻断普通提交，等待处置。取消先完成则处置不生效；处置先完成则取消/重试只能保留该终态。回应丢失先查回执；模型迟到、重复唤醒、不同请求键重复确认同一候选均不得新增处置效果或重新打开候选。仅幂等返回原回执不改写原理由；修改理由需要单独审计，不能覆盖既有回执。

**批次例子。**两个候选中一个completed、一个dismissed，则resolved_count=2、pending_count=0，批次completed；两个都dismissed也正常结束，candidate_count仍为2、dismissed_count为2。它与AI-01完整抽取出0候选的无事件结果可以明确区分。非事件候选不参与交付；若批次完全没有事件变化消息，delivery_status=not_required，不伪造received；混合批次仍独立展示已提交事件的真实交付状态。

## 4. 乐观并发与正式提交

事务读取候选代次与取消状态，检查commit_key；命中返回既有结果。复用事件时检查expected_revision，冲突则退出事务重新准备相关上下文、建议与审批；不覆盖较新历史。新事件还须在事件集合锁内验证召回快照未过期，通过后消费已确认身份决策并分配event_id，关系中的candidate引用在本次提交中解析为该真实身份。不同候选并发NEW的处理见第7.2节。

同一事件不同候选即使来自同一资料也独立比较，第二个提交必须基于第一个提交后的修订重检去重及评级依据。跨资料语义同一性不由唯一约束凭空证明，归组不明时复核。

正式事件、适用关系、证据、修订、处理回执与Outbox一个事务；模型和对象准备在事务外。纯重复无业务修改只完成处理记录，不新增EventRevision。Outbox按实际变化生成，复投使用原message_id。

## 5. 审计与历史查询

每个正式结果能反查：CommitReceipt → 有效建议/校验/审批 → 输入与方法包 → 固定资料版本 → 原文。EventRevision冻结当时对象与引用，不能查询到今天的字典或资料“最新”替代历史。若证据权限被撤销或对象故障，明确显示受限/不可用并保留历史引用，不能伪装成没有引用。

状态和约束的执行证据要求见[契约验证](../../../05-%E6%9E%B6%E6%9E%84%E6%B2%BB%E7%90%86%E4%B8%8E%E9%AA%8C%E8%AF%81/%E6%9E%B6%E6%9E%84%E9%AA%8C%E8%AF%81/%E5%A5%91%E7%BA%A6%E4%B8%8E%E9%9B%86%E6%88%90%E6%B5%8B%E8%AF%95/L0%E5%A5%91%E7%BA%A6%E4%B8%8E%E9%9B%86%E6%88%90%E9%AA%8C%E8%AF%81%E8%AE%BE%E8%AE%A1.md)及[故障恢复验证](../../../05-%E6%9E%B6%E6%9E%84%E6%B2%BB%E7%90%86%E4%B8%8E%E9%AA%8C%E8%AF%81/%E6%9E%B6%E6%9E%84%E9%AA%8C%E8%AF%81/%E6%95%85%E9%9A%9C%E6%81%A2%E5%A4%8D%E9%AA%8C%E8%AF%81/L0%E6%95%85%E9%9A%9C%E6%B3%A8%E5%85%A5%E4%B8%8E%E6%81%A2%E5%A4%8D%E9%AA%8C%E8%AF%81%E8%AE%BE%E8%AE%A1.md)。

## 6. 正式事件聚合的物理表

以下表均位于`information` schema；中间处理表见[T01 §6～7](../../../02-%E4%B8%93%E9%A2%98%E6%8A%80%E6%9C%AF%E6%9E%B6%E6%9E%84/T01-%E6%95%B0%E6%8D%AE%E4%B8%8E%E5%AD%98%E5%82%A8%E6%9E%B6%E6%9E%84.md)。列名映射：功能文档information_id对应materials.id，information_version_ref对应material_versions.id；event_id对应events.id。正式业务ID不得指向event_candidates。

| 表 | 关键列与类型 | 物理约束 |
| --- | --- | --- |
| events | id uuid、title text、description text、subject_name text、action_code text?、event_status text、event_time timestamptz?、event_time_precision text、event_time_text text?、event_time_kind text、event_time_start timestamptz?、event_time_end timestamptz?、revision_no bigint | PK id；revision_no正整数；不按标题设唯一；(updated_at,id)查询索引 |
| event_sources | event_id uuid、information_id uuid、role text | PK(event_id,information_id)，分别FK事件/资料 |
| event_evidence | id uuid、event_id uuid、information_id uuid、version_id uuid、segment_id uuid、start_cp int、end_cp int、quote text、role text | FK(event_id,information_id)→event_sources；FK(information_id,version_id)→版本；FK(version_id,segment_id)→分段；CHECK 0≤start_cp<end_cp |
| definition_snapshots | id uuid、kind text、definition_id uuid、definition_version text、payload jsonb、digest bytea | UNIQUE(kind,definition_id,definition_version)；由M2读取快照，非模型创建正式定义 |
| event_targets | event_id uuid、target_id uuid、definition_snapshot_id uuid、relation_note text | PK(event_id,target_id)；快照类型/ID由程序检查 |
| event_target_variables | event_id uuid、target_id uuid、variable_id uuid、definition_snapshot_id uuid、relation_type text、change_direction text、impact_status text | PK(event_id,target_id,variable_id)；FK(event_id,target_id)→event_targets |
| event_updates | id uuid、event_id uuid、business_change_key uuid、update_type text、summary text、previous_status text?、current_status text?、effective_at timestamptz?、recorded_at timestamptz | UNIQUE(event_id,business_change_key)、UNIQUE(event_id,id) |
| event_update_supersedes | event_id uuid、update_id uuid、superseded_update_id uuid | PK三列；两组(event_id,update_id)复合FK；CHECK新旧ID不同；程序验证无环 |
| event_ratings | id uuid、event_id uuid、assessment_key uuid、scope_key text、assessment_scope jsonb、research_horizon jsonb、method_version text、m numeric(5,2)?、dimension_scores jsonb、financial_usages jsonb、reasoning_summary text、rating_status text、basis_revision_no bigint、supersedes_rating_id uuid? | UNIQUE(event_id,assessment_key)、UNIQUE(event_id,id)；m为空或0～100；FK(event_id,supersedes_rating_id)→event_ratings(event_id,id)，程序检查非自指与无环 |
| event_revisions | id uuid、event_id uuid、revision_no bigint、commit_key uuid、snapshot jsonb、snapshot_digest bytea | UNIQUE(event_id,revision_no)、UNIQUE(event_id,commit_key)；不可变；时间查询索引(event_id,created_at,revision_no) |
| event_identity_catalog | scope_key text、catalog_epoch bigint | PK scope_key；首切片单行scope_key=l0-event-catalog、初始epoch=0；epoch非负且只在正式事件变更事务中递增 |
| event_identity_snapshots | id uuid、candidate_id uuid、generation bigint、scope_key text、catalog_epoch bigint、retrieval_policy_ref text、authorization_scope_digest bytea、permission_epoch bigint、manifest_artifact_id uuid、manifest_digest bytea、retrieval_truncated boolean、coverage_status text | PK id；UNIQUE(candidate_id,generation,id)；FK candidate及catalog；不可变，manifest保存查询条件、召回时间、event_id与revision列表及覆盖依据 |

identity_decisions以(candidate_id,generation,retrieval_snapshot_id)复合引用event_identity_snapshots(candidate_id,generation,id)，防止跨候选或跨代次借用检索记录。快照是程序维护的上下文，不由模型自报版本。首切片集合行必须预先建立，缺失时拒绝新建，不临时视作epoch=0。

events以(id,revision_no)、event_ratings以(event_id,basis_revision_no)引用event_revisions(event_id,revision_no)；初始事件/评级与修订在同事务创建，外键延迟至提交时检查。精确时间仅在时区明确时写timestamptz；月/年/未知时间保留原文和精度，不填造精确时间。

关系、更新和评级证据用专用连接表`event_target_evidence`、`event_variable_evidence`、`event_update_evidence`、`event_rating_evidence`；每表带event_id及对应实体复合键和evidence_id。event_evidence增加UNIQUE(event_id,id)，连接表同时FK到同事件实体和同事件证据，阻断跨事件串引。事件本体证据直接查询event_evidence。

跨表字符长度和语义支持不能用单表CHECK完成：程序在事务前解析quote与segment文本，提交事务重新核对不可变版本摘要、同事件归属及读取资格。EventRevision保存关系/字典版本和证据引用的完整快照，避免当前关系行变更后历史查询漂移。

## 7. commitCandidate事务步骤与并发结果

使用一个数据库连接和一个事务；READ COMMITTED下按固定锁序操作。模型、原文读取和大对象写入已经完成，事务内不调用外部网络。

| 顺序 | 数据库动作 | 条件不满足时 |
| --- | --- | --- |
| 0 | 取得 identity.permission_epochs 共享锁并检查当前提交/复核权限 | 无权拒绝；撤权与提交的先后按 T06 固定 |
| 1 | 锁processing_runs，再锁event_candidates；读取已有CommitReceipt及原代次的持久失效记录 | completed/dismissed回各自原回执；有效非事件决定待执行时返回DISPOSITION_PENDING；已失效提交回原失效结果；其他取消/代次失效返回STALE_EXECUTION |
| 2 | 核查Step 2～5当前代次结果均成功/合法跳过，核对最终proposal_digest与review_decisions | 不具备完整门槛返回COMMIT_NOT_ELIGIBLE，零正式写入 |
| 3 | 取得event_identity_catalog排他锁；REUSE再锁events并比较expected_revision；NEW检查identity_decision未消费、快照范围/权限/规则有效且catalog_epoch一致 | 修订变化返回REVISION_CONFLICT；NEW快照过期返回IDENTITY_SNAPSHOT_STALE，按第7.2节持久失效并回Step 2；不得随机换ID或仅替换epoch |
| 4 | 核定实际变化键、评价键及目标引用，复核来源关系/证据/定义快照 | 冲突回滚；语义不明转复核 |
| 5 | 写适用Event、来源、证据、关系、更新及评级 | 所有正式ID由程序分配；任何FK/唯一失败整笔回滚 |
| 6 | 有业务变化才写revision_no+1与完整snapshot，CAS更新events.revision_no；同时使catalog_epoch加1，新建首修订亦如此 | 任一更新失败整笔回滚，epoch不单独提交；纯重复不新增修订、不推进epoch |
| 7 | 插入CommitReceipt；有应交付变化则插messages及各consumer的delivery行 | 消息与修订同事务，不能保存后另一次事务补消息 |
| 8 | 候选completed、resume_step=NULL，写saved_result_refs并更新批次汇总；提交 | 事务成功才允许返回完成 |

程序在事务外生成CommitProposal，把事实、关系、changes、评级/跳过决定、证据、身份决定、expected_revision与各节点输入摘要序列化成不可变工件；同时绑定retrieval_snapshot_id、manifest_digest、scope_key、catalog_epoch和检索规则/授权范围。身份复核摘要及最终提交摘要均覆盖该绑定。在candidate行保存commit_payload_artifact_id、commit_proposal_digest和固定commit_key。复核只批准该摘要；提交从此工件读取，禁止接受调用方临时传入另一套业务payload。

批准的最终建议包含新增事件事实、关系、变化和评级的摘要；改变任一内容都使该审批失效。第一阶段身份复核与最终提交复核是不同scope；自动身份规则未发布时均需有效决定。它们可由同一授权人处理，但不能由模型响应代替。

SQL死锁或连接中断先回滚/查询回执后重试原commit_key；不重新调用模型。若第一次事务已成功而客户端不知道，第二次读取completed及回执返回同一event/revision。纯重复也有result_kind=NO_CHANGE回执，但effects为空且无消息。

### 7.1 两候选同事件的具体竞争

C1、C2都读取Event E的revision=3。C1先提交生成revision=4；C2随后取得锁时发现expected=3≠4，整个事务退出。C2重读revision=4，重新比较AI-04增量及AI-05评价依据；若发现C1已保存相同变化则复用变化身份并完成无变化结果；若仍有独立变化，生成新建议/审批后提交revision=5。不能仅把expected_revision改成4后原样重放旧建议。

### 7.2 不同候选并发新建的集合版本校验

**首切片选择：单组织内共享一个事件集合版本，配合短事务行锁。**不按标题、主体或模型输出划锁范围，避免两个同义候选落入不同锁域。该版本表示正式事件集合的变化，不证明语义相同；AI-02与授权复核仍负责身份判断。

1. **冻结召回依据。**程序在权限校验后的短读事务中取得集合行共享锁，读取epoch，并从主库读取该授权范围内的匹配事件、固定修订及覆盖信息；同一事务完成检索后释放锁。首切片不从异步索引或只读副本生成可支持NEW的快照。事务外生成不可变manifest，再按候选有效代次条件保存event_identity_snapshots；失败或代次变化不发布该快照。仅记录时间戳或在检索结束后另查epoch，不能证明检索与版本一致。
2. **固定决定与审批。**IdentityDecision引用该快照，AI-02输入摘要包含manifest摘要；身份批准与最终批准绑定相同快照。查询失败、覆盖不足或截断未解决时不形成可提交NEW；人工也须先取得覆盖充分的检索依据，不能只批准一份不完整清单。
3. **提交时校验。**按T01锁序取得集合行排他锁，检查NEW快照的scope_key和epoch仍与当前相同，授权范围、权限代次及检索规则也仍有效。REUSE不因无关集合变化自动失效，继续检查自身expected_revision及权限。校验通过后，正式事件写入、身份决定消费、集合版本递增、回执与Outbox在同一事务完成，锁保持到提交或回滚。
4. **过期决定失效。**NEW校验失败时，在任何正式写入之前，将原代次Step 2记录的reason_code设为IDENTITY_SNAPSHOT_STALE，reason_details保存失败commit_key、快照ID、旧/当前epoch与具体原因；候选proposal_generation加1，Step 2～5旧结果标为superseded，清除当前身份/CommitProposal绑定并使旧审批不可再用，保存resume_step=2及review状态，同事务更新批次汇总。只提交这些控制记录，不产生正式事件、修订、业务回执或Outbox；原快照、决定和审批保留审计。重复的旧代次请求按原Step 2失效记录返回同一结果，不能再次递增代次。
5. **重新归组。**Workflow读到持久恢复点后，按授权恢复政策在原processing/candidate下重新召回、执行AI-02并完成身份复核，再重建Step 3～5及最终审批。模型和复核全在事务外；期间旧模型结果与旧审批按代次拒绝。新commit_key随新的有效决策代次固定；锁超时等技术失败则保留原代次/commit_key有界重试。不得清零模型预算，预算不足或连续冲突进入待处理，不无限重跑。

**版本推进范围。**首切片所有正式事件新建、修订（包括来源/证据、关系和评级变化）都先取得同一集合锁并同事务推进epoch；NO_CHANGE、运行状态变化、失败或回滚不推进。后续接入合并、拆分、归档或影响召回可见性的业务操作时，同样必须覆盖此协议，不允许旁路写入；权限变化另由T06权限代次控制并使相关授权快照失效。

**两候选推演。**C1、C2均在epoch=12时获得NEW批准。C1先提交Event E并将epoch推进到13；C2取得锁后发现12≠13，零正式写入并退回Step 2。重新召回若确认同一事件，C2改为REUSE E并重新审批；若确认是独立事件，则基于epoch=13形成新的NEW决定。不是把所有并发候选强行合并为一个事件。

**成本与保证边界。**无关事件修订也可能使NEW重新复核，这是首切片用较粗范围换取可检查并发边界的代价；应记录冲突率和锁等待。该机制保证不能沿用事件集合变化前的旧NEW决定直接提交，不保证检索或模型不会漏判语义重复。多租户或高并发阶段再设计稳定的分区范围、跨区锁序及迁移规则，不能直接用模型主体名称分片。

## 8. 召回、历史读取与查询设计

AI-02召回在程序中执行：先按明确政策/行动标识读取关联事件，再按规范化主体与动作进行结构过滤；文本补充使用参数化ILIKE并转义`%`和`_`，不拼接SQL。缺失时间不会作为排除条件；未知主体不得凭空补词。默认最多返回100个事件摘要，按updated_at和id稳定排序；命中多于100标记retrieval_truncated=true，禁止据截断结果自动判NEW。

可用于新建提交的召回必须按第7.2节绑定集合版本与覆盖依据；超过上限需缩小有业务依据的检索范围或完成受控补充检索，不能将截断标志清除后复用旧清单。范围/规则改变形成新快照及输入摘要，旧审批不能转用。

首切片不采用向量近邻阈值作归组裁决，也不假设通用全文分词对中文已适配。定义匹配可先读取受控的小规模Target/Variable快照；超过配置容量则明确分页/检索并记录覆盖，不能用任意前N条伪装完整字典。

读取历史按(event_id,revision_no)定位不可变snapshot；事件更新按业务时间和recorded_at分开排序。结果查询使用专用表及定长游标，数据库执行权限过滤和分页后返回；不在内存加载全库再过滤。设计默认第一页20条、最大100条，具体容量须验证。
