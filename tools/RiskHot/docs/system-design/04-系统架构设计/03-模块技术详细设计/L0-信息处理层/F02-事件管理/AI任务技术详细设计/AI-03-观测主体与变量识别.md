# AI-03 观测主体与变量识别技术详细设计

## 1. 输入准备

程序取得已核定EventContextRef及身份决定，准备事件描述、主体、状态、当前资料证据，以及允许的Target和全局Variable定义快照。每个定义提供真实ID、版本、名称、类型/辖区/范围、单位及有效状态；无匹配定义应明确表达，不能用自由文本伪造正式ID。

新事件使用候选上下文，正式EventTarget/三元关系仍到Step 6才形成。模型不得因观察到某变量名称就调用外部指标数据或创建定义；本步只识别原文直接涉及的关系。

## 2. 建议结构

| 项目 | 逻辑内容 | 合法空值 |
| --- | --- | --- |
| 观测主体关系建议 | target_id及版本、关系说明、证据 | 可无任何Target |
| 直接变量关系建议 | target_id、variable_id及版本、关系类型、变化方向、作用阶段、描述与证据 | 可仅有Target而无Variable |
| 定义候选 | 名称、类型/辖区/边界或变量定义/单位、未匹配理由与证据 | 缺定义时记录候选，不给正式ID |
| 待确认问题 | 身份/范围/直接性歧义 | 无问题可空 |

模型区分行为发起者和观测主体；只保留直接改变、宣布调整或已观察变化的变量。融资成本等传导推测留给后续层，不因“合理”就在L0建关系。

## 3. 程序校验与交接

检查每个正式ID是否在允许集合且版本/状态适用、Target类型与范围是否匹配；三元关系必须对应本次已确认或建议的同事件EventTarget。引用资料必须已属于或将同事务加入该事件，定位可回溯。任何关系都不得用candidate_id冒充正式event_id。

经验证的空关系是正常结果，继续Step 4；定义候选交治理入口保留，不阻止其他合法结果。若某项正式关系引用或证据无效，该候选停在本步恢复/复核，不能静默删掉坏项后称全部有效；复核明确排除该项时保留决定及理由再继续。

## 4. 异常与一致性

字典读取失败不同于字典确实无匹配，前者待恢复，后者允许候选定义。身份变化、定义版本被撤销或证据变动使受影响建议失效；恢复须重新准备本步及后续依赖。模型故障不能伪装“无关系”成功。

Step 6再次核对定义引用和事件关系。跨事件target/variable串联、变量不在全局字典、仅有变量无对应Target、把静态Target—Variable归属当本次事件证据均拒绝。

## 5. 验证与审计

验证两Target多Variable、一Target无变量、完全无直接关系、定义缺失、无效ID、停用定义、间接传导误识别及字典服务失败。保存定义快照、建议、逐项校验和复核；正式关系反查原文。共用调用和故障协议见[T04](../../../../02-%E4%B8%93%E9%A2%98%E6%8A%80%E6%9C%AF%E6%9E%B6%E6%9E%84/T04-AI%E4%B8%8EAgent%E6%9E%B6%E6%9E%84.md)，验收见[质量方案](../../../../05-%E6%9E%B6%E6%9E%84%E6%B2%BB%E7%90%86%E4%B8%8E%E9%AA%8C%E8%AF%81/%E6%9E%B6%E6%9E%84%E9%AA%8C%E8%AF%81/AI%E8%B4%A8%E9%87%8F%E8%AF%84%E6%B5%8B/L0%E6%A8%A1%E5%9E%8B%E4%B8%8E%E8%AF%81%E6%8D%AE%E8%B4%A8%E9%87%8F%E8%AF%84%E6%B5%8B%E8%AE%BE%E8%AE%A1.md)。
