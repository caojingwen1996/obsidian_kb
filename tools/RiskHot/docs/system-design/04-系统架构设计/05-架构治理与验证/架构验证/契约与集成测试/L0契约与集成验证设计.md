# L0 契约与集成验证设计

> V0.7 · 2026-10-24 · 仅验收设计，所有用例待实现阶段执行。

## 1. 测试边界

以受控模型响应隔离系统职责，同时使用真实持久化和接收回执机制验证交接。所有“真实”指未来测试环境要求，本轮未启动任何服务。五项主场景以[总方案](../L0%E6%9C%80%E5%B0%8F%E4%B8%9A%E5%8A%A1%E9%97%AD%E7%8E%AF%E9%AA%8C%E8%AF%81%E6%96%B9%E6%A1%88.md)为准。

## 2. 契约检查矩阵

| 边界 | 正向断言 | 反向断言 |
| --- | --- | --- |
| 命令 → Operation | 同键同载荷回原接收记录，异步可查 | 同键异载荷冲突，不覆盖原Operation |
| F01保存 → F02接收 | 固定版本、对象与映射可读，返回持久processing_ref | 临时对象、未知版本、摘要不符、越权不受理 |
| AI-01 → 候选集合 | 全部结构有效后一次固定N项，0也是完整结果 | 截断、坏引用、半集合不能固定count |
| AI-02 → 身份上下文 | 新候选/已有事件两种上下文明确 | 伪ID、召回失败当NEW、错误修订拒绝 |
| AI-03 → 关系建议 | 已有Target、Variable真实且直接关系有证据；合法空关系正常 | 无对应EventTarget的三元关系、跨事件引用拒绝 |
| AI-04 → 写入动作 | 七类增量映射准确，实际变化键去重 | 来源增加造更新、重复造评级、纠正覆盖旧历史拒绝 |
| AI-05 → 评级建议 | 范围/期限/方法/依据固定，程序负责计算或合法空M | 模型改范围、伪总分/批准状态、失败生成默认草稿拒绝 |
| Step 6 → 正式结果 | 业务对象/修订/候选回执/Outbox原子一致 | 旧审批、取消代次、过期修订无部分写入 |
| Step 7 → 下游 | 原message_id重投，Inbox效果一次，缺序可识别 | 重投触发重分析或以送达冒充业务完成拒绝 |
| 查询 → 原件 | 固定修订可回原文及当时定义 | 权限缺失明确拒绝，不返回他人原件 |

## 3. 幂等验证的多种重复

依次设计同HTTP请求重试、不同请求键同来源版本、F01换消息ID重发同版本、同候选提交重试、同消息多次下游接收。每一层都比较前后逻辑对象和唯一身份；获取/运行/尝试记录可以增加，但不得因此增加业务版本、EventUpdate或EventRating。

并发两次提交S-MULTI：应只接纳一个候选集合和一个INITIAL处理。提交成功后故意丢失回应，再提交同commit_key，必须返回原修订。方法升级后普通重交仍返回旧处理；授权重算则生成新analysis_key但不自动重造实际变化。

## 4. 适用数据库断言

新事件最小聚合有Event、EventInformation、至少一条有效EventEvidence、初始更新、首修订及提交回执；Target/Variable和量化M不是强制非空。纯重复只增加/完成处理记录，不生成空EventRevision。来源增加仅增加适用来源/版本证据并按功能设计形成可交付修订，不造进展。

两候选分别提交时，资料汇总与候选状态保持一致。任一必要任务失败，该候选的正式表差量为0；已提交独立候选保持不变。数据库断言与读接口结果须一致，不能只测试页面标签。

未来每项证据包括请求/回执（脱敏）、输入摘要、正式数据差量、引用解析、冲突/错误类别及清理记录，汇总到[验收报告](../%E6%9E%B6%E6%9E%84%E9%AA%8C%E6%94%B6%E6%8A%A5%E5%91%8A/L0%E6%9C%80%E5%B0%8F%E9%97%AD%E7%8E%AF%E9%AA%8C%E6%94%B6%E6%8A%A5%E5%91%8A_%E5%BE%85%E6%89%A7%E8%A1%8C.md)。Schema向后兼容按[T02](../../../02-%E4%B8%93%E9%A2%98%E6%8A%80%E6%9C%AF%E6%9E%B6%E6%9E%84/T02-%E6%8E%A5%E5%8F%A3%E4%B8%8E%E9%9B%86%E6%88%90%E6%9E%B6%E6%9E%84.md)、[T04](../../../02-%E4%B8%93%E9%A2%98%E6%8A%80%E6%9C%AF%E6%9E%B6%E6%9E%84/T04-AI%E4%B8%8EAgent%E6%9E%B6%E6%9E%84.md)检查，旧AI@1.0不得被未发布草案覆盖。

### 6.1 不同候选并发新建的验证设计

依据[F02数据设计第7.2节](../../../03-模块技术详细设计/L0-信息处理层/F02-事件管理/事件数据与状态设计.md#72-不同候选并发新建的集合版本校验)。用受控模型响应和人工决定固定语义结论，以执行屏障控制“同版本召回—均批准—先后提交”；既覆盖不同资料，也覆盖同资料内不同候选。运行阶段须检查真实数据库锁、事务及持久恢复，不能仅用顺序模拟证明并发正确。

| 场景 | 控制顺序 | 必须成立的断言 |
| --- | --- | --- |
| 同一事件并发NEW | C1/C2均冻结epoch=12并获批；C1提交后再放行C2；重新归组明确REUSE | 首轮仅一个Event及首修订；C2返回IDENTITY_SNAPSHOT_STALE，正式表/业务回执/消息差量为0；候选身份和Step 1集合不变，Step 2～5旧结果失效；新审批后C2关联同一Event，按实际来源变化生成必要修订 |
| 两个独立事件并发NEW | 同上，但C2重新召回后明确仍为独立NEW | C2必须使用新快照、新决定和新审批；最终两个Event，不能把集合冲突解释为语义重复并强制合并 |
| 召回与写入交错 | 在读取epoch后、读取匹配事件前暂停召回；另一事务尝试正式写入 | 共享/排他集合锁使二者串行完成；不能产生“旧召回集合绑定新epoch”的快照；锁超时按有界技术恢复处理 |
| 版本推进与回滚 | 在事件写入及epoch递增后、事务提交前注入故障；再测试正常修订和NO_CHANGE | 回滚后事件、epoch、身份消费、回执和消息均无新增；正常修订同事务推进epoch；NO_CHANGE不推进；所有受控正式写入口遵循相同集合锁序 |
| 旧决定或旧审批重放 | C2失效后重放旧proposal_generation、旧摘要；或只把epoch换为当前值 | 不允许写正式表；不能借用其他candidate/代次的快照；不能重复递增失效代次；迟到模型响应不能推进新代次 |
| 成功回应丢失 | C1已提交，但客户端未知；期间其他事件推进epoch，再重试原commit_key | 优先回原CommitReceipt，不因epoch变化重做归组，不新增Event、修订或消息 |
| 失效回应丢失与预算耗尽 | 失效控制记录已提交后中止Worker；或恢复时已无模型预算 | 根据持久resume_step=2继续；旧请求只读原失效结果；预算不足保持待处理，不清零计数或默认NEW |
| 范围与覆盖失效 | 改变权限代次/检索规则；或传入截断、失败、缺少集合行的快照 | 缺失、越权或范围不匹配不能提交；不得仅改epoch或清除截断标志重用旧审批；取得完整新快照后才可重新批准 |

记录candidate_id、retrieval_snapshot_id、旧/新catalog_epoch、proposal_generation、commit_key、锁等待、冲突原因和正式数据差量。上述均为待执行用例，不作为任意同义文本去重率或并发性能的实测结论。

### 6.2 确认非事件与批次结束验证设计

依据[F02数据设计§3.1](../../../03-模块技术详细设计/L0-信息处理层/F02-事件管理/事件数据与状态设计.md#31-授权确认非事件与正常结束)。以下为待执行场景，人工权限与明确决定使用受控测试身份；未来以真实事务、工作流唤醒和数据差量验证。

| 场景 | 输入或竞争顺序 | 必须成立的断言 |
| --- | --- | --- |
| 混合终态 | 两个固定候选，一个completed，一个授权确认非事件 | 原candidate_count=2；completed_count=1、dismissed_count=1、resolved_count=2、pending_count=0，批次completed；已完成事件及交付保持原样 |
| 全部否决与零候选区分 | 两个固定候选分别确认非事件；对照AI-01合法零候选 | 前者count=2、dismissed_count=2，有两份NOT_EVENT回执；后者count=0、dismissed_count=0，无候选回执；都正常结束，均无正式事件及通知，delivery_status=not_required |
| 适用性与权限 | 模型失败/取消/身份未知冒充非事件，空理由、错误依据、过期代次或无candidate_disposition权限 | 不形成有效终态；普通identity/commit拒绝不隐式变dismissed；模型无处置写权限，原失败仍可查 |
| 审批受理与处置分离 | reviews返回202后暂停IO Worker，再恢复；同时丢弃signal | 202时候选仍review且普通提交受DISPOSITION_PENDING阻断；轮询/对账发现决定并完成处置，不调用剩余AI任务 |
| 与正式提交竞争 | 分别控制正式提交先完成、非事件决定先受理 | 前者拒绝处置且保留Event；后者拒绝普通提交，最终只有NOT_EVENT回执；不得出现同候选的两种终结效果 |
| 取消/撤权/迟到模型 | 在决定受理和最终处置之间取消或撤权；处置后再返回旧模型响应 | 取消/撤权先完成则不终结；处置先完成则保留终态；迟到响应不接纳、不重开候选、不写事件 |
| 回滚、重放与回应丢失 | 在处置回执和汇总更新之间故障；成功后丢回应；同键及不同键重复确认 | 失败整笔回滚；恢复只消费原有效决定；成功重放返回原回执，计数只变一次，原理由不可覆盖；错误摘要不能获得新处置资格 |
| 重试与改判 | 对dismissed普通retry，再发起授权重算 | retry仅返回旧NOT_EVENT；授权重算创建新processing/候选并保留父关联，原终态与审计不改写；重复已有事件仍走REUSE/NO_CHANGE |

处置事务的正式数据差量须为0：Event、来源/证据关系、EventUpdate、EventRating、EventRevision、catalog_epoch以及事件变化messages/deliveries均不增加或修改。允许增加授权决定、审计、NOT_EVENT处理回执并更新候选/批次状态。记录依据摘要、操作者、权限、决策代次、执行代次与恢复轨迹；不能仅凭页面显示“完成”判定通过。

### 6.3 F01 独立复核与恢复验证设计

依据[F01数据设计第7章](../../../03-模块技术详细设计/L0-信息处理层/F01-信息接入与标准化/关键接口与数据设计.md#7-f01-复核与恢复契约)。本组全部待实现阶段执行；使用真实操作记录、命令回执、固定工件及事务屏障验证，不能只检查接口返回202。

| 场景 | 输入或中断位置 | 必须成立的断言 |
| --- | --- | --- |
| 无资料ID的身份复核 | Step 4强身份冲突，information_id及version_decision_id未确定 | 仅凭原operation_id建立/查询F01案件，比较依据可回原件；无需F02 processing/candidate，不写F02复核表 |
| 受理后进程崩溃 | 返回202后、Step 2前终止API | material_operations、command_receipts、execution_intent同事务存在；可由command_artifact恢复完整正文和来源，不用摘要猜输入 |
| 批准与拒绝 | 同一案件分别测试APPROVE_PLAN、RECOMPARE、REJECT_INTAKE | 批准绑定原basis/计划并从Step 4校验，不直接saved；重比较形成新决定代次/案件；拒绝保留历史，旧执行不能保存 |
| 依据并发变化 | 复核之前或批准之后由另一操作推进资料当前版本 | REVIEW_BASIS_STALE；旧批准不能换绑新版本；失效代次只推进一次，生成只准备案件的Step 4意图，重新复核前零资料保存效果 |
| 权限与范围 | F02复核者调用F01入口、未授权来源、批准后撤权或停用来源 | information_review/information_retry独立检查；越权不能读取依据或恢复，保存前资格失效阻断，不增加版本 |
| 技术恢复防重复 | 获取/标准化失败后相同键及不同键并发retry | 同键同体同回执；不同键旧代次仅一个被接纳；一个新执行意图，原输入/规则和有效工件复用，旧执行不能覆盖检查点 |
| 保存回应丢失 | Step 5已提交后丢回应，再恢复原操作；同时别人推进当前版本 | 先查material_save_receipts，回原固定版本；REUSE亦有回执，不新增资料版本，不回退当前指针、不重启接入 |
| 原消息交付恢复 | F02已接收但回执丢失，或投递窗口耗尽后授权恢复 | 同version/message重新交付，F02回同processing；交付恢复代次只增加一次，累计attempts不清零，窗口有界，旧lease_token无效 |
| 状态与篡改拒绝 | review无批准时retry、rejected恢复、替换resolution_ref/basis/正文或指定resume_step | 明确拒绝，不替用户批准或变更资料；saved/received重复恢复返回原结果，控制回执始终关联原接入操作 |

证据至少记录原operation_id、控制命令回执、两类代次、case/decision及依据摘要、version_commit_key/保存回执、消息与交付窗口；比较资料/版本/F02处理数量及状态差量。所有运行项保持未执行。

### 6.4 F01 历史晚到与当前版本指针验证设计

依据[F01保存分支§6.3.1](../../../03-模块技术详细设计/L0-信息处理层/F01-信息接入与标准化/关键接口与数据设计.md#631-保存分支与当前版本指针)。准备同一资料v1、v2、v3及当前指针v3，固定各版本来源顺序、正文/产物和交付回执；以下运行用例均待执行。

| 场景 | 受控判据或执行顺序 | 数据库与交付断言 |
| --- | --- | --- |
| 复用当前v3 | 同一来源修订及产物，无有效变化 | 不新增版本/segments；current及row_version不变，获取记录关联v3，回执返回v3并复用交付 |
| 历史v1晚到 | 确认原来源修订，expected=v3、target=v1 | current仍v3、row_version不变；无v4；获取记录与保存回执指向v1，已received返回原回执，未received恢复v1原消息 |
| 来源新回滚到v1内容 | 有证据证明是发生在v3之后的新来源修订 | 新增v4、parent=v3、current=v4、row_version仅加1；保留与v1内容相同的依据，v4有独立固定版本交付 |
| 无法区分晚到与回滚 | 只有相同哈希或不可靠发布时间 | 进入review；current仍v3，版本/成功保存回执/新消息差量为0；批准也不能省略来源顺序依据 |
| 晚到与新修订竞争 | 先生成expected=v3的晚到决定，另一操作先保存v4 | 旧决定不能原样保存；重新比较或重新复核后复用v1，current保持v4；原版本和消息不重复创建 |
| 保存回应丢失与事务回滚 | REUSE或新增分支分别在提交前中断、提交后丢回应 | 提交前版本/指针/获取关联/回执/消息整体回滚；提交后使用原version_commit_key返回同一结果，不再更新指针/row_version |
| 历史版本处理修复及未保存历史 | 修复v1的标准化产物，而current=v3；或晚到内容找不到已保存版本 | 不自动将历史内容提升为当前修订；明确复核/待处理，不能仅凭max+1产生新当前版本 |

断言同时读取materials.current_version_id/row_version、material_versions的数量与parent、material_acquisitions.version_id、material_save_receipts.version_id及material_deliveries.message_id。特别比较“返回的结果版本”和“当前版本”两个值，不能仅凭操作saved判断指针正确。

### 6.5 F01 完整请求持久化与恢复验证设计

依据[F01请求持久化定义§7.1.1](../../../03-模块技术详细设计/L0-信息处理层/F01-信息接入与标准化/关键接口与数据设计.md#711-完整接入请求的持久化定义)与[T05引用保护及清理§6.4](../../../02-专题技术架构/T05-信息与知识工程架构.md#64-接入请求工件的引用保护与清理)。以下为待执行设计；未来使用真实持久卷、数据库事务及进程中断验证，不以模拟返回202作为持久化证明。

| 场景 | 中断位置或输入 | 必须成立的断言 |
| --- | --- | --- |
| 受理后API重启 | 返回202后、Step 2生成原件前终止API；丢失进程内存 | 原operation能读取ready的intake-command完整正文与来源；回执、操作引用/摘要、启动意图一致；恢复原流程，不要求客户端再次提供正文 |
| 工件写入失败 | 在staged、写盘、持久发布或校验阶段注入失败 | 不返回202，无已受理操作和启动意图；残留对象不能被执行；重试仍使用原幂等键 |
| 对象成功而事务失败 | ready后在三类业务记录写入之间故障或回滚 | 无部分接收回执、material_operations或启动意图；未绑定工件不代表受理成功，只能按批准的清理规则处置 |
| 回应丢失及并发提交 | 提交后丢回应；同键同载荷并发，再用同键异载荷提交 | 只保留一个有效operation/输入绑定/初始意图；同载荷回原回执，异载荷409；失败方工件不换绑、不覆盖胜者 |
| 工件缺失或篡改 | 删除测试副本、改字节、错大小/摘要、错operation或未知Schema | INPUT_ARTIFACT_UNAVAILABLE/INPUT_ARTIFACT_INVALID，保持recoverable并从Step 2恢复；无空资料成功、无F02事件；仅同内容同摘要修复可继续 |
| 正文与摘要边界 | 中文、非BMP、CRLF、空格、正文BOM；改变JSON键序/转义写法；另测非法Unicode | 语义相同请求的payload_digest相同，正文实际字符变化可区分；整工件摘要与正文摘要分别校验；Step 2原件等于content.text的UTF-8字节，清洗仅在Step 3；非法编码受理前拒绝 |
| 清理与绑定竞争 | 分别控制受理事务和清理事务先取得工件行锁；再检查saved/rejected操作 | 绑定先完成则保留工件；清理先标deleting则禁止绑定及202；已绑定工件不能作为孤立对象删除；未批准保留政策时不自动删除 |
| 授权与敏感信息 | 工件context包含历史权限但当前已撤权；使用其他身份读取；请求携带认证头 | 当前越权读取/执行被阻断，历史快照不替代授权；工件不保存令牌、Cookie或认证头，日志不含正文与凭据；原受理记录保持可审计 |

证据记录operation_id、command_artifact_id、object_key、工件/载荷/正文三类摘要、artifact状态、回执与启动意图、事务提交结果和恢复轨迹。检查持久化记录及文件实际内容；审计报告只存授权的脱敏摘要，不复制完整敏感正文。以上八组运行用例均未执行。
