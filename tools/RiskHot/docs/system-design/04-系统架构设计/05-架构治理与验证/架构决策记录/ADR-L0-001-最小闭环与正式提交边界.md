# ADR-L0-001 最小闭环与正式提交边界

> 日期：2026-10-24；状态：拟采用，待架构评审。记录本轮设计选择及代价，不把未确认业务政策标为已批准。

## 1. 背景与约束

用户要求按总体、专项、L0、F01/F02、AI任务顺序完成架构文档，保证五项最小闭环要求可验证；本轮不开发。最新F01只有信息接入和标准化，F02有七步、前五步由程序与AI协作、Step 6正式保存。

[旧总体架构](../../../../../aihot/%E5%BD%92%E6%A1%A3/%E6%97%A7%E7%89%88%E7%B3%BB%E7%BB%9F%E6%9E%B6%E6%9E%84%E8%AE%BE%E8%AE%A1/00.%20%E7%B3%BB%E7%BB%9F%E6%80%BB%E4%BD%93%E6%9E%B6%E6%9E%84.md)仍有指标接入及旧幂等口径；不能直接作为最新L0的完整契约。新事件保存前的AI任务又需要事件上下文，必须区分候选身份和正式身份。

## 2. 拟采用的决策

| 决策 | 选择 | 原因与代价 |
| --- | --- | --- |
| 最小资料范围 | 受控来源、可完整读取并定位的文本 | 可以检验全部核心机制；不证明抓取/OCR全格式能力 |
| 结构 | 模块化核心、API/Worker、PostgreSQL、Temporal、不可变对象存储 | 由业务不变量推导；选型比较见 ADR-L0-002 |
| 业务真相 | 数据库记录业务状态与提交回执，工作流负责推进 | 避免运行状态替代业务判断；需要对账与恢复 |
| 候选集合 | 完整抽取一次固定，候选后续独立执行 | 防部分响应造成漏处理；集合坏项需先修复 |
| 新事件上下文 | candidate/event判别式EventContextRef | 不提前制造正式Event；需新Schema及旧任务兼容评审 |
| 正式提交 | Step 6统一短事务，模型仅产生建议 | 防错误或半成品入库；需要前后校验与并发重检 |
| 初始提交政策 | 无批准自动通过规则时，授权复核者确认最终建议后提交变化 | 不编造自动阈值；引入人工时延与依赖，待业务/架构评审 |
| M规则未定 | 有效文字评价 + 空M草稿；失败仍待恢复 | 最小闭环不依赖未批准公式；不验证量化能力 |
| 消息交付 | 持久启动意图、Outbox/Inbox、固定修订与原消息重投 | 接受至少一次传输，业务幂等；需要积压监控 |
| 验证接收端 | 可用隔离持久接收端验证L0交付 | 不要求L1全部实现；不能声称完成下游业务 |

## 3. 未采用方案

不让LLM直接写正式Event；不为运行中的新事件预先插入正式空壳；不以事件标题唯一键保证语义去重；不把空响应当无事件；不把模型故障写成默认空分草稿；不将工作流历史作为永久业务去重依据。暂不把向量检索、自主Agent或额外消息总线作为首切片前提。

## 4. 业务契约与历史记录边界

新包装、状态及逻辑接口均为目标设计，不修改旧AI@1.0或V0.1提示词发布状态。新接口明确候选关联到业务 event_id 的转换、技术增量/身份枚举及消息身份含义；不自动兼容旧应用路由、旧消息或旧数据库。旧架构清单与开发工作包仅作历史记录，不得作为新方案的开发输入。

本轮L0范围以[新总体入口](../../01-%E7%B3%BB%E7%BB%9F%E6%80%BB%E4%BD%93%E6%8A%80%E6%9C%AF%E6%9E%B6%E6%9E%84%E8%AE%BE%E8%AE%A1.md)及其分册为准；旧分册保留技术背景，不将旧F01指标路径重新纳入。历史开发报告只说明当时情况，不作为五项新验收已通过的证据。

## 5. 待决项及可运行替代

| 编号 | 待决问题 | 首切片处理 | 后续门槛 |
| --- | --- | --- | --- |
| D-L0-01 | 新任务Schema/候选身份映射 | 本稿给出逻辑契约，未发布 | 实现前评审并发布兼容版本 |
| D-L0-02 | 自动归组/提交政策 | 拟用显式授权复核，不设虚构阈值 | 首次提交前确认复核政策；自动化另行评测 |
| D-L0-03 | 事件粒度及跨来源歧义 | 逐案例复核，保留UNRESOLVED | 冻结标注样本与身份规则 |
| D-L0-04 | M方法、范围及期限口径 | 固定每次输入；文字评价、空M草稿 | 使用量化分支前批准方法与锚点 |
| D-L0-05 | 资料定位格式/长度/版本规则 | 确定性文本映射，超限待处理 | 冻结受控切片格式及判据 |
| D-L0-06 | 真实模型许可/版本/质量门槛 | 未启用模型，不填实测结果 | 真实评测前冻结任务包、数据政策及门槛 |
| D-L0-07 | 并发预算、重试参数、保留期及恢复目标 | 采用 T02/T03 的验证默认值，生产指标未定 | 集成验证/部署前明确并验证 |
| D-L0-08 | 下游消息Schema与来源变化订阅 | 设计固定修订与持久回执 | 集成前确认接收契约；L1业务单独验收 |

## 6. 验证与后果

[验证方案](../%E6%9E%B6%E6%9E%84%E9%AA%8C%E8%AF%81/L0%E6%9C%80%E5%B0%8F%E4%B8%9A%E5%8A%A1%E9%97%AD%E7%8E%AF%E9%AA%8C%E8%AF%81%E6%96%B9%E6%A1%88.md)为每个不变量提供验收场景。设计解决了候选隔离、零结果、重复、引用和失败隔离的责任边界；其代价包括更多持久中间记录、人工复核和版本治理。是否可运行必须依赖后续执行证据，本ADR不批准工程实施或生产上线。

## 7. 独立选型及旧实现清除

V0.3 撤销 V0.2 中“以现有代码和依赖为技术基础”的前提。[ADR-L0-002](ADR-L0-002-%E7%8B%AC%E7%AB%8B%E6%8A%80%E6%9C%AF%E9%80%89%E5%9E%8B%E4%B8%8E%E8%AE%BE%E8%AE%A1%E5%9F%BA%E7%BA%BF.md)以业务闭环要求重新比较方案并确定技术基线；本 ADR 保留候选身份、正式提交与失败隔离等业务不变量。

旧应用源码、测试、数据库脚本和工程配置已从项目删除；业务文档、原型、历史资料与运行数据保留。全部目标组件需重新实现，旧测试结果不计入新闭环验收。当前阶段仅进行技术设计和文档编写。
