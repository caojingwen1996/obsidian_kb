# ADR-L0-003：业务任务队列替代 Temporal

- 日期：2026-10-30。
- 状态：用户已确定采用AIHOT模式；技术方案供评审，工程未实施，运行未验收。
- 范围：替代ADR-L0-002中的持久执行选型及三类Worker/启动中继分工；正式提交、幂等、权限与交付原则继续有效。

## 背景

用户要求后台采用AIHOT的业务Job交接方式，先重构技术架构。现有代码仍是Temporal、三类技术队列、启动意图及Relay；现有功能已明确F01计划主责和F02独立复核/保存边界。

## 决策

1. 使用pg-boss与同库事务入队，业务消费者保存结果时提交下一Job。
2. 首版API和一个后台Worker独立运行，按采集、抽取、事件处理、提交、增强、交付分队列；周期扫描由Worker统一注册。
3. 取消独立工作流、IO和模型队列。模型由业务任务调用受限子进程，子进程无数据库权限；业务父进程拥有受控校验与存储职责。
4. 人工等待保存领域状态并结束Job；决定与续办Job同事务提交。失败恢复依靠队列和领域检查点，不重建通用工作流引擎。
5. 保留执行代次、固定输入/任务包、模型预算、正式回执及Outbox/Inbox；取消仅阻止未提交工作。
6. 先停新受理并排空或登记待迁移旧运行，再切新引擎；同对象同代次不能被两引擎执行。

详细机制见 [[tools/RiskHot/docs/system-design/04-系统架构设计/02-专题技术架构/T03-任务编排与可靠性架构|T03]]，数据见 [[tools/RiskHot/docs/system-design/04-系统架构设计/01-数据模型与存储设计/S01任务执行数据契约|S01数据契约]]。

## 备选与取舍

| 方案 | 收益 | 代价与本次选择 |
| --- | --- | --- |
| 保留Temporal | 已有实现与持久步骤编排，可表达长等待 | 继续维护独立服务、历史和投递层；不符合本次简化方向 |
| pg-boss业务任务交接 | 依托现有PG，事务入队，按业务队列控制资源 | 领域须明确检查点、复核续办及恢复扫描；本次采用 |
| 自建PG队列 | 可定制全部行为 | 自行维护领取、心跳、清理和兼容；本次不采用 |
| 内存任务/定时器 | 初期实现少 | 进程退出可丢任务，缺少持久交接；不采用 |

运行成本减少的是Temporal服务及启动投递层，并不保证CPU/内存或吞吐一定改善，需相同负载比较。pg-boss与业务争用同一数据库；队列并发不等于模型全局配额。取消独立模型Worker后，父消费者成为更强的信任边界，必须验证子进程凭据隔离及输出接纳。

## 兼容与风险

- 不复制AIHOT的业务规则、任务并发或全部队列；只采用任务执行模式。
- Cron检测改为一分钟；信源自身计划保持，触发延迟纳入验证。
- 首版禁止多个模型调用Worker实例；扩容前完成共享配额和工件访问设计。
- 模型调用未知时不能保证不重复计费，必须保存未知尝试并按预算恢复。
- 所选pg-boss版本及Node/PG兼容、事务适配、权限和过期语义待PoC；未验证不得上线。
- 旧技术分册中的Temporal机制不再是目标要求；AI任务及业务模型版本不能借此自动升级。
