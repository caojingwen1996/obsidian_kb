# ADR-L0-003：Fact 与唯一事件模型

## 状态

2026-10-27 的业务模型变更已由用户明确确认；其后 Fact/Event 模型已有实施记录。2026-10-31 用户进一步确认 fact_material 命名并取消独立事件归属表，本次修订为已确认的目标设计，尚未迁移运行库；下文原决策保留历史语义，以新增修订覆盖冲突部分。

## 背景

旧 EventUpdate 是事件增量历史，另有候选、事件修订及前后关系，业务字段与表结构分散在领域、功能和技术设计中。用户要求将候选事实与唯一正式事件分开，简化 Event 字段，取消 F02 事件版本模型，并集中数据模型文档。

## 决策

以下记录 2026-10-27 的原决定；第 1、2、4 项按下节 2026-10-31 修订执行。F01 已取消原件及独立资料版本表，其现行存储边界以所属模块最新设计为准。

1. Fact 表达从 Information 提取的候选事件；Fact 与 Information 多对多，通过 fact_information 关联。
2. Event 表达唯一正式事件，与 Fact 一对多，通过 event_fact 关联；一个 Fact 未归组时不挂 Event，归组后最多一个。
3. Event 使用 subject、action，删除 event_type、subject_type、first_seen_at；只保留 event_time 表示发生时间。
4. 对象之间的业务关联放在关系表，不在对象表放外键属性或 ID 数组；Subject 仍是文字属性。
5. 取消 EventUpdate 历史实体、事件修订及更新前后链；保留 F01 资料版本、定义版本、运行/复核/提交/交付审计。
6. 领域文档仅保留对象、关系和业务属性规则；具体表结构由[[tools/RiskHot/docs/system-design/04-系统架构设计/01-数据模型与存储设计/F02事件管理模块数据模型与存储设计|F02 数据模型与存储设计]]维护。
7. 旧数据迁移以真实候选及证据为依据，不对 event_updates 执行简单改名；当前轮不执行迁移。

## 2026-10-31 修订：来源表命名与直接事件归属

1. Fact 表达跨报道统一后的同一次具体发生。来源关联表由 fact_information 改为 fact_material，资料键由 information_id 改为 material_id，保留多对多、来源作用及证据追溯。
2. 取消独立 event_fact 表，不新建同义 fact_event。当前唯一 Event 归属迁至 fact.event_id，未归组为空；原关系的角色、理由和时间分别迁至 event_relation_role、event_relation_note、event_assigned_at。其他业务关系继续按原设计维护。
3. 原第 4 项“不在对象表放关联外键”不再适用于 Event—Fact。一对多以可空外键表达，不需要中间表；多对多资料关联仍需独立表。单值 event_id 不保证并发提交不覆盖，必须配合行锁、旧归属检查及受控调整。
4. 事件内的 Target、变量与评价事实依据改为复合引用 fact(event_id,id)，继续禁止跨事件依据。正式 Event 至少有一个 Fact 的校验覆盖直接写入、删除和改组，不因取消关系表而取消完整性要求。

领域对象同步：FactMaterial 表达 Fact—material 的多对多来源关系，由 F02 随 Fact 管理，Fact 尚未归组时即可存在。EventMaterial 退出独立领域对象清单，事件资料入口从 Event → Fact → FactMaterial → material 派生；Event—Fact 不新设 EventFact 关联对象。来源支持/质疑作用与事实对事件的归属作用分别保留。本次只是将领域表达对齐已确认存储，不增加表或改变业务基数。

取舍：保留 event_fact 能继续集中存放归属属性，但对当前“每个 Fact 最多一个 Event”没有必要；将 material_id 直接放入 Fact 则不能承载已确认的多来源业务，故不采用。当前方案减少一张表及一层查询连接，代价是归属属性进入 Fact，并须同步外键、权限、查询、事务和审计。如果未来允许 Fact 同时属于多个 Event，需要重新决策，不能改为 ID 数组绕过约束。

本次只修改设计及引用。结构、迁移、并发与回退验收集中见 [[tools/RiskHot/docs/system-design/04-系统架构设计/01-数据模型与存储设计/F02事件管理模块数据模型与存储设计#9.4 V1.10 来源表改名与归属字段迁移（待实施）|V1.10 迁移设计]]；运行 SQL、应用适配与隔离库验证均待实施，已有验收不覆盖本次变更。

## 2026-10-31 修订：按领域属性核对存储

以 L0 当前领域定义为准，Fact 增加可空 object 以承载客体；EventTargetVariable 回到三元关联、说明及识别依据职责，change_direction/impact_status 退出其目标字段；EventRating 的金融用途由独立功能承接，不再是评价表目标必填项。既有用途和变化字段保留兼容读取，不能未核定新载体就删旧数据或机械转换成观测。

关联依据、定义快照与精确证据是业务规则的存储支撑，保留相应连接表，并补齐“每项正式关系至少有一条本事件Fact依据”的提交约束。材料附件、覆盖和采用配置口径复用受控metadata，不恢复已取消的原件、资料版本或信源版本表。

取舍是避免在关联表中保存某一次取值结论，并保留事实原始客体；代价是旧读写契约需迁移，新提取结果及金融用途载体仍需专门设计。观测级精确证据映射继续作为未完成设计项，不以共享变量事实上下文代替。逐对象结果见[[tools/RiskHot/docs/audit/数据模型与领域对象一致性检查-2026-10-31|一致性检查记录]]；本次不修改运行代码或数据库。

## 技术细化与代价

单一 event_time 用可空部分日期/时刻文本避免伪造精确时间；当前 Event 内容及关系摘要用于并发复查，共享消息依赖用于交付顺序。它们是本轮设计选择，仍需契约、性能和故障验证。

收益：候选与正式事件职责清楚，多来源复用通过关系表达，字段与数据模型集中。
代价：取消 Event 历史版本查询；当前事实纠正、并发控制和消息交付必须改造。追溯依靠原 Fact、原文和运行审计，不能再承诺旧版事件快照回放。

## 替代方案

保留 EventUpdate 并改标签不能满足新的候选定位；把全部历史塞入 Event JSON 会隐藏关系；直接删除运行库版本表会破坏现行读取与交付。均不采用。

## 验证与回退

实施前备份并核对候选、正式事件、证据、审批及交付记录，隔离库验证新旧映射和恢复。切换失败回滚应用与数据入口，不删 F01 原件、定义快照或共享审计。此次仅通过文档检查，不宣称迁移或真实任务完成。
