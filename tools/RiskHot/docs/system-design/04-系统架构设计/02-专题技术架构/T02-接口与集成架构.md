# T02 接口与集成架构

> V0.7 · 2026-10-27 · 接口技术评审稿。第5～7章定义目标HTTP路由、载荷、错误码与幂等过程；均不声明现有实现。

## 1. 接口分类

| 操作 | 调用者 → 所有者 | 接收与完成语义 |
| --- | --- | --- |
| SubmitInformation | 授权入口 → F01 | 持久接收资料命令；返回operation_ref，随后查询保存与交付 |
| AcceptInformationVersion | F01 → F02 | 核验固定资料版本并持久创建/复用处理记录；返回processing_ref |
| GetProcessing / GetCandidate | 读者 → F02 | 返回抽取状态、候选数、逐候选状态与结果引用 |
| ReviewInformation / RetryInformation | 授权复核者或运行入口 → F01 | 按接入操作及复核案件作决定；恢复原操作/原交付，不要求F02处理或候选身份 |
| ReviewCandidate | 授权复核者 → F02 | 对指定建议摘要作决定；程序再次检查权限、代次与版本 |
| RetryProcessing / Recompute | S01受托入口 → F01/F02 | 前者继续原身份；后者需业务授权生成新分析身份 |
| ReadEvent / ReadFact / ResolveEvidence | 读者 → F02/F01 | 当前 Event、关联 Fact 及证据原文；权限随原文检查 |
| AcceptEventChange | F02 → 下游入口 | 固定事件提交内容的持久接收，不代表下游分析完成 |

命令请求携带request_key、payload_digest、actor、authorization_scope、correlation_id和schema_version。服务端重算摘要；同键同摘要返回原回执，同键不同摘要拒绝。异步HTTP承载可用202表达已持久接收，不能表达业务成功；查询显示数据库业务状态。

## 2. 交付信封

| 字段 | 约束 |
| --- | --- |
| message_id | 程序生成的消息身份，重投不变 |
| message_type / schema_version | 如资料版本就绪、事件提交变化；契约协商后固定 |
| producer / aggregate_ref | 生产模块与资料/事件身份 |
| business_revision_ref / commit_ref | F01使用确定资料版本；F02使用提交身份及固定内容摘要，不提供事件修订号 |
| operation_ref / correlation_id | 运行关联；不能代替业务幂等键 |
| occurred_at / recorded_at | 业务发生时间可未知；记录时间由程序产生 |
| payload_ref / payload_digest | 受控读取的不可变载荷及摘要 |
| causation_ref | 上游提交或消息身份，可追踪因果 |

新信封中 message_id 只表示消息身份；业务事件身份位于 aggregate_ref 或载荷 event_id。首切片只接收本设计发布的契约版本，未知旧消息返回 UNSUPPORTED_SCHEMA，不推断映射。

## 3. 接收、重投与顺序

F01交付只包含已保存可读版本；F02收件事务创建Inbox及INITIAL处理记录，重复消息或新消息重复引用同资料版本均返回原处理。两级幂等缺一不可。F02对外只发送正式提交产生的变化；无事件、纯重复不产生事件变化通知。

接收方先验证授权、Schema及摘要，再在事务中接收，成功后回执包括message_id、consumer_id、received_at和持久接收引用。回执丢失时发送方使用原message_id重发，接收方回原回执。超预算转交付待恢复，已提交结果保持不变。

事件提交消息可能乱序：共享交付记录以独立前序消息依赖关系标识同事件先后，接收方登记Inbox后，仅在前序已应用时应用当前内容；缺前序先恢复。重投固定原消息与载荷，不能重新读取最新Event。此设计不增加事件版本表或revision_no，接收与应用分开记录。重新分析与交付重试仍为不同操作。

## 4. 错误契约

| 错误类别 | 是否重试 | 业务效果 |
| --- | --- | --- |
| 输入/Schema不支持、同幂等键异载荷 | 修改请求后新命令 | 不创建正式效果 |
| 权限或信源失效 | 授权处理后重入 | 不绕过检查 |
| 资料暂不可读、依赖超时 | 有界技术重试 | 原身份保留 |
| 证据失配、身份歧义 | 业务复核或修正 | 当前候选不提交 |
| 内容上下文/代次冲突 | 重新准备受影响上下文 | 原建议和审批失效 |
| 已完成重复请求 | 返回原结果 | 不重复执行业务 |

对外错误给出reason_code、可恢复性、下一步及关联ID，不泄露原文或模型凭据。字段枚举与传输Schema的正式版本待发布，不能以本稿自动替换AI@1.0。验证见[契约方案](../05-%E6%9E%B6%E6%9E%84%E6%B2%BB%E7%90%86%E4%B8%8E%E9%AA%8C%E8%AF%81/%E6%9E%B6%E6%9E%84%E9%AA%8C%E8%AF%81/%E5%A5%91%E7%BA%A6%E4%B8%8E%E9%9B%86%E6%88%90%E6%B5%8B%E8%AF%95/L0%E5%A5%91%E7%BA%A6%E4%B8%8E%E9%9B%86%E6%88%90%E9%AA%8C%E8%AF%81%E8%AE%BE%E8%AE%A1.md)。

## 5. HTTP路由与请求契约（目标设计）

目标接口统一使用 `/api/v1/l0/`，由 Fastify 承载，按 T06 的新认证与权限设计建立受理边界。下列路径均待重新实现；不提供旧通用命令路由兼容层。actor、角色、访问范围来自已认证会话，调用者不得通过JSON自报授权身份。写接口要求Idempotency-Key，键限制128个ASCII字符，服务端持久计算请求摘要。

| 方法与路径 | 请求主要字段 | 返回与异常 |
| --- | --- | --- |
| POST /api/v1/l0/information-submissions | source_id、source_identity{namespace,value}、content{text,media_type}、title?、published_at?、parent_operation_id? | 首次持久接收202：operation_id、status_url；同键同体回同operation；同键异体409；无权403；超限413 |
| GET /api/v1/l0/operations/{operation_id} | 路径UUID | 200返回保存/分析/交付各自状态，不以一个success替代三者 |
| GET /api/v1/l0/information-operations/{operation_id} | 原接入操作UUID | 200返回F01状态、代次、检查点、案件/依据、保存及交付回执；未分配的资料/版本/F02引用为null |
| GET /api/v1/l0/information-operations/{operation_id}/review-cases/{case_id} | 操作与案件UUID | 200返回比较依据、basis_digest、计划及历史决定；案件不属于操作404，越权403 |
| POST /api/v1/l0/information-operations/{operation_id}/reviews | case_id、expected_execution_generation、decision_generation、basis_digest、action、resolution_ref?、reason | 按第5.3节持久复核/启动意图后202；REJECT_INTAKE持久拒绝后200；过期409，无权403 |
| POST /api/v1/l0/information-operations/{operation_id}/retry | scope、expected_execution_generation?、version_id?、consumer_id?、expected_delivery_generation?、reason | 持久恢复回执及意图后202；已保存/已接收回原结果200；代次/状态不符409，无权403 |
| GET /api/v1/l0/information/{id}/versions/{version_id} | 两个UUID | 200固定版本、可读字段与分段链接；无权403，不存在404，工件不可读503 |
| GET /api/v1/l0/processings/{id} | include_candidates布尔值；候选分页cursor/limit | 200抽取状态、count可空、候选汇总；limit默认20，最大100 |
| GET /api/v1/l0/candidates/{id} | UUID | 200当前建议/校验/复核要求、恢复点、正式结果或处置回执；含disposition_basis_digest及proposal_generation |
| POST /api/v1/l0/candidates/{id}/reviews | scope、proposal_digest、proposal_generation、decision、reason | scope=disposition及CONFIRM_NOT_EVENT走第5.2节；其他复核持久记录决定及唤醒意图后202；过期摘要/代次409，越权403；不在HTTP线程调用模型 |
| POST /api/v1/l0/processings/{id}/cancel | expected_execution_generation、reason | 栅栏与取消意图持久后202；已提交结果保留，代次过期409 |
| POST /api/v1/l0/processings/{id}/retry | resume_token、reason | 202继续原业务身份；已完成200返回原结果；不改变analysis_key |
| POST /api/v1/l0/processings/{id}/recomputations | reason、task_manifest_id | 202新processing_id/analysis_key与parent_id；需重算权限 |
| GET /api/v1/l0/events/{id} | UUID | 200当前事件、关联Fact、主体/变量/评价及资料证据 |
| GET /api/v1/l0/facts/{id} | UUID | 200候选事实、资料关系、原文证据及有权读取的处理状态 |
| GET /api/v1/l0/evidence/{id} | UUID | 200引文、固定资料版本、原件定位及受控读取入口 |

接入切片仅支持`text/plain; charset=utf-8`：正文上限20,000个Unicode码点，请求总大小上限2MiB，原件上限1MiB，候选上限50。这些是本轮验证默认值，可通过版本化运行政策修改；不是已测容量或业务事件数量上限。超限明确停止，不能截断后继续。

### 5.1 接收响应与错误体

接收响应字段固定为`operation_id:uuid`、`accepted_at:date-time`、`status:"accepted"`、`status_url:string`、`replayed:boolean`。普通重复提交可拥有不同operation_id，但其`processing_id`必须收敛到同一资料版本的INITIAL；相同请求键则operation_id也相同。

错误体固定为`code`、`message`、`retryable`、`operation_id`（可空）、`details`（只放允许公开的字段），例如`IDEMPOTENCY_CONFLICT`、`SOURCE_DISABLED`、`MATERIAL_NOT_READABLE`、`STALE_PROPOSAL`、`EVENT_CONTEXT_STALE`。JSON格式失败400；类型/业务字段不满足422；服务不可用503。返回码不是业务结果状态，失败后的运行详情通过operation查询。

### 5.2 确认非事件的复核契约

沿用reviews入口，scope=disposition、decision=CONFIRM_NOT_EVENT；proposal_digest取GET Candidate返回的disposition_basis_digest，绑定当前候选内容、资料/证据和proposal_generation，不能提交模型自报摘要。reason必填非空，首切片上限2,000个Unicode码点；身份来自认证会话，需要T06的candidate_disposition权限及资料范围授权。

在权限、processing、candidate锁内核对未终态、未取消及依据有效，持久记录复核决定、审计与唤醒意图后返回202；IO Worker完成处置后查询得到dismissed及NOT_EVENT回执。202仅表示决定已接收。当前代次存在有效非事件决定时，其他identity/commit审批及普通事件提交返回DISPOSITION_PENDING，不允许越过待处置决定继续。

同键同体返回原受理回执；同键异体409。不同键再次确认已dismissed候选，在权限校验后200返回原NOT_EVENT回执（replayed=true），不覆盖原理由。已completed候选409 CANDIDATE_ALREADY_COMMITTED；旧依据/代次409 STALE_PROPOSAL；已取消409 STALE_EXECUTION；越权403。未终结且同代次已有相同非事件决定时复用原决定和受理状态；理由或依据改变则409 DISPOSITION_CONFLICT，须走授权重新准备，不能追加相互覆盖的决定。

查询候选返回status、result_kind、receipt_ref、review_decision_ref及来源证据引用；dismissed的正式event归属为空，Fact与审计仍保留。具体原子处置及竞争规则见[F02数据设计§3.1](../03-模块技术详细设计/L0-信息处理层/F02-事件管理/事件数据与状态设计.md#31-授权确认非事件与正常结束)。

### 5.3 F01 复核与恢复

F01专用入口以原SubmitInformation的operation_id定位，平台通用GET operations保留。查询字段、记录类型及恢复矩阵由[F01数据设计第7章](../03-模块技术详细设计/L0-信息处理层/F01-信息接入与标准化/关键接口与数据设计.md#7-f01-复核与恢复契约)维护；复核或恢复控制命令有自己的命令回执，但result_ref必须指回原接入操作。

reviews.action仅允许APPROVE_PLAN、RECOMPARE、REJECT_INTAKE。APPROVE_PLAN必须提供属于该basis_digest的resolution_ref，其余动作该字段为空；reason非空且最多2,000个Unicode码点。expected_execution_generation、decision_generation及依据摘要须与GET返回一致。服务端不接受请求自行填写information_id、current_version或替换原正文。需要更换输入/规则时使用新的information-submissions请求；可带parent_operation_id，服务器核验其为有权访问的F01操作并建立追踪关联，原操作及其工件不变。复核权限information_review独立于F02候选复核。

retry.scope=processing时必须提供expected_execution_generation，禁止带交付字段；scope=delivery时必须提供version_id、consumer_id、expected_delivery_generation，禁止带processing执行代次。续接步骤由服务器判断，不接收客户端resume_step。两类恢复均需information_retry及原资料来源范围权限；processing恢复不能改变固定输入/规则或绕过待复核，delivery恢复仅重投原message_id。

同键同体回原控制命令回执，同键异体409。不同键并发恢复通过期望代次只接纳一次；旧代次返回STALE_EXECUTION或STALE_DELIVERY_GENERATION，不能创建第二条启动意图。已经saved的processing恢复200返回原保存回执，已经received的delivery恢复200返回原接收回执，均先鉴权；rejected恢复返回OPERATION_REJECTED。

错误还包括REVIEW_REQUIRED、REVIEW_ALREADY_DECIDED、REVIEW_BASIS_STALE、OPERATION_ALREADY_SAVED、OPERATION_RUNNING及DELIVERY_RUNNING，均409且携带有权读取的当前状态/定位。缺失必填项或非法action/scope为422；读取工件失败503，不能伪装复核通过。审批/恢复受理返回202不能表示资料已saved或F02已received，后续结果从原操作查询。

## 6. 模块内调用与消息载荷

F01与F02同属information模块，首版通过受控应用端口调用，不增加内部HTTP服务。F01保存事务写`information.version.ready.v1`消息；中继调用F02 AcceptInformationVersion；F02在一个事务内写Inbox、复用/新建processing_runs、写启动意图并返回持久回执。

| 消息类型 | payload必填内容 | 接收者/去重 |
| --- | --- | --- |
| information.version.ready.v1 | information_id、version_id、manifest_artifact_id、source_config_ref | f02；Inbox去重后还按资料版本/INITIAL去重 |
| event.committed.v2（目标草案） | event_id、commit_key、change_kinds、固定Event内容、Fact及来源证据、适用关系/评价、payload_digest | 已登记消费者；按message_id去重及前序消息依赖应用 |

通用信封使用第2节字段；小载荷直接存platform.messages.payload，与事件提交同事务可见。大正文只用受控artifact_ref引用。发送目标从服务端consumer配置读取，模型不能决定接收地址。每个consumer独立message_deliveries行，一处接收故障不覆盖其他接收回执。

同进程端口与未来跨服务HTTP都遵守相同接收事务；首切片不部署跨模块HTTP仅为模拟微服务。迁移时旧event.revision.committed.v1必须按旧Schema显式处理或冻结归档，新消息使用新Schema。禁止把旧event_update_id直接解释为fact_id；旧文件和回执保留，不能因切换而改写。

## 7. 请求幂等的数据库过程

认证与Schema校验后，将语义请求规范化为固定字段集合；缺省可选字段明确转null，排除trace/header等运行噪声。canonical-json-v1规定对象键按Unicode码点排序、数组保留顺序、UTF-8编码，数值限制在契约允许的表示；记录规范化版本及原请求摘要。正文原始字节摘要另存，不能被请求规范化覆盖。

F01资料接入先保存并校验完整不可变输入工件，再在接收短事务中写command_receipts、material_operations（绑定该工件）及execution_intents；F01复核/恢复的决定或代次变化也须与命令回执、适用启动意图同事务。其他接收短事务尝试插入command_receipts及execution_intents。唯一键冲突时读取已提交记录：摘要相同回原operation，摘要不同409。事务失败不返回accepted；客户端可使用原键安全重试。不能先返回202再把命令放进内存队列。查询分页以(created_at,id)为游标边界，返回opaque cursor；不依赖偏移分页恢复业务处理。

### 7.1 F01 的202持久受理门槛

“完整请求已保存”指[F01接入请求工件契约](../03-模块技术详细设计/L0-信息处理层/F01-信息接入与标准化/关键接口与数据设计.md#711-完整接入请求的持久化定义)，保存位置为ArtifactStore的intake-command工件。PG通过material_operations.command_artifact_id关联artifact_objects；command_receipts.payload_digest与material_operations.input_digest均为规范化payload摘要，整个工件文件摘要另由artifact_objects.sha256维护。

只有工件已持久发布、字节验证通过，且命令回执/操作引用/启动意图全部提交后，information-submissions才返回202。工件失败、事务回滚或未确认提交不得返回accepted；并发同键胜者确定后只能返回胜者operation，不换绑失败方工件。返回202后API重启，后台可仅凭数据库引用恢复完整原输入；Workflow启动失败不撤销受理，由原启动意图重试。

POST受理阶段的存储失败返回503；后台读取受理输入失败由操作查询返回recoverable及INPUT_ARTIFACT_UNAVAILABLE/INPUT_ARTIFACT_INVALID，不表示客户端输入为空。响应不暴露对象存储路径或凭据；修复/恢复保持原请求内容与摘要。

## 8. 边界校验和查询响应

HTTP body 与模型 payload 使用受控 Ajv2020 校验器：strict=true、coerceTypes=false、useDefaults=false、removeAdditional=false。未声明字段直接拒绝；不会自动改类型、补业务值或删除模型多写的字段。URL 参数和 query 先按公开契约显式解析，再严格验证；错误映射到第5章的400/422。Fastify 默认校验可能进行类型转换和字段处理，不能直接视作本系统的严格校验，见[官方说明](https://fastify.dev/docs/latest/Reference/Validation-and-Serialization/)。

响应由显式 DTO 映射并经相同方言验证后使用标准 JSON 编码输出，不依赖未经验证的默认序列化器解释 2020-12 Schema。UUID/date-time 等格式由受控格式校验插件验证；不联网加载 Schema。错误体最多返回20项字段错误，避免超大错误响应。

Processings 查询必含 extraction_status、candidate_count（失败时null）、result_status、delivery_status、completed_count、dismissed_count、resolved_count、pending_count 和 candidate_refs。计数及终态按F02数据§3计算；全部候选合法dismissed可正常结束且保留原candidate_count，无消息时delivery_status=not_required。终态由数据库记录计算；不能把某次HTTP成功或Temporal完成映射为业务成功。权限检查在幂等回执返回前执行，撤权后即使持有原请求键也不能取得旧结果。

输入正文是 JSON content.text 的 UTF-8 编码原件；需要保留上传文件的 BOM 或原始字节时，必须采用未来另行定义的二进制上传契约。本文本入口不声称保存浏览器上传前不存在于请求中的文件字节。

F01资料版本号、执行代次和建议代次的 HTTP 字段及路径片段使用正十进制字符串，按 T01 的 bigint 传输规则校验；候选计数、页大小和字符偏移保持有界 JSON integer。客户端不可先转为可能失真的浮点数再发送。
