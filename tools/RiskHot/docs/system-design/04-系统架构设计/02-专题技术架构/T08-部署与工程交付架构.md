# T08 部署与工程交付架构

> V0.4 · 2026-10-24 · 仅部署边界与交付门槛设计，不含开发排期、实现代码或可执行部署配置。

## 1. 最小部署单元

| 单元 | 职责与隔离 | 持久化要求 |
| --- | --- | --- |
| Web / API | 用户命令、查询、权限；API不等待长模型调用 | 无本地业务状态 |
| Workflow Worker | 确定性流程推进；独立进程，不直接访问业务库/工件/模型 | 进度由Temporal历史支持 |
| IO Worker | 程序准备、资料处理、校验、正式事务；独立进程 | 业务结果进入数据库/工件存储 |
| 模型 Worker | 受控调用模型并保存响应；独立进程，无正式表写权限 | 尝试记录和响应工件 |
| 中继 | 启动意图与Outbox投递；可与Worker同主机部署，保持独立进程和权限 | 租约、尝试和回执持久化 |
| PostgreSQL | 业务与幂等真相 | 备份、恢复演练、访问隔离 |
| 对象存储 | 原件、正文、映射、模型证据 | 不可变引用、完整性验证、引用保护 |
| Temporal | 持久执行、超时及重试 | 独立运行存储与备份策略，不替代业务库 |
| 模型服务 | 固定任务包下的推理 | 不持有正式写入权限 |

开发验证环境可以单机容纳多个进程，但生产故障域不能由此视为已验证。对象存储可使用具有同等不可变/持久能力的受控适配，选型由PoC确认；不能用Worker临时目录充当已保存原件。

## 2. 环境与版本

隔离设计验证、集成验证和生产数据/凭据。环境清单固定应用契约版本、任务包、数据库逻辑版本、适配器与基础服务版本；实际运行版本、兼容范围和许可状态在进入实现时核验，本稿不指定未经测试的版本组合。

Worker升级要能处理在途固定任务包；不兼容版本通过独立队列或排空策略切换，旧运行不能静默换用新Prompt/Schema。数据库与消息契约采用可兼容增补、双读过渡及明确退出窗口；本轮未执行任何迁移。

## 3. 备份、恢复与回退

备份覆盖业务数据库、对象清单及对象、发布的任务/方法包。恢复后先验证数据库引用与对象摘要，再恢复启动中继与交付，防止把已提交动作重新执行。Temporal恢复另行核对业务回执；即使运行记录丢失也不能丢业务幂等历史。

应用回退不得回滚删除已生效事件、复核和交付事实；不兼容时先暂停受影响的新任务，保留读取与恢复通道。恢复时间/数据损失目标由用户规模与PoC测量后确认，不以本架构设计宣称零损失。

## 4. 交付门槛

先评审业务边界和接口，再进行机制PoC、受控契约/故障验证、真实模型质量评测，最后按证据验收。五项用户要求必须全部有执行证据，任何正式事件越过提交门槛属于阻断问题。真实模型语义与可用性不足时不能用替身通过记录宣布L0可生产使用。

本轮交付仅文档。具体实现任务、测试程序、数据库变更、上线和生产保障另行授权；完整待办见[验证总方案](../05-%E6%9E%B6%E6%9E%84%E6%B2%BB%E7%90%86%E4%B8%8E%E9%AA%8C%E8%AF%81/%E6%9E%B6%E6%9E%84%E9%AA%8C%E8%AF%81/L0%E6%9C%80%E5%B0%8F%E4%B8%9A%E5%8A%A1%E9%97%AD%E7%8E%AF%E9%AA%8C%E8%AF%81%E6%96%B9%E6%A1%88.md)及[ADR](../05-%E6%9E%B6%E6%9E%84%E6%B2%BB%E7%90%86%E4%B8%8E%E9%AA%8C%E8%AF%81/%E6%9E%B6%E6%9E%84%E5%86%B3%E7%AD%96%E8%AE%B0%E5%BD%95/ADR-L0-001-%E6%9C%80%E5%B0%8F%E9%97%AD%E7%8E%AF%E4%B8%8E%E6%AD%A3%E5%BC%8F%E6%8F%90%E4%BA%A4%E8%BE%B9%E7%95%8C.md)。

## 5. 首个L0验证环境的具体拓扑

选用单主机容器/进程隔离的验证环境，组件间采用私有网络；这不是生产高可用承诺。技术组合按 ADR-L0-002 的业务约束独立选择；从空环境建立组件，不读取旧工程依赖或自动挂载旧数据。首切片不要求 Kubernetes 或独立消息总线。

| 组件 | 端口/访问设计 | 状态与卷 | 调用关系 |
| --- | --- | --- | --- |
| Web静态资源及反向代理 | 对使用者提供HTTPS 443 | 构建制品只读 | /api转发API，其余静态资源 |
| Fastify API | 私网8080，不直接暴露公网 | 无业务本地状态 | PG、ArtifactStore；写意图，不等待模型 |
| Workflow Worker | 不开放用户端口 | 固定流程代码；不挂载资料卷 | Temporal工作流队列；不直接访问业务库或模型 |
| IO Worker | 不开放用户端口 | 固定任务包；受控工件卷 | Temporal程序活动队列、PG、ArtifactStore；不持模型密钥 |
| 模型 Worker | 不开放用户端口 | 仅授权输入/输出工件权限 | Temporal、受限运行记录、模型供应方；无正式表写权限 |
| Relay | 不开放用户端口 | 无独立业务状态，租约在PG | PG→Temporal/受控下游接收端 |
| PostgreSQL | 私网5432 | 独立持久卷与备份 | riskhot业务库；Temporal持久库隔离账号与库 |
| Temporal Server | 私网7233 | 使用持久数据库，不采用开发SQLite模式作为闭环验收基线 | Worker轮询、Relay启动/唤醒 |
| LocalArtifactStore | 无公开文件端口；受控读取经API | /var/lib/riskhot/artifacts独立持久卷 | API/Worker共享同一受控存储，跨主机扩展前替换适配 |
| 隔离交付接收端 | 私网受控入口或进程内端口 | 独立consumer_id与Inbox记录 | 只用于验证交付，不代表L1实现 |

若API与Worker分布到不同主机，不能继续各自读本地同名路径；必须先启用共享对象存储适配再扩展。模型并发2的首版限制依赖一个模型Worker组；多副本部署前增加共享配额/租约，不能让每个副本各自放大限额。

## 6. 配置归属、启动检查与最小运行参数

连接地址与凭据来自运行环境的密钥配置；文档不写密钥值。环境配置只负责PG/Temporal/ArtifactStore连接和模型供应方账户；任务行为由已发布method_manifest和runtime_policy定义，不靠临时环境变量偷偷改变Prompt或评分规则。

启动按进程职责检查数据库逻辑版本、对象存储读写、Temporal/Worker、任务 Schema、任务包和模型能力。API 的 `/health/live` 表示进程存活，`/health/ready` 表示接收能力；Worker 另报执行就绪状态。具体分界见第8章；查询就绪单独判断，不能因模型故障把已保存资料隐藏。

最小参数采用T02正文/候选限制及T03超时、重试、队列并发；前端对运行中operation每5秒轮询，完成或页面隐藏停止。无需引入WebSocket以证明闭环，未来需要推送时再基于持久状态提供增量通知。

## 7. 发布、恢复和新环境边界

API、Worker、Relay作为可独立发布进程，共用版本化应用核心。发布前登记契约版本、任务包摘要、校验器与数据库逻辑版本；在途旧manifest仍由兼容Worker执行，不因新版本上线改用新Prompt。

旧应用代码与工程配置已删除；保留的 .data 属于历史运行数据，不是新环境的初始化输入。未来执行验证必须明确使用真实模型还是受控响应替身，完成资料卷/PG/Temporal恢复一致性检查后才能给出运行验收结果。

## 8. 身份与访问拓扑

API 作为 OIDC confidential client，在服务端完成认证回调，浏览器只持有 HttpOnly 会话 Cookie。验证环境使用专用身份域；issuer、client_id、redirect_uri 和可信签名算法在部署清单固定，密钥由环境注入。身份服务提供登录事实，应用数据库提供角色和对象权限；无身份提供者或授权配置时阻止提交，不开放匿名管理员替代。

私网只允许 API/IO Worker/Relay 访问其授权数据库角色；模型 Worker 只取得运行记录和工件最小权限。PostgreSQL、Temporal 管理端和原件目录不公开。首切片同主机隔离不等于生产故障域隔离，生产需另行确定备份目标、可用性与密钥管理方案。

部署就绪分两类：接收就绪要求业务库、原件保存与权限服务可用；执行就绪要求任务包、Worker、Temporal 与模型能力可用。执行暂不可用但接收可持久化时可受理并明确展示 queued/dependency_unavailable；不得返回“分析成功”。积压达到运行政策上限时停止受理并返回可重试错误。

技术单元标识及业务映射统一见 [总体架构第5.4～5.6节](../01-%E7%B3%BB%E7%BB%9F%E6%80%BB%E4%BD%93%E6%8A%80%E6%9C%AF%E6%9E%B6%E6%9E%84%E8%AE%BE%E8%AE%A1.md)；本分册维护环境与部署参数。接收模块代码可装载在Relay中，通过模块端口提交Inbox/处理记录，数据库角色按接收职责授权，不能借此获得任意正式写入权限。
