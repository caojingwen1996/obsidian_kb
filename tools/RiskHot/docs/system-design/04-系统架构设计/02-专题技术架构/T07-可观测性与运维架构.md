# T07 可观测性与运维架构

> V0.1 · 2026-10-24 · 状态必须让使用者区分“业务完成、仍在处理、需复核、可恢复、待交付”。

## 1. 关联链与状态读模型

用correlation_id串联请求、Operation、processing_id、candidate_id、attempt_id、commit_key、event_revision_ref与message_id。每个运行节点记录输入摘要、方法包、开始/结束时间、结果类别、恢复点和父节点；不把原文放入普通日志。

查询分别展示：资料保存与交付状态、抽取完整性与候选数、逐候选处理状态、正式结果引用、下游交付状态。候选数未知显示“尚未确定”，不能显示0；部分候选完成显示partial及剩余项，不能用一条“失败”隐藏成功结果。

## 2. 指标与告警设计

| 观察项 | 用途 | 响应 |
| --- | --- | --- |
| 启动意图积压年龄、工作流未接收数 | 检测接收后未运行 | 检查中继租约与编排服务 |
| 模型超时/拒答/结构失败率、尝试预算 | 区分供应故障与资料问题 | 暂缓相应任务，保持可恢复状态 |
| 引用验证失败、不可读证据数量 | 识别定位或存储故障 | 阻止相关新提交，定位版本与规则 |
| 待复核数量及年龄 | 判断人工处理瓶颈 | 提示授权复核者处理 |
| 提交冲突/幂等命中次数 | 识别竞争与重复请求 | 核对上下文和回执，不直接重跑 |
| Outbox积压、回执延迟、重投次数 | 交付可靠性 | 重投原消息、检查接收端 |
| 业务已完成但运行未终止差异 | 检测运行投影漂移 | 按持久提交回执修复投影 |

阈值、采样与保留期尚待容量验证；不能凭空给出生产SLO。验收所需日志和完整记录独立保留，不能被采样丢弃。

## 3. 运维操作契约

运维仅发起业务模块支持的恢复命令：恢复原任务、重试交付、重新准备受影响上下文、申请授权重算。每次保存操作者、原因、旧新执行代次与结果。禁止直接把失败状态改为completed或手工插入Event来消除告警。

模型服务恢复后从未完成候选和原resume_step继续；数据库/对象恢复后先核对对象可读性、提交回执与Outbox一致性；工作流历史丢失按[T03](T03-%E4%BB%BB%E5%8A%A1%E7%BC%96%E6%8E%92%E4%B8%8E%E5%8F%AF%E9%9D%A0%E6%80%A7%E6%9E%B6%E6%9E%84.md)处理。已提交错误结果需业务纠正流程，不能由运维删除历史。

## 4. 验收证据

每个测试场景保存输入及方法摘要、状态转移、模型尝试、校验/审批、正式对象计数与修订、交付回执。仅截图不能证明幂等或故障安全。审计导出应脱敏，同时保留可由授权验收者回查的原文引用。未来执行结果登记至[验收报告](../05-%E6%9E%B6%E6%9E%84%E6%B2%BB%E7%90%86%E4%B8%8E%E9%AA%8C%E8%AF%81/%E6%9E%B6%E6%9E%84%E9%AA%8C%E8%AF%81/%E6%9E%B6%E6%9E%84%E9%AA%8C%E6%94%B6%E6%8A%A5%E5%91%8A/L0%E6%9C%80%E5%B0%8F%E9%97%AD%E7%8E%AF%E9%AA%8C%E6%94%B6%E6%8A%A5%E5%91%8A_%E5%BE%85%E6%89%A7%E8%A1%8C.md)。
