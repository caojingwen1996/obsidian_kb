# T01 数据与存储架构

> V0.9 · 2026-10-27 · 目标设计。本文是共享持久化、事务和身份约束的主定义；字段为逻辑契约，不是建表脚本。

## 1. 存储职责

PostgreSQL保存业务对象、版本清单、候选处理、方法引用、复核决定、提交回执及Outbox/Inbox。对象存储保存不可变原件、标准化正文/定位映射、模型输入输出与较大证据包；数据库保存其不可变引用、摘要、大小和可用性。Temporal负责推进，不作为正式事件或交付结果的唯一保存处。

| 记录组 | 所有者 | 最小内容 |
| --- | --- | --- |
| 资料与版本 | F01 | 来源身份、原件及标准化版本、映射清单、保存状态 |
| Processing / Candidate | F02 | 固定输入、analysis_key、候选集合、逐候选状态和恢复点 |
| 模型尝试 / 建议 | F02业务关联，S01运行投影 | attempt_id、输入摘要、任务包、原始响应、校验结果、有效代次 |
| 正式事件聚合 | F02 | Event、Fact、资料/事实/主体/变量/评价关系及原文证据；不保存事件版本 |
| MaterialReviewCase / MaterialReviewDecision | F01 | 按接入operation及决定代次冻结身份/版本比较依据、批准计划、操作者与理由；主定义见F01数据§6～7 |
| ReviewDecision | F02 | 授权人、决定、理由、proposal_digest、上下文与策略版本 |
| Operation / CommitReceipt | 应用命令与业务模块 | 请求摘要、幂等身份、接收结果、提交效果引用 |
| Outbox / Inbox | 发送模块 / 接收模块 | message_id、业务修订、接收者、尝试、持久接收回执 |

## 2. 身份与唯一性

| 层次 | 建议唯一键 | 效果 |
| --- | --- | --- |
| 接口请求 | 权限空间 + command_type + client_request_key | 同键同请求返回原回执；同键不同请求冲突 |
| 资料身份 | source_id + 标识命名空间/作用域 + 稳定来源标识 | 同源同一资料聚合；跨来源不因文本相同合并 |
| 资料版本 | information_id + 程序核定的版本判据 | 防并发重复保存；判据见F01数据设计 |
| 首次事件处理 | information_id + information_version_ref + INITIAL | 同版本普通重交不因模型升级而重新抽取 |
| 授权重算 | information_id + version + 新analysis_key | 保留父处理及原因，与普通重试区分 |
| 候选 | processing_id + candidate_key | 固定集合内稳定；模型自报序号不能直接充当跨重试身份 |
| 业务提交 | candidate_id + 有效决策代次构成commit_key | 重复提交回原结果；旧代次不能提交 |
| 事件提交 | commit_key及对应运行操作唯一；event_fact约束唯一归属 | 复用回执，锁内核对当前内容与关系摘要；不建立事件版本 |
| Fact与评价效果 | 运行输出项与Fact连接、提交回执与评价连接 | 原操作重试复用效果；语义Fact复用和评价范围/依据由业务核验，不再使用event_update变化键 |
| 消息接收 | consumer_id + message_id | 多次投递只产生一次接收效果 |

资料身份规则版本作为审计属性，不进入稳定身份唯一键；规则升级通过显式别名映射关联既有身份，映射冲突转复核，不能自动另建Information。

以上键必须由程序生成或验证并持久保存。摘要键保存规范化规则及原始判据；同摘要但判据不同作为冲突处理，不能盲目复用。跨资料事件语义去重仍需AI-02及复核，不是散列函数能解决的问题。

## 3. 事务边界

- **接收事务**：F01先持久发布完整请求工件，再在单一事务中锁artifact_objects确认ready，同时写命令幂等记录、绑定工件及摘要的material_operations和启动意图。三者全部提交后才返回202；完整载荷定义见F01数据§7.1.1。其他命令也必须能从受理记录恢复输入，不能只存摘要和执行身份。
- **资料保存事务**：先在事务外完成对象写入、摘要与可读性校验，再写不可变版本清单和交付意图。对象与数据库不具有跨系统原子性；对象成功但事务失败留下可识别暂存对象，不能暴露为完成资料。
- **候选集合事务**：校验完整抽取结果后，用处理代次条件写入候选集合、count、抽取完成状态及逐候选启动意图；并发返回只允许一个结果被接纳。0候选也写完成记录。
- **候选提交事务**：锁定候选有效代次及目标事件当前内容，复核提交门槛；写适用业务对象、Fact关系、证据、操作审计、提交回执、候选完成和Outbox；更新处理汇总。全部成功或全部回滚。不得把模型调用放在事务中。
- **非事件处置事务**：按F02数据§3.1复核当前权限与候选依据，原子写NOT_EVENT处理回执、审计、dismissed终态及批次汇总；不写正式事件聚合、集合版本或事件变化消息。
- **接收消息事务**：接收方Inbox、业务接收记录和后续启动意图一起提交，然后返回接收回执；消费后的具体业务完成另行记录。

事件锁按稳定身份顺序取得，失败释放后重试。新建事件的已确认身份决策引用须唯一消费，防同一决策重复建事件。不同候选的新建还须通过事件集合版本校验：召回快照记录catalog_epoch，正式提交在集合锁内比较；过期决定退回身份归组及复核，不能只改版本号继续提交。集合与快照表、版本推进条件及失效协议由F02数据设计第6、7.2节维护。

## 4. 版本与对象生命周期

原件、正文、分段映射及模型输入均不可就地覆盖；版本清单串起原件摘要、处理规则版本、标准化摘要与证据包摘要。对象缺失或校验失败时阻止新分析/新提交，显示既有结果的证据不可用状态并修复，不能生成替代原文掩盖损坏。

清理只能针对无已提交引用且超过保留政策的暂存对象；在途任务、待复核和历史修订引用均保护。删除/脱敏必须有授权和引用影响记录；生产保留期未定，不默认立即清理。备份恢复同时核对数据库引用与对象清单，见[T08](T08-%E9%83%A8%E7%BD%B2%E4%B8%8E%E5%B7%A5%E7%A8%8B%E4%BA%A4%E4%BB%98%E6%9E%B6%E6%9E%84.md)。

## 6. PostgreSQL物理模型与类型约定

本节将业务不变量落实为目标物理表，选用 pg 执行显式参数化 SQL。新环境从空库建立结构；F02具体表结构统一见 [[tools/RiskHot/docs/system-design/04-系统架构设计/01-数据模型与存储设计/F02事件管理模块数据模型与存储设计|F02 数据模型与存储设计]]；本节只保留F01与共享运行约定，不重复F02表定义。业务表位于 information schema，共享执行表位于 platform。关系字段由数据库约束，灵活建议与快照由 JSONB 承载。此处仅定义设计，未编写或执行迁移。

统一类型：程序分配UUID v4主键；系统时间用timestamptz并输出UTC ISO 8601；F02的event_time按单字段部分日期口径存储；顺序/代次用bigint；SHA-256摘要用bytea并限定32字节；状态用text配数据库CHECK；可变建议和不可变快照用jsonb。ID/外键/状态/修订号/业务幂等键不得仅放JSONB。范围键、稳定键限定字节长度，超长原始判据另存并比较，不依赖无限长文本B-tree键。

| 表 | 核心列（省略通用created_at/updated_at） | 主键、唯一性及关系 |
| --- | --- | --- |
| information.materials | id uuid、source_id uuid、identity_namespace text、identity_digest bytea、identity_value text、current_version_id uuid?、row_version bigint | PK id；UNIQUE(source_id,identity_namespace,identity_digest)；摘要命中还比较identity_value |
| information.material_versions | id uuid、information_id uuid、version_no bigint、kind text、parent_version_id uuid?、version_commit_key uuid、manifest_artifact_id uuid、status text | PK id；UNIQUE(information_id,version_no)、UNIQUE(information_id,version_commit_key)、UNIQUE(information_id,id) |
| information.material_segments | id uuid、version_id uuid、ordinal int、normalized_text text、codepoint_count int、locator jsonb | PK id；FK version_id；UNIQUE(version_id,ordinal)、UNIQUE(version_id,id) |
| information.processing_runs | id uuid、information_id uuid、version_id uuid、analysis_key text、parent_id uuid?、candidate_count int?、extraction_status text、result_status text、execution_generation bigint、cancel_requested_at timestamptz? | PK id；UNIQUE(information_id,version_id,analysis_key)；组合FK(information_id,version_id)→material_versions(information_id,id) |

`candidate_count`只有抽取成功后才能非空，数值非负；抽取失败不能写0。Schema外键列顺序必须一致：版本表的复合键为(information_id,id)，处理表引用使用(information_id,version_id)。正式事件/Fact/关系的物理表见 [[tools/RiskHot/docs/system-design/04-系统架构设计/01-数据模型与存储设计/F02事件管理模块数据模型与存储设计|F02 数据模型与存储设计]]，资料扩展表见F01数据§6。

材料版本information_id外键指向materials，parent引用使用同资料的复合外键；materials以(id,current_version_id)引用material_versions(information_id,id)，保证当前版本属于本资料。当前指针首建时为空、row_version初始0；首次保存或经确认的新当前修订才在同事务更新指针并递增row_version。REUSE及历史晚到不更新两者，返回历史版本回执不等于改变当前版本。新增version_no在资料锁内按该资料max+1分配，父版本固定为已校验的当前版本；完整分支由F01数据§6.3.1维护。循环引用延迟到事务结束校验。Fact 与运行输出项通过独立连接记录关联；原 candidate 运行身份的迁移映射保留，业务事实以 Fact 为准。

## 8. 事务隔离、锁顺序与索引选择

采用READ COMMITTED + 显式行锁 + 条件更新 + 唯一约束。模型等待期间不持数据库事务。首切片增加事件集合行锁，短暂协调召回读取与正式事件写入；不锁住资料接入、模型分析或人工复核全过程。正常查询使用B-tree；大JSON响应不默认加全字段GIN，只有经查询验证需要的路径再建索引。

候选提交统一锁序：权限代次共享锁 → processing_runs → Fact运行关联与Fact → 共享集合协调记录 → 已存在event（多个时按UUID排序）。已完成候选在取得集合锁之前回原回执；NEW在集合锁内校验召回版本，REUSE校验批准时的当前内容与关系摘要。所有事件创建及当前业务内容写入都遵循集合锁协议，并同事务推进catalog_epoch；NO_CHANGE不推进。取消、复核变更和恢复也先锁同一processing/candidate行，避免取消与提交的检查竞态。批次汇总在同一事务更新。

召回短读事务取得权限代次共享锁后，只取得集合行共享锁，不反向申请processing/candidate/events行锁；在锁内读取集合协调标记、匹配事件及当前内容摘要，然后释放锁，事务外生成工件和调用模型。其他受控事件写入口同样先集合、后events；不得持events行锁再申请集合锁。相关记录与范围策略见F02数据设计第7.2节。

F01复核、恢复和保存统一先取得权限代次共享锁，再锁material_operations、复核案件（如涉及）、materials（多个按UUID排序）并核对row_version；交付恢复再按material_deliveries → platform.message_deliveries顺序锁定。任何路径不得持materials锁反向取得operation锁。同一来源新身份并发时先尝试唯一插入，冲突方读取已有身份，再在锁内复核实际判据。数据库摘要冲突、序列冲突或更新影响行数为0时返回明确冲突，不通过重新分配随机ID掩盖。

消息领取用到期筛选和`FOR UPDATE SKIP LOCKED`形成短租约事务，网络发送在事务外。确认发送结果须同时匹配lease_token，防止过期工作者覆盖新的投递状态。索引聚焦状态/到期时间、事件提交与固定身份；对象查询禁止一次加载全部JSONB记录到内存再过滤。

## 9. 类型传输、连接和错误处理

同一提交事务始终使用一个 pg 客户端连接，取得连接后进入事务，失败回滚并在 finally 释放；不能混用连接池上的独立查询执行事务中的步骤。该约束依据 [pg 官方事务说明](https://node-postgres.com/features/transactions)。

数据库 bigint 在 JSON 边界编码为十进制字符串，避免超过 JavaScript 安全整数后发生修订/代次错误；数量和偏移使用受限 int。金额和 M 计算使用十进制计算策略，numeric 对外采用十进制字符串或明确的定标整数，禁止二进制浮点误差改变评分结果。摘要对外为小写十六进制字符串，服务端验证后转换为固定 32 字节。

设计默认：API 连接池上限 10，IO Worker 8，Relay 2；每事务 lock_timeout=2 秒、statement_timeout=5 秒，总事务预算 10 秒。它们是单机验证参数，需实测后调整。池耗尽返回可恢复忙状态，不无限排队；SQLSTATE 23505 按具体唯一键判断重放/业务冲突，23503 和 23514 作为约束错误阻断；40P01/40001 允许按原提交身份有界重试；提交时断连先查回执，不能直接判断失败并换键。

正式写入前先取得 T06 定义的权限代次共享锁，再按第8章业务锁序执行；撤权取得同一权限行排他锁。外部身份服务或模型调用不进入该事务。
