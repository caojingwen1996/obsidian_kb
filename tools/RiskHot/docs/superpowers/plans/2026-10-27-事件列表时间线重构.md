# 事件列表时间线重构计划

> 日期：2026-10-27。状态：已按批准规格实施并完成本机验证；本轮未提交或推送代码，未变更真实业务数据。
> 主设计方法：Impeccable / Operate，沿用 RiskHot 现有浅色绿色视觉。本文存放于既有工程计划目录，不调用 Superpowers 工作流。

## 1. 目标与依据

将 `/events#events` 的简单双列列表改为按时间分组的事件时间线。用户浏览时可以直接识别事件的时间、信源、标题、description 和业务阶段，再进入正式事件详情。

输入依据：

- 用户提供的参考截图：日期与星期分组、左侧时间和节点、右侧连续内容卡片、来源与正文分层。
- 用户确认的排序规则：新闻发布后72小时内被收录，采用系统首次收录时间；超过72小时才收录，采用原文发布时间；按所得展示时间倒序。
- [[tools/RiskHot/docs/system-design/03-系统功能架构/F02 事件管理模块功能设计 V1.0|F02 功能设计]]：默认进入正式事件列表，详情读取当前 Event、关联 Fact 与原文证据。
- [[tools/RiskHot/docs/system-design/04-系统架构设计/01-数据模型与存储设计/F02事件管理模块数据模型与存储设计|F02 数据模型与存储设计]]：来源经关联关系推导；发生时间允许年、月、日、完整时刻或空值。
- [[tools/RiskHot/docs/system-design/06产品UI原型设计/标题区域设计规范|标题区域设计规范]]与当前实际页面：继承字体、间距、配色、焦点及窄屏规则。
- [[tools/RiskHot/docs/system-design/工程开发与实现步骤|工程开发与实现步骤]]：按查询、页面、验证拆分可检查的实施任务。

## 3. 页面方案

### 3.1 布局

保留侧栏、顶栏和“正式事件 / 信息接入任务”工作区导航。正式事件内容区采用单列时间线，不增加大幅介绍区或统计卡。

```text
正式事件                         按展示时间 · 最新在前

10月27日  星期二 · 本页2条                         [收起]
 16:11  ● ┌────────────────────────────────────────────┐
        │ │ 信源名称                      已完成       │
        │ │ 事件标题（点击进入详情）                    │
        │ │ description：当前事件的事实、数字和条件…  │
        │ │ 另2个关联信源 ▾                            │
        │ └────────────────────────────────────────────┘
 时刻   ● ┌────────────────────────────────────────────┐
 未明确 │ │ 信源名称                      已宣布       │
          │ 事件标题                                   │
          │ description…                               │
          └────────────────────────────────────────────┘

10月26日  星期一 · 本页1条                         [收起]
 ……

                         上一页  下一页
```

示意中的数量、时间和名称仅说明结构，不作为实际数据。

- 日期标题比卡片标题更明显；跨年时展示年份，日期组默认展开，可折叠。
- 左侧为窄时间列、节点和1px连接线；右侧为白色、细边框的内容卡片，卡片高度随正文变化。时间线按日期组断开。
- 信源为第一行次级信息；标题为主要可点击链接；description 紧随标题；阶段作为辅助文字，不占据与标题同等视觉权重。
- 首版 description 完整展示、自然换行，不生成新的 AI 摘要。通过字号、行距和段落留白控制阅读密度。
- 不套用参考图中无现有业务依据的“精选”“推荐理由”、作者头像或社交账号信息。信源名称来自真实信源档案。
- 卡片内有独立展开操作，避免将包含按钮的整个卡片包在链接中。标题链接支持键盘、新标签页和浏览器原生操作。

### 3.2 每条事件的信息

| 展示信息 | 真实来源 | 处理规则 |
| --- | --- | --- |
| 时间 | 按72小时规则计算的展示时间 | 规则见第4节；显示“首次收录”或“原文发布”依据，可查看两项原始时间 |
| 信源 | `m1.sources.name`，经事件/候选/资料关系获取 | 按信源ID去重；同名不同ID不直接合并 |
| 标题 | `event.title` | 全文换行，点击进入现有详情 |
| description | `event.description` | 展示当前已保存描述；输出转义，不使用资料标题替代 |
| 阶段 | `event.event_status` | 复用现有中文映射；未知值有明确回退 |
| 其他信源 | 同一事件的其他关联信源 | 显示“另N个关联信源”，展开显示名称；不暗示它们均支持同一结论 |

多信源的最终展示顺序将时间计算所用原文的信源放在首位，其余按首次建立来源关联的时间、信源ID稳定排序。首位不声明为全网首发或权威主来源。来源关联时间不作为新闻首次收录时间。

首版来源展开显示名称；时间说明展示所采用原文的信源、原文发布时间、首次收录时间及选择依据。原文阅读沿用详情中按 Fact 组织的证据入口，不把信源主页链接当作具体原文。

### 3.3 窄屏与可访问性

- 1440px及常规桌面显示左侧时间列；390px和320px收窄时间轴，时间必要时移入卡片顶部，description 使用可读字号自然换行。
- 日期组、卡片与标题保持正确标题层级；可解析时间使用 `<time>`，部分日期不生成虚构完整时间。
- 展开控件有明确名称与展开状态，点击区域至少44px；焦点轮廓沿用现有绿色规范。
- 长信源、长标题、URL式长词、缺失信息不会造成页面横向滚动。

## 4. 展示时间：用户已确认的72小时规则

原先建议的“按事件发生时间”已被本节替代。时间轴的日期、左侧时分和倒序排序统一采用**展示时间**；业务发生时间 `event_time` 保留原语义，不参与72小时判定。

### 4.1 核心规则

设 `P` 为新闻原文发布时间，`C` 为该新闻在系统中的首次收录时间，`D` 为展示时间：

```text
收录延迟 = C − P
0 ≤ 收录延迟 ≤ 72小时：D = C（首次收录）
收录延迟 > 72小时：    D = P（原文发布）
列表按 D 倒序排列。
```

- “72小时内”包含恰好72小时，按连续经过时间计算，不按三个自然日计算。
- 比较的是首次收录与原文发布的时间差，不是“当前时间减发布时间”；一条新闻不会仅因浏览时间推移而自动切换排序依据。
- 最近发布且及时收录的新闻出现在收录时点；迟到的历史新闻回到原文发布时间，不因补抓旧闻而挤到列表顶部。
- 重试、重复抓取、资料重新解析、正式事件稍后建档、审核通过及普通更新时间，都不能重置首次收录时间。
- 完整时刻统一为可比较的瞬间后计算时差；页面按 `Asia/Shanghai` 归日和显示。同一展示时刻以事件ID稳定排序。
- 时间旁或可展开说明中标记“首次收录”/“原文发布”，并可查看原始 `P`、`C` 和选择依据。

| 原文发布 P（北京时间） | 首次收录 C（北京时间） | 收录延迟 | 展示时间 D |
| --- | --- | --- | --- |
| 10月27日 08:00 | 10月27日 16:11 | 8小时11分 | 10月27日 16:11，首次收录 |
| 10月24日 09:00 | 10月27日 09:00 | 恰好72小时 | 10月27日 09:00，首次收录 |
| 10月24日 09:00 | 10月27日 09:01 | 72小时1分 | 10月24日 09:00，原文发布 |

### 4.2 数据对应与多信源：实际采用规则

以下策略最初由计划提出，后经批准规格纳入实施范围；当前按此实现，保留其与用户原始72小时公式的来源区别：

- 已核对 `information.material_version_origins.collected_at` 来自首次保存该版本的 `information.acquisitions.acquired_at`，相同版本重用时不会重写；原文发布时间文本保存在对应 `information.material_versions.published_at_text`。
- 通过 `event_fact → fact_evidence → material_versions → material_version_origins` 定位实际支撑事件的原文及版本。只使用可追溯的成功收录记录，不使用失败请求时间、首次发现链接时间、Fact保存时间或 `event.created_at`。
- 以新闻资料身份去重，核对其支撑本事件的首个已收录版本；取该版本绑定的首次采集记录和原文发布时间作为一对 `C/P`。后续来源修订或重复抓取不能把新版本采集时间直接当成原新闻首次收录时间。若首次新闻版本与事件证据版本有差异，当前仅允许实际事件证据版本参与，未采用无本事件证据的更早资料版本，不跨版本拼凑时间。
- 同一 Event 有多篇新闻时，选其中最早被系统成功收录、且支撑本事件的原文作为时间依据；同刻按资料ID/版本ID确定次序。展示其信源及依据版本，其他信源汇总展示。不得拿A新闻的首次收录时间与B新闻的发布时间计算时差，也不取各来源展示时间的最大值将旧事件反复置顶。
- 补充更早的有效历史证据或纠正原文时间，可能使时间依据和位置变化；普通新增转载不能以其较晚收录时间将已有事件置顶。变化应有明确来源依据，刷新时保持阅读锚点。

### 4.3 缺失、低精度与异常时间：实际降级规则

- `published_at_text` 目前是文本，必须按实际格式、日历合法性及明确来源时区解析；无时区且来源也没有可靠时区依据时，不猜测完整时刻。
- 仅有日期/月/年的发布时间按上海日历范围判断；成功收录使该低精度范围上界收紧至C，不改变输出精度：整个范围均落在收录前72小时内时可取 `C`；整个范围均早于72小时门槛时取原文时间并保留原精度；范围跨越门槛时不能宣称已精确判定。
- 原文时间缺失、无法解析、未来时间导致负延迟，或低精度范围跨越72小时门槛时，采用可验证的首次收录时间，并标注“按首次收录展示，发布时间待核实”。这是异常降级规则，不标成已满足72小时条件。
- 首次收录证据缺失时，采用可验证的原文时间并标注“首次收录时间待核实”；两者都不可用时进入“展示时间未明确”区域，按ID保持稳定。不得以现在、事件建档时间或最新更新时间假冒首次收录时间。
- 展示时间只有日期时，在对应日期组显示“时刻未明确”；只有月/年时进入完整日期组之后的独立“展示日期不完整”区域，按范围起点倒序、原值及ID稳定排序；未知最后；标明精度，不补造午夜。
- 每个日期组的数量标记为“本页N条”；服务端应用权限和展示时间全局排序后分页，前端不对已经截断的单页数据冒充全局排序。

## 5. 已实现查询与接口契约

复用 `GET /api/v1/l0/events`，保持现有分页参数和响应的 `items / next_cursor` 外层形态。当前接口已提供以下派生字段，权威口径见[[tools/RiskHot/docs/system-design/04-系统架构设计/03-模块技术详细设计/L0-信息处理层/F02-事件管理/事件数据与状态设计#8.1 正式事件时间线查询契约|现行查询契约]]：

- 保留 Event 当前字段；新增 `sources` 摘要集合，每项只返回信源ID、目录键及展示名称。
- 已增加派生列表字段 `display_time`、`display_time_basis`、时间精度、`first_collected_at`、`published_at`及其原始文本、依据资料/版本标识；字段名已在查询契约中固定。展示时间属于查询视图，不写入或覆盖 Event 的 `event_time`。
- 先为有权访问的全部候选 Event 批量解析来源时间、选定依据并计算展示时间，再全局排序和分页；分页后批量补齐当前页来源展示信息。不能先按 `updated_at` 截取一页再计算展示时间。不得逐事件请求详情，也不得因关联多条 Fact/资料造成事件重复、条数膨胀或信源重复。
- 沿用现有整事件可见性规则：关联来源中存在无权读取的来源时，该事件不可见。列表字段、计数和分页都采用同一规则，不通过来源名称或数量泄露不可见信息。
- 缺失来源显示“信源信息暂缺”；查询失败显示失败与重试，不伪装为空来源或空事件。
- 实际复用已有采集来源记录，无迁移；同时校验采集工件、首次时间及采集操作与origin一致。应用层为全部可见证据及每事件版本排序，分页后排序该页来源；成本与规模限制已记录于查询契约。后续扩大规模如需规范化发布时间或读模型，须另做存储与回填设计；本轮没有逐事件读取原文工件的N+1。

分页沿用现有偏移方式：静态数据下保证稳定顺序；并发新增或时间纠正可能影响跨页位置，这一边界必须在验证中记录，不宣称具备快照分页保证。首版不引入无限滚动或新的分页协议。

## 6. 交互与状态

1. **进入列表**：读取按72小时规则全局排序后的一页正式事件，按展示日期分组；未归组 Fact 不混入正式事件时间线。
2. **阅读来源**：单信源直接显示；多信源展开不会打开事件详情。日期组和来源展开状态在当前列表刷新后保留。
3. **进入详情**：点击标题沿用当前事件地址，并携带经过校验的列表页上下文；详情上方的“返回事件列表”恢复该页与事件锚点。单独打开详情且无列表上下文时返回首页。
4. **返回与刷新**：同一浏览会话保存页码、阅读锚点和展开状态；恢复时以事件ID定位优先，没有可用卡片锚点时恢复日期标题位置或已保存滚动；缺少有效快照才定位页首。浏览器后退和显式返回按钮均验证。
5. **分页**：沿用每页20条及上一页/下一页；切页后定位列表顶部；禁用/隐藏不可用翻页方向。
6. **自动更新**：无变化不重建DOM；有变化时保留键盘焦点、展开项和当前可见事件锚点。状态在替换DOM前捕获，包含请求等待期间最新滚动、折叠及summary焦点；全部日期折叠也恢复日期位置。
7. **异常状态**：首次加载、无事件、读取失败、权限不足分别展示。已有列表发生临时故障时保留已读取内容，并说明刷新失败；401/403清空受限内容。详情失败或重试不覆盖先前列表快照。

## 8. 验收标准

| 编号 | 场景 | 预期结果 |
| --- | --- | --- |
| TL-01 | 多天、多事件 | 日期组及其事件按72小时规则所得展示时间倒序；同一事件只出现一次 |
| TL-02 | 单条事件 | 信源、标题、description和阶段可直接阅读，标题可进入详情 |
| TL-03 | 一事件关联多个Fact和来源 | 按信源ID去重，数量正确，展开后名称完整，不重复事件卡片 |
| TL-04 | 完整时刻跨UTC日期 | 按上海时区显示日期与时分，日期组正确 |
| TL-05 | 日、月、年、空时间及异常原文时间 | 按第4节保留精度、说明降级依据，不补造时分；不修改业务发生时间 |
| TL-06 | 超过20条、同日跨页 | 全局排序后分页，日期标题与“本页”数量准确，静态数据无重复遗漏 |
| TL-07 | 从第二页进入详情再返回 | 返回原列表页和阅读锚点；直接打开详情后仍能返回列表首页 |
| TL-08 | 刷新时存在展开项或键盘焦点 | 保留阅读状态；失败时不清空已有列表 |
| TL-09 | 部分来源不可访问 | 与现有详情权限一致，不泄露事件或来源名称与计数 |
| TL-10 | 空列表、请求失败、来源异常 | 有各自明确状态和可执行的恢复入口，不用假数据补齐 |
| TL-11 | 长标题、长description、特殊字符 | 正确转义、完整可读，无脚本注入和横向溢出 |
| TL-12 | 1440/390/320像素与键盘操作 | 时间轴、卡片、分页和展开操作可用，焦点可见，截图复查通过 |
| TL-13 | 收录延迟为0、72小时减1毫秒、恰好72小时、72小时加1毫秒 | 前三者取首次收录时间，最后一项取原文发布时间；不得取当前时间参与判定 |
| TL-14 | 同一新闻重复抓取、重新解析、延后建档或普通转载补充 | 首次收录依据不被重置，事件不因这些动作被重新置顶 |
| TL-15 | 多来源及原文修订 | 同一篇原文的C/P成对，版本依据可追溯，来源聚合不改变事件唯一性 |
| TL-16 | 今天补抓一篇发布超过72小时的旧闻 | 落在原文发布日期组，保持全局倒序；等待一天或再次刷新不改变判定 |

验证按最快相关检查开始：先运行页面单元测试，再查询/API专项测试和 `npm run typecheck`，最后运行隔离浏览器及真实页面验证。实际命令、结果和证据写入验证记录；测试数据只能进入隔离测试环境。
