## 三、实施选择及依据

采用“现有消息 + 固定交付工件 + 明确回执”的方案：保留原 `message_id`、Inbox 和处理记录，避免迁移出第二套消息身份。交付包由 F01 产生，F02 只读消费。

单独增加一个导出命令只能解决人工找文件，无法证明下游接收与恢复，因此不作为闭环实现。把整个流程迁移到新消息服务会扩大范围且缺乏当前业务必要性。

以下文件协议和物理补充是本计划提出的实现决策，等待本次计划确认；不冒充已发布的 M3 方法或完整系统技术协议。

### 3.1 文件位置与发布规则

运行时以既有 `ARTIFACT_ROOT` 为根目录，不增加环境变量。当前本机对应：

```text
/Users/cjw/dev/Obsidian/wiki/tools/RiskHot/.riskhot/artifacts/
  <摘要前两位>/<完整摘要>                    既有不可变工件
  handoffs/f01-f02/<delivery_id>/
    information.json                        F01 固定资料交付包
    receipt.json                            F02 固定接收回执
    analyses/<processing_id>/candidates.json 抽取完成后的完整候选结果
```

- `delivery_id` 直接使用已有 `platform.messages.id`。同版补发、恢复和重新采集命中同版时仍使用原目录。
- 每个 JSON 文件采用 UTF-8、`application/json`、末尾换行；内容先经 ArtifactStore 不可变发布和摘要核验，再以硬链接原子发布上述可读名称；文件权限沿用私有工件权限。
- 可读名称指向同一份已登记字节，不建立可人工修改的第二份资料真值。JSON 内不写绝对主目录、密码、令牌或完整私有配置。
- 文件路径的所有身份由服务端生成并校验为 UUID；原件路径只由已验证摘要产生。消费者不允许读取客户端给出的任意路径或 URL。
- 发布中断不能留下可见半文件。文件已生成但数据库事务未提交，不算接收；以数据库绑定和有效回执为准。可读名称缺失时允许从已登记工件重新建立，摘要冲突时阻断，禁止覆盖未知内容。
- 原件仍是 F01 的既有工件，交付包只保存引用。标准化正文嵌入 `information.json`，同时保存其原工件引用和字节摘要，以便直接阅读和核对。

### 3.2 `information.json` 的版本化格式

Schema 标识固定为 `riskhot.information-handoff.v1`，未知版本拒收。使用严格结构校验；字段如下，来源未知的可空字段明确为 `null`。

| 字段 | 内容与约束 |
| --- | --- |
| `schema_version`、`delivery_id`、`consumer` | 固定 Schema、原消息 UUID、`F02` |
| `information` | `information_id`、`version_id`、`version_no`、`previous_version_id`、`version_kind`；首次为 `initial`，按现有保存算法确认的新修订为 `source_revision` |
| `source` | `source_id`、实际 `source_config_version`、来源名称/目录键、连接器和采集范围；取历史配置白名单字段，不读取当前配置替代 |
| `provenance` | 原保存操作、原获取记录、`collected_at`、原件获取地址；时间采用真实获取记录，不能用导出时间代替 |
| `material` | 当前 `NormalizedMaterial` 的完整已保存内容；保留段落 ID、表格、数字、单位、原始定位及时间原文 |
| `artifacts` | 原件与标准化工件的 `artifact_id`、SHA-256、字节大小和由摘要生成的固定存储定位 |
| `normalization` | 解析器版本、正文语义摘要、标准化检查结果、已知采集限制和附件范围状态；未采集附件不得声称附件完整 |
| `saved` | 原保存操作、已保存版本和保存时间；复用版本保留原保存依据，当前重新获取操作另查原操作记录 |

取得时间、发布时间、观测时间和快照时间保持各自含义。发布时间的原始文本和已知精度单独表达；只能确定日期时记录日精度，无法判断则精度未知，禁止补造时分秒。已有 `publishedAtText` 原值保留。

交付包记录的是资料输入，不包含模型密钥、实时登录状态或客户端自报权限。M3 的 Prompt 草案只作为现有候选切片的固定运行依据，不能标记为正式发布方法。

### 3.3 `receipt.json` 与 `candidates.json`

接收回执 Schema 为 `riskhot.information-receipt.v1`，包含 `delivery_id`、`information_id`、`version_id`、交付包工件和 SHA-256、`processing_id`、固定 `analysis_key`、`accepted_at` 与 `status: received`。它证明可靠受理，不跟随抽取状态重写。当前抽取状态通过查询接口取得。

候选文件 Schema 为 `riskhot.candidate-result.v1`，在集合成功接纳后生成，包含：资料身份/版本、交付与接收引用、`processing_id`、分析范围、输入/方法工件、完成时间、候选数量，以及每项已固定的 `candidate_id`、`candidate_key`、`ordinal`、`status` 和完整 `payload`。同时包含 `covered_segment_ids`、`no_event_reason`、`warnings` 和当前切片限制。

非空候选标明下一业务步骤为 F02 Step 2，候选仍为待处理；完整合法零候选为 `NO_EVENT`，附原因为正常结果。抽取未完成不生成成功结果文件，也不生成空候选占位文件。文件导出失败单独记录并修复，不撤销已接纳候选、不再次调用模型。

### 3.4 版本关联和历史兼容

新增版本在保存事务中固定来源配置、获取记录、保存操作、前版和版本性质；复用旧版不得把本次来源配置或抓取时间写回旧版依据。原消息与交付记录在同一保存事务中创建或复用。

现存版本仅在能够找到原件、标准化工件均匹配的原保存操作及真实获取记录时回填依据；有多个不一致解释或缺失依据时标为待核对。前版按现有保存算法及版本顺序核验；不能确认时不猜测。

历史已接收消息保留原 Inbox 时间和 `processing_id`，回执注明 `acceptance_basis: legacy_inbox`；新核验和导出时间单独记录，不伪装成历史时刻已执行新增校验。历史抽取原输入/方法不改写。历史合法结果未独立留存无事件原因时，尝试从原响应与固定输入重新校验恢复；不能恢复则明确说明缺失，不编造原因、不重跑模型。

### 3.5 重复处理与异常恢复

| 情况 | 处理规则 |
| --- | --- |
| 同资料、同版本重复交付或两个 Relay 并发接收 | 唯一 `(version_id, consumer_id)`、原消息及 Inbox 去重；返回相同接收和处理身份 |
| 同请求键、不同恢复请求体 | 沿用 `Repository.action()`，返回 409；先鉴权再查旧回执 |
| 接收事务已提交但响应丢失 | 查原 Inbox 和回执，补齐文件入口；不新建处理或启动意图 |
| 版本原件/正文缺失、摘要错或版本引用不匹配 | 接收前阻断，交付待恢复；不能产生 `received` 或 `NO_EVENT` |
| 来源停用、当前权限失效或任务已暂停 | 不接收新交付，不启动模型；恢复后再次检查当前资格 |
| 来源配置在保存后变化 | 内容仍按原保存版本和旧配置读取；当前资格另外检查，不混用新配置 |
| 模型失败/超时/额度或登录异常 | 资料仍已接收，抽取数量未知；沿用原输入、方法、代次和现有模型恢复策略 |
| 候选已完整接纳后再次交付 | 返回原候选清单和稳定身份，不调用模型；将来的归组仅续接未完成候选 |
| 候选/回执文件发布失败 | 重建同一数据库结果的文件，不重新接收、抽取或保存候选 |
| 新内容版本被 F01 确认并保存 | 新版本单独交付；绑定原前版供未来 F02 增量判定，不沿用旧候选冒充新结果 |

交付使用独立恢复代次和租约围栏。沿用 F01 §7.4 的每窗口最多 10 次，累计尝试不清零；复用现有 Relay 的 60 秒租约和 30 秒故障退避。窗口耗尽为待恢复；有权限的恢复命令开启新窗口，保留原消息并记录理由。文件发布不消耗模型预算。每条交付独立捕获失败，避免一个坏文件阻断其他来源。

接收后的文件修复也采用独立的每窗口 10 次及 30 秒退避；文件恢复代次、计数和错误与交付窗口分别保存。窗口耗尽后提供授权“重新生成文件”，不重置接收回执或模型预算。文件操作只恢复缺失的可读名称或尚未完成的派生输出；真值工件缺失/损坏时保留明确阻断，不能从未验证内容覆盖。

## 四、审查重点

1. 旧资料重采后使用了新配置或新时间：任务 2/3 测试原版本依据不变。
2. 文件已落盘而事务失败、接收提交而回执文件缺失：任务 1/3/4 故障注入确认两种恢复均不重建结果。
3. 双进程接收、重试与暂停/权限撤销竞争：任务 3 使用真实数据库并发和旧代次检查。
4. 失败显示成零候选，或候选导出只包含第一页：任务 4/5 覆盖失败未知和 50 条完整导出。
5. 历史结果缺元数据却被包装成新完整成功：任务 2/4 保留来源与限制标记，缺失必需依据不得冒充接收成功。
