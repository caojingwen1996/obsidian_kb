# RiskHot — [AGENTS.md](http://AGENTS.md)

## 1. 项目工作原则

- 执行任务前，识别当前所处的软件生命周期阶段。
- 优先阅读项目现有设计文档，继承已确认的设计决策。
- 根据任务类型选择已安装的专业 Skill。
- 同一任务优先确定主 Skill，其他 Skills 仅作为必要补充。
- 重要设计变更必须说明原因、影响范围及关联文档。
- 所有文档类编写必须用中文.

## 2. Skill 调度规则


| 开发阶段      | 主要 Skill              | 辅助 Skill          |
| --------- | --------------------- | ----------------- |
| 系统功能详细设计  | BMAD Method           | 项目功能设计规范          |
| 产品页面与原型设计 | Impeccable            | UI/UX Pro Max     |
| 系统技术架构设计  | Architecture Designer | BMAD Architecture |
| 工程开发与实现   | Superpowers           | 项目工程开发规范          |


以上为工具选择策略。执行时应先检查对应 Skill 是否可用，并遵循实际安装的名称与使用接口。缺少 Skill 时须明确说明。

### 功能设计

- 读取上游业务架构及模块功能架构文档。
- 明确功能清单、业务流程、规则、状态及异常场景。
- 明确页面与操作的功能映射关系。
- 输出可以被验证的验收标准。
- 文档输入：先读 `02-业务架构与领域设计/` 的业务总览与相关层设计，再读 `03-系统功能架构/` 的功能总览及对应模块设计（均位于 `docs/system-design/` 下）。
- 文档产出：在 `docs/system-design/03-系统功能架构/` 更新对应功能设计；涉及 AI 任务时同步核对其 `AI任务与提示词/` 内容及状态。



### 原型设计

- 以已确认的功能设计为输入。
- 先确定页面信息架构，再设计具体交互。
- 优先复用统一布局、设计系统和组件。
- 输出可运行原型并进行设计评审。
- 文档输入：读取对应模块功能设计，以及 `docs/system-design/06产品UI原型设计/` 中的统一规范、相关页面设计和现有原型。
- 文档产出：在该原型目录对应的页面或模块子目录维护设计说明、交互原型与验证记录，保留功能到页面操作的对应关系。



### 技术架构设计

- 基于已确认的功能需求和非功能需求。
- 明确组件边界、数据主责、接口契约及依赖关系。
- 关键技术决策应有依据和权衡记录。
- 检查跨模块架构一致性。
- 文档输入：读取已确认的业务与功能设计，再按[[tools/RiskHot/docs/system-design/04-系统架构设计/大纲|系统架构设计大纲]]查阅总体架构、专题架构、模块详细设计及公共技术契约。
- 文档产出：按职责更新 `docs/system-design/04-系统架构设计/` 下对应文档；关键决策及验证方案、结果进入 `05-架构治理与验证/`，场景案例与执行报告在 `docs/system-design/05-场景验证/` 维护。



### 工程开发

- 依据已确认的技术设计制定实施计划。
- 按任务粒度进行编码、测试及代码审查。
- 保持实现与业务规则、架构决策、接口契约一致。
- 关键功能完成后提供测试和验收证据。
- 文档输入：依据[[tools/RiskHot/docs/system-design/工程开发与实现步骤|工程开发与实现步骤]]，核对对应技术设计、公共契约、已确认的迭代规格和实施计划；页面开发同时读取对应 UI 设计。
- 文档产出：在 `docs/superpowers/specs/` 与 `docs/superpowers/plans/` 维护迭代设计和计划，在 `docs/verification/` 保存实际验证结果；实现中发现设计偏差时回写对应设计文档，同步必要的操作说明、项目索引和维护日志。



## 4. 质量与一致性

- 文档、原型和代码之间应保持需求可追踪。
- 不得擅自改变已确认的业务规则或架构决策。
- 遇到冲突应指出冲突来源、影响及建议处理方案。
- 不得将未经验证的实现标记为已完成。



## 5. 交付要求

每个复杂任务至少给出：

- 输入依据
- 关键设计或实现结果
- 涉及的文件
- 验证结果
- 遗留问题与风险



## 6. 项目结构与目录约定

以下路径以 RiskHot 项目根目录为基准，工程代码统一放在 `src/` 下：

```text
RiskHot/
  src/
    data/        信源清单、连接配置与演示配置
    db/          数据库建库 SQL
    information-ingestion/  信息采集：从信源配置到候选入库
      sources/     信源档案、版本审计、目录读取与连接器注册
      processing/  资料获取、解析、标准化与 AI 事件候选抽取
    event-management/  完整事件：独立候选、归组、关系、增量、评价、复核与交付
    platform/    身份认证、权限、数据库、工件存储与通知
    runtime/     API、Temporal 工作流、Worker、投递与调度进程
    web/         M1管理、事件阅读、流水线全景、同源接口调用与页面状态
    scripts/     初始化、启动、运行、监测与后台服务管理命令
    tests/       自动化测试及测试辅助代码
  docs/          业务、功能、技术设计、UI 原型、实施计划与验证记录
  aihot/         参考资料、外部源码快照与旧设计归档
  .agents/       项目技能与协作配置
  _bmad/         已安装的 BMAD 工具与工作流
  _bmad-output/  BMAD 规划与分析产物
  AGENTS.md      Agent 工作规则及项目结构
  README.md      安装、启动、运行与操作说明
  index.md       项目文档导航
  log.md         项目维护日志
  package.json   npm 命令及依赖声明
  package-lock.json 依赖版本锁定
  tsconfig.json  TypeScript 编译与类型检查配置
  compose.yaml   本地依赖服务编排
  .env.example   环境配置示例
  .env           本地私有配置（不提交）
  .riskhot/      本地工件、运行记录及日志（不提交）
```

`information-ingestion/` 汇集信息采集相关的业务代码：`sources/` 对应架构中的 M1，`processing/` 对应当前已实现的 L0 候选处理切片。架构文档及已有接口、数据库和工作流标识继续沿用原编号，代码目录按业务职责命名。

目录维护规则：

1. 新增业务代码、前端实现、命令脚本、自动化测试与 SQL 均归入 `src/`，按职责建立或复用子目录；根目录保留项目配置和文档入口。
2. 信源身份与参考元数据统一维护在 `src/data/source-catalog.js`，连接范围维护在 `src/data/source-connections.json`；`source-demo.js` 仅用于原型演示。
3. `docs/` 中的设计原型、`aihot/` 中的参考快照及已安装工具保留各自的资料归属；实际产品实现放入 `src/`。
4. 所有 npm 命令在项目根目录执行，由 `package.json` 指向 `src/scripts/` 等实际入口。
5. 调整目录时，同步更新导入、文件读取和启动路径，以及 `package.json`、`tsconfig.json`、README 与本节说明。
6. 私有配置、依赖目录、构建产物及运行数据遵循 `.gitignore`，不纳入代码提交。
7. 实际 M1 页面由运行层在 `/m1` 提供，消费真实管理接口；`docs/` 原型只作为设计依据，不导入其演示运行状态。
8. 流水线全景由 `/pipeline` 提供，位于“配置”分组，与信源管理中心同级；流程图、固定任务定义和提示词来源登记由 `npm run pipeline:sync` 生成，`npm run pipeline:check` 检查其同步状态；已登记提示词的正文及元数据在页面打开或刷新时由服务端实时读取，修改正文、版本或状态无需手动同步。提示词读取只服务展示，不修改或发布运行任务包。页面仅用于业务定义阅读，不触发流程执行；来源文档按明确清单提供只读入口，不开放任意文件路径。
